# Management, driver and MQTT operation

The default build enables `bridge`, `scripting` and `gui`. A full API-only build
uses `--no-default-features --features bridge,scripting`. The core
`--no-default-features` build omits both LG and Rhai; it still supports local
transports, management and durable retained cleanup. Omit `cloud_account` and
`drivers` in that build. Disabled capabilities are rejected explicitly.

Add these optional sections to the daemon's TOML configuration. File paths are
relative to the configuration file. Unknown fields and invalid types are rejected.

```toml
[management]
bind = "127.0.0.1:8080"
gui = true
raw_inject_toggle = false

[drivers]
directory = "../rusthinq-scripts"
topic_prefix = "rusthinq"
bindings = {}
watch = true

[external_mqtt]
host = "localhost"
port = 1883
tls = false
client = "rusthinq-0.2"
inventory = "retained.json"
```

This is an optional-section example, not a complete device/TLS configuration.
Omitting `external_mqtt` disables remote publication while preserving script output
observation and management. Network failures keep the core daemon running. When both `drivers` and `external_mqtt` are configured, an independent authenticated
MQTT connection subscribes to `{drivers.topic_prefix}/#` at QoS 1 and routes
`{prefix}/{device}/{property}/set` to the driver’s `on_set_property(ctx, prop, value)`
unvalidated; a driver without it ignores commands. Any validation, reject and
semantic topic is the script's; scripts publish with `ctx.publish_raw(topic, payload,
retain)`. The 0.1 `il_prefix` setting no longer exists in the host. Retained instructions are acknowledged and discarded;
duplicate QoS 1 packets already handled in that connection are not executed again.
Clean reconnects do not replay queued commands. Admission errors are reported in
management events; PUBACK confirms receipt, not appliance execution. Cloud, raw
and account control topics remain outside this property route. The subscriber
stops with the device core, before terminal output is flushed by the publisher.

Authentication is optional, as in 0.1: setting both `user` and `password` enables HTTP Basic on every route. Without them, anyone who can reach `bind` can control devices and the bridge, so bind a non-loopback address only on a trusted LAN.
Terminate HTTPS at a trusted proxy when exposing management remotely. Set `gui`
to false for API-only operation. State-changing browser requests and WebSocket
upgrades require a matching Origin/Host; API clients may omit Origin.

## Management routes

- `GET /api/health`, `/api/devices`, `/api/mqtt`: state and adapter status.
- `POST /api/devices/{id}/forget`: `{ "incarnation": 1 }`; 202 means admitted,
  not durable completion. Observe application events for removal/failure.
- `POST /api/devices/{id}/send`: incarnation, generation and string `payload`;
  successful transport receipt means wire write, not appliance acknowledgement.
- `POST /api/devices/{id}/invoke`: incarnation, generation, script_generation,
  function and string input. For drivers use `function: "__command"` and a JSON
  string containing `prop` and `value`. 202 returns the execution sequence;
  `/api/events` reports execution and delivery results separately.
- `POST /api/devices/{id}/inject`: incarnation, generation, hex and direction
  (`toDevice`/`fromDevice`); disabled unless explicitly configured. Synthetic
  input does not forge transport acknowledgements or lifecycle identity.
- `/api/events`: typed WebSocket events, initial snapshot and loss indications.
- `/ws`, `/device?id=...`, `/monitor?id=...`: existing dashboard and monitor.

Integer generation fields are presented as decimal strings in snapshots so JavaScript
cannot lose precision. Control requests must use those captured values.
Cloud account login/logout now use the management API and existing dashboard.
Per-device GUI pair, enable, disable and unpair use the same management API.
See [tool migration](0.2-tools-migration.md#tools-migration) for CLI/MCP and staged 0.1 conversion.

## LG account ownership

Add `cloud_account = "account.json"` at the top level, before any table header, of the daemon configuration
to enable account management. The parent directory must already exist. The
exclusive sidecar lock prevents multiple writers; schema 1 atomically stores only
country and refresh token. New checkpoints have mode 0600 on Unix. The file is
credential material and belongs with restricted deployment backups. Invalid or
oversized checkpoints are preserved and stop startup. A write failure makes the
owner refuse further checkpoint writes until restart.

- `GET /api/cloud`: enabled, loggedIn, stored, country, busy and redacted error;
  no token or authorization code is returned.
- `POST /api/cloud/login` with `{"country":"KR"}` returns the LG sign-in URL.
- `POST /api/cloud/login/complete` with `{"url":"<final LG callback URL>"}`
  exchanges the code, authenticates the account, saves credentials and then
  activates it. The callback must be the HTTPS LG `login/iabClose` endpoint with
  exactly one nonempty code. Starting another login replaces the pending flow.
- `POST /api/cloud/refresh` explicitly authenticates saved credentials again.
- `POST /api/cloud/logout` writes a credential-free checkpoint before clearing
  active and pending accounts; HTTP success confirms durable removal.

An owned actor serializes account changes through an eight-command queue and a
one-slot priority logout queue. Accepted logout advances a cancellation epoch:
in-flight network work is dropped and older queued requests return cancellation.
Network cancellation cannot leave a background login that activates after logout.
Accepted checkpoint writes are joined on shutdown. On restart, saved credentials
enter the same renewal schedule as active accounts. Remote failures preserve the
file and are visible in status without preventing local device service. A failed
replacement preserves the old active account. Successful refresh keeps the LG
client ID and updates authentication atomically. Renewal occurs before expiry,
with a margin of ten percent of remaining lifetime, capped at sixty seconds.
If LG omits refresh expiry, the adapter uses a one-hour fallback. Network and
transient HTTP failures back off from one second to at most five minutes.
Authentication rejection, API rejection and checkpoint failure stop automatic
renewal; use explicit refresh, a new login or storage repair/restart. Status and
cloud device APIs refuse expired authentication even while renewal is pending. Account authentication does not imply that any appliance is paired or relaying.
The dashboard shows account status and uses these same APIs without external MQTT.

## Retained ownership and deletion

Every retained value is inventoried durably before network publication. QoS 1
PUBACK confirms deletion; network failure means an unknown outcome and retryable
work. The exclusive MQTT connection does not share packet IDs with another owner.

`POST /api/mqtt/retained/delete` accepts exactly one scope:

```json
{"scope":"topic","owner":"device/1:d/1","topic":"rusthinq/d/available"}
{"scope":"owner","owner":"device/1:d/1"}
{"scope":"all"}
```

The route returns `confirmed`, counting broker-confirmed deletions. It clears queued
retained values in the selected scope and durably records the full deletion batch
before its first tombstone. Timeout returns an unknown result rather than success.
Reconnect drains saved deletion intent even if the device is still known. Durable
removal cleans orphaned incarnation owners; known offline device inventories are
preserved. Reconnection to the same broker clears old owner topics before replaying
current retained values. Inventory files are broker-specific: do not repoint the
same inventory at a different broker or change topic mappings without cleanup.

Inventory schema 2 adds `deleting` to schema 1 ownership records. Schema 1 loads
without deletion intent; the next durable write upgrades it. Older binaries cannot
read schema 2: keep a pre-upgrade backup for rollback. Never delete the sidecar lock
while an owner runs, nor erase the inventory as a substitute for remote cleanup.

## Current limits

Driver initialization, transport callbacks, timer effects and script-side IL
validation are implemented. Set `drivers.watch` to true for automatic reload
(default false): a single owned task polls source content once per second, prepares
replacements off the async thread, and replaces only the captured current session
and script generation. Successful reload clears old timers and runs `__init` in the
fresh scope before admitting subsequent commands or data. Unrelated model files
do not trigger reload; changes to imported modules do. Compilation failure leaves the previous scope running and reports an
application rejection event; another source edit can retry. Faulted scripts are not
restarted merely because they faulted. Shutdown joins all preparation work.

Driver `on_drop` runs once after finishing the active call and cancelling queued
calls. Retirement workers remain in the worker budget until joined; the application
continues processing other sessions while callbacks finish. Only opaque publications
are accepted from a disconnected current incarnation/generation; a replacement
connection invalidates these outputs. Device sends and timers are rejected. Faulted
scripts stay faulted and are not restarted for the hook. `scriptStopped` reports
execution separately from publication confirmation.

The daemon stops device services first, flushes admitted terminal MQTT output for
up to ten seconds, then joins adapters and signing. Unconfirmed output is an error;
retained inventory remains available for deletion/recovery. A crash cannot guarantee
that an exit hook executes. Known disconnected inventories are preserved, including
descriptors and property records, when the availability hook updates its own topic.

Model/platform/device-type information shares the durable lifecycle writer and is
incarnation-scoped. Restart restores it for offline device-list projection and
ThinQ1 model selection after reconnection. ThinQ2 readiness still comes from fresh
provisioning events. Forget prunes model records; stale incarnation writes are
rejected. Snapshot `modelPersisted` distinguishes live observation from saved data.
Lifecycle schema 2 adds `metadata`; schema 1 loads with an empty model map and
upgrades on its next write. Older binaries cannot read schema 2: retain a backup
for rollback. Unknown/malformed ownership data is rejected without overwriting it.

The L4 LG HTTP/OAuth account and registration adapter is implemented and fixture-tested,
and is now exposed through optional `cloud_account` configuration and management.
Pairing, outbound LG transport/reconnect, MQTT cloud/raw control routes and full
tool migration remain tracked in the milestones.
Real-appliance/LG-account validation is excluded; automated tests remain required.

## Explicit driver reload and fault recovery

With configured drivers and the `scripting` feature, an online device with an
attached driver exposes `driverReloadable=true` in `/api/devices`. The dashboard
shows `Reload script`, or `Recover script` when the worker is faulted. This operation
works without external MQTT and without the file watcher. A fault does not trigger
an automatic restart or replay.

`POST /api/devices/{id}/reload` reads the configured model/module files again:

```json
{"incarnation":"1","generation":"2","script_generation":"1"}
```

Take all three scope fields from the latest device snapshot. A successful response
contains the new `scriptGeneration`; `initialized=false` means initialization is
queued but its execution/effects are not confirmed by that response. Script events
report eventual success or failure. Source/compile failure preserves the previous
worker, generation and fault state; rejection events carry the preparation error.
A different model/session/script generation
rejects the prepared replacement; old timers are removed only after replacement.

The management authentication/same-origin rules also apply to reload. HTTP 409
reports a stale scope, 429 reports bounded admission pressure, 503 reports disabled
scripting/drivers or a stopped runtime, and 400 reports invalid input/preparation.
A timeout reports an unknown outcome: inspect the current script generation/events
before deciding to retry. Neither the API nor GUI automatically retries.

Automatic attachment and explicit disk reload share L5's two-job preparation budget.
L6 owns each blocking preparation job and joins it on shutdown. A cancelled caller
cannot authorize a later replacement if cancellation is observed before reload;
an already-started worker replacement can have an unknown outcome to that caller.
Retained outputs from reinitialization use the existing MQTT topic inventory and
exact/owner/all/restart deletion paths; reload adds no separate publisher.

## Per-device LG bridge

Configuring `cloud_account` also opens its private `.pairings` checkpoint.
`GET /api/cloud/devices` reports paired, enabled, connected and redacted error
states; `GET /api/cloud/inventory` reads the authenticated LG device inventory.
`POST /api/devices/{id}/bridge/{pair,enable,disable,unpair}` requires the captured
incarnation. Pair additionally accepts deviceType and optional alias. Registration
intent is persisted before the remote request. Ambiguous outcomes stay pending;
reconcile with unpair before trying a new registration or forgetting the device.

Pair and enable are separate durable decisions. Restart restores registered
devices with their saved enable intent. A session waits for the matching account
and local device, then owns verified TLS and RTI or MQTT provisioning. Reconnect
uses bounded exponential delay; uplinks never survive reconnection. Logout,
account replacement, local replacement and event loss cancel the current session.
Disabling joins the socket task and clears local bridge state. Cloud command
ACKs follow confirmed local writes; they do not claim appliance execution.
ThinQ2 provisioning uses actual local deployment app/platform information.

The MQTT subscriber also accepts reserved, non-retained JSON control envelopes:
`{prefix}/{device}/$bridge/{pair,enable,disable,unpair}/set` requires
`incarnation`; pair also requires `deviceType`. Raw routes
`{prefix}/{device}/$raw/{inject,emit}/set` require captured `incarnation` and
`generation`, `hex`, and `inject_ok:true`. Raw admission requires the runtime
injection switch, which always starts off. `management.raw_inject_toggle = true` allows
switching it with `POST /api/raw-inject {"enabled":true|false}` (`GET` reads it),
`rusthinqctl raw-inject on|off|status` or the device monitor; the switch is shared by the
inject route, the monitor and these MQTT routes, and is never persisted. Restrict these
MQTT routes with broker ACLs.
Retained control envelopes are discarded and QoS 1 duplicates are suppressed in a
bounded connection-local cache. PUBACK acknowledges receipt; errors appear in
management events. No command queue crosses reconnect. The subscriber currently
requires the scripting build and configured drivers/topic prefix; management
bridge APIs remain available independently of Rhai and external MQTT.

Archived 0.1 registrations can be reconciled with
`POST /api/devices/{id}/bridge/adopt`: captured incarnation, matching archiveDevice,
and archive JSON. The daemon confirms the device in the authenticated LG account
before atomically storing disabled ownership. Region/platform mismatches, stale
identity and existing ownership are refused. Enable remains a separate decision.
See [cloud registration adoption](0.2-tools-migration.md#tools-migration-adopt-archived-cloud-registration)
for CLI usage and expired-certificate handling.

## LG notifications in Rhai drivers

With `bridge` and `scripting` enabled, `Start LG feed` also delivers newly observed
LG account notifications to live drivers. This remains an explicit, ephemeral
opt-in: restart disables the feed, and history is never replayed into scripts.
Add the optional callback to a model driver and reload it:

```rhai
fn on_cloud_event(ctx, event) {
    // Account events have no identified device; ignore them for this automation.
    if event.correlation != "device" { return; }
    ctx.publish_raw("automation/lg/" + ctx.id(), event.raw, false);
}
```

The event includes `topic`, `raw`, parsed `payload`, local observation time `t`
(milliseconds since Unix epoch), `sequence` (string), `devices` (array of IDs),
and `correlation` (`device` or `account`). Match notification payload fields in
script code; the host does not interpret appliance semantics. Device events go
only to matching local device IDs. Account events without an identified device
are offered to every live driver; each callback chooses whether to handle them.
Offline devices and unattached scripts do not receive notifications.

Callbacks run through the existing bounded, serialized script workers. Admission
captures the current local session and script generation; removal, reconnection,
or reload invalidates pending stale notifications. Queue overflow reports a
script rejection and drops the event, without blocking LG reception or replaying
it later. Existing script error/fault behavior and output fencing apply.
For manually attached scripts, set `Callbacks.cloud` to the desired entry point;
that entry point receives the event as a JSON string (configured model drivers
parse it before calling `on_cloud_event`).
