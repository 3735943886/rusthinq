# Management, driver and MQTT operation

Add these optional sections to the daemon's JSON configuration. File paths are
relative to the configuration file. Unknown fields and invalid types are rejected.

```json
{
  "management": {
    "bind": "127.0.0.1:8080",
    "gui": true,
    "raw_inject": false
  },
  "drivers": {
    "directory": "../rusthinq-scripts",
    "topic_prefix": "rusthinq",
    "il_prefix": "ildevice",
    "bindings": {}
  },
  "external_mqtt": {
    "host": "localhost",
    "port": 1883,
    "tls": false,
    "client": "rusthinq-0.2",
    "inventory": "retained.json"
  }
}
```

This is an optional-section example, not a complete device/TLS configuration.
Omitting `external_mqtt` disables remote publication while preserving script output
observation and management. Network failures keep the core daemon running. Broker
subscriptions and automatic command intake are not yet implemented; use the
management invoke endpoint for driver commands.

Non-loopback management requires both `user` and `password` (HTTP Basic).
Terminate HTTPS at a trusted proxy when exposing management remotely. Set `gui`
to false for API-only operation. State-changing browser requests and WebSocket
upgrades require a matching Origin/Host; API clients may omit Origin.

## Management routes

- `GET /api/health`, `/api/devices`, `/api/mqtt`: state and adapter status.
- `POST /api/devices/{id}/forget`: `{ "incarnation": 1 }`; 202 means admitted,
  not durable completion. Observe application events for removal/failure.
- `POST /api/devices/{id}/send`: incarnation, generation and string `payload`;
  successful transport receipt means wire write, not appliance acknowledgement.
- `POST /api/devices/{id}/invoke`: incarnation, generation, script_generation,
  function and string input. For drivers use `function: "__command"` and a JSON
  string containing `prop` and `value`. 202 returns the execution sequence;
  `/api/events` reports execution and delivery results separately.
- `POST /api/devices/{id}/inject`: incarnation, generation, hex and direction
  (`toDevice`/`fromDevice`); disabled unless explicitly configured. Synthetic
  input does not forge transport acknowledgements or lifecycle identity.
- `/api/events`: typed WebSocket events, initial snapshot and loss indications.
- `/ws`, `/device?id=...`, `/monitor?id=...`: existing dashboard and monitor.

Integer generation fields are presented as decimal strings in snapshots so JavaScript
cannot lose precision. Control requests must use those captured values.
Cloud login/logout and GUI bridge management are still pending.

## Retained ownership and deletion

Every retained value is inventoried durably before network publication. QoS 1
PUBACK confirms deletion; network failure means an unknown outcome and retryable
work. The exclusive MQTT connection does not share packet IDs with another owner.

`POST /api/mqtt/retained/delete` accepts exactly one scope:

```json
{"scope":"topic","owner":"device/1:d/1","topic":"rusthinq/d/available"}
{"scope":"owner","owner":"device/1:d/1"}
{"scope":"all"}
```

The route returns `confirmed`, counting broker-confirmed deletions. It clears queued
retained values in the selected scope and durably records the full deletion batch
before its first tombstone. Timeout returns an unknown result rather than success.
Reconnect drains saved deletion intent even if the device is still known. Durable
removal cleans orphaned incarnation owners; known offline device inventories are
preserved. Reconnection to the same broker clears old owner topics before replaying
current retained values. Inventory files are broker-specific: do not repoint the
same inventory at a different broker or change topic mappings without cleanup.

Inventory schema 2 adds `deleting` to schema 1 ownership records. Schema 1 loads
without deletion intent; the next durable write upgrades it. Older binaries cannot
read schema 2: keep a pre-upgrade backup for rollback. Never delete the sidecar lock
while an owner runs, nor erase the inventory as a substitute for remote cleanup.

## Current limits

Driver initialization, transport callbacks, timer effects and script-side IL
validation are implemented. Lifecycle `on_drop`, automatic file watching/reload,
persisted model metadata, outbound LG registration/reconnect, automatic MQTT
command subscriptions and full tool migration remain tracked in the milestones.
Real-appliance/LG-account validation is excluded; automated tests remain required.
