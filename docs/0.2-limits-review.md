# Current constraints review — 2026-10-17

This review checks the operating guide against the source and current tests. It
is not a new release-approval gate. Historical milestone acceptance remains in
[the validation ledger](0.2-validation.md#milestones).

## Why the previous list looked unfinished

The former `Current limits` section described implemented reload, retirement,
shutdown and metadata contracts, then incorrectly said pairing, reconnect, bridge
controls and migration were still pending. Those paths exist in
`cloud_devices.rs`, `session.rs`, `mqtt_commands.rs`, and `migration.rs`, with host
integration tests. The operating guide now separates implemented behavior, actual
constraints, and intentional failure semantics. The stale bridge crate summary
is corrected too; dated implementation evidence is kept as history.

## Lint suppression review

No lint suppression is needed for these paths:

- Capture readiness uses a normally routed HTTP/WebSocket fixture server. Only
  the enable POST and exact notification socket path exist; status GETs/wrong
  paths fail. The test still checks cursor/device parameters and connecting/
  connected transitions. No custom handshake error callback is necessary.
- SoftAP request construction uses one immutable `AccessPoint` configuration for
  both initial and scan-refined passes. Scan overrides retain precedence; request
  serialization is independent of socket lifetime.
- A cloud connection takes `CloudSession` (identity, ownership and transport) and
  `SessionSignals` (mutable event/cancellation sources), rather than eleven
  positional arguments. Session generations and cancellation ownership are kept.
- Feature-dependent bindings use conditional construction or immutable shadowing,
  rather than `allow(unused_mut)`.

Workspace source has no `allow(clippy::...)` or `allow(unused_mut)` after these
changes. This does not mean every `expect` is a smell: assertions after bounded
reads or validated state transitions are distinct from ignoring a lint. No
unchecked untrusted input has been substituted to satisfy Clippy.

P1 and P2 are now implemented. The table preserves the original findings and

### P1 implementation

Driver compilation fingerprints the exact source/module strings already read,
rather than rereading disk after preparation. Successful attachment/reload commits
that fingerprint alongside the device session and script generation; failed/stale
requests cannot overwrite it. Retirement removes the stored baseline. Generic
explicit scripts without a filesystem bundle are left under their explicit owner.

The watcher compares against this committed baseline at startup, on native file
events, and after attachment/generation changes. Other state changes do not scan
sources. File debounce and capacity retry preserve their deadlines across lifecycle
wakeups. Tests cover late attachment plus unrelated edits, imported module edits
with exactly one generation advance, compilation failure preserving the live
scope, a prepared bundle becoming outdated before manual reload/watcher startup,
and cancellation during debounce. Reconnection starts a new session at script
generation 1 and ignores unrelated edits there too. The automatic attachment
regression also uses a source budget above the old fixed worker ceiling. Existing
session fencing tests still apply.

### P2 implementation

`rusthinq-driver-config` is a small engine-independent crate so both the daemon
(including builds without scripting) and Rhai preparation use one limits type,
defaults and validation. `[drivers.limits]` configures source, strings, operations,
output count/aggregate bytes, state keys/bytes, worker capacity and input bytes.
The engine uses that configuration for automatic/manual/file preparation; automatic
attachment derives its worker settings from the same value. Existing workers
retain their configured limits across reload, and configuration changes require
restart.

Defaults remain unchanged. Validation rejects zero/unlimited, unknown fields,
invalid types, allocation-size overflow and unsupported semaphore capacities.
Source accounting still covers generated entry points and the entire static
module bundle; lowering limits cannot bypass aggregate source/output accounting.
Regression tests exercise custom parsed values/defaults, invalid limits,
aggregate source/output exhaustion and immutable prepared fingerprints. Existing
worker overload/reload tests cover queue backpressure and generation fencing.
See the operating guide for the complete configuration example.

## Contracts to keep

| Behavior | Why it is not fixed by relaxing it |
| --- | --- |
| No guaranteed `on_drop` on crash/power loss | The process cannot execute code after termination. Use persisted inventory, reconnect resync and explicit recovery; do not claim exactly-once remote cleanup. |
| No automatic script restart/replay after a fault | Reinitialization or replay can repeat appliance commands. Opt-in recovery would need a bounded policy and explicit idempotency semantics. Manual recovery already exists. |
| ThinQ2 readiness requires fresh provisioning | A stored model or previous session cannot prove the new connection's deployment/identity. Restoring it blindly would bypass session fencing. |
| Sent/Queued are not appliance acceptance | Transport progress and broker PUBACK do not establish device execution. Model-specific acknowledgement/correlation belongs in the driver or protocol that can prove it. |
| Real-account/appliance validation is separate | Synthetic replay and fake services establish host behavior, not undocumented live LG service or firmware compatibility. Run model regressions in the external scripts repository and record any live validation separately. |

See [the polling audit](0.2-polling-audit.md) for the rationale behind retained
reconciliation, retry, liveness and telemetry periods.
