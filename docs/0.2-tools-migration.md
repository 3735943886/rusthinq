# Tool migration and rollback

Build the consolidated tools with `cargo build -p rusthinq-tools --bins`. Online
commands use the daemon management API and work without an external MQTT broker.
Set `RUSTHINQ_API` (default `http://127.0.0.1:8080/`) and, when required,
`RUSTHINQ_USER`/`RUSTHINQ_PASSWORD`. Remote endpoints require HTTPS. Redirects,
URL credentials and query tokens are refused. Tool errors omit credentials.

| 0.1 capability | 0.2 command | Compatibility decision |
| --- | --- | --- |
| Device list / commands | `rusthinqctl devices`, `set DEVICE PROPERTY VALUE`, `send DEVICE JSON` | Capture incarnation/session/script generation before admission |
| Packet parser | `packet-parser HEX` | Shared offline AABB/TLV codec; unknown frames remain analyzable |
| Packet sender | `packet-sender DEVICE HEX --inject-ok` | Explicit client opt-in and daemon `management.raw_inject=true` required |
| Capture | `rusthinq-capture DEVICE OUTPUT.jsonl` | Append rx/tx/note JSONL; sent means completed local wire write; gaps recorded |
| LG monitor | `lgcloud-monitor list` | Authenticated management `/api/cloud/inventory`; account owned by daemon |
| Retained GC | `rusthinq-retained-gc '{"scope":"all"}'` | Kept for repair; deletes only durably owned inventory with PUBACK confirmation |
| MCP | `rusthinq-mcp` | Newline JSON-RPC, offline codecs/capture, managed device list/health/injection |
| SoftAP setup | `rusthinq-setup` | Direct appliance bootstrap; ThinQ1, ThinQ2 and Whisen flows retained |
| Driver test runner | `rusthinq-script-test PATH_TO_SCRIPTS` | Executes upstream test functions against the production Rhai host |
| Config migration | `rusthinq-migrate OLD_CONFIG DESTINATION_DIRECTORY` | Offline staged output; never edits the original installation |

MCP replaces `set_mqtt_host` with `set_api_endpoint`. Other baseline tool names
remain. Notifications have no response; stdout contains protocol messages only.
`read_capture` accepts legacy and new JSONL, filters direction/type and limits
line/file size. Capture ends on a disconnected event stream instead of silently
joining separate sessions. Notes are bounded to 64 KiB. Review a `lost` record
before drawing conclusions from a capture.

SoftAP setup uses a device's self-signed bootstrap endpoint, then installs the
configured server identity. This deliberate bootstrap trust exception is confined
to the setup executable. LG cloud and management TLS continue verifying peers.

## Staged 0.1 migration

Stop 0.1 before cutover. Run the migration against its configuration and a new,
nonexistent directory. It creates `config.toml`, a private copy of the old config,
a redacted `migration.json`, and a private cloud archive when configured. Country
and refresh token become the new schema-1 account checkpoint. Account tokens are
never printed. Certificates and script directories keep absolute references to
the original installation; retain them for both versions.

Review the generated configuration before starting 0.2. External MQTT credentials,
retained ownership and raw permissions require explicit configuration. The new
management endpoint starts on loopback with raw injection disabled. Proxy/root
certificate overrides, advertised endpoints and custom outbound DNS are refused
rather than silently changed. These configurations need manual mapping and
verification. Legacy per-device cloud files do not identify a durable new account
owner; they are archived for reconciliation and are never automatically enabled.
When present, `known_devices.json` is converted into a new offline device ledger
with fresh deterministic incarnations. Recognized model/platform metadata is
preserved; archived orphan entries remain known without invented metadata. Session
generations start separately and advance durably after restart. The original
last-seen timestamps, model IDs and software versions remain in the archive.

Both 0.1 retained-state shapes (`id -> properties[]` and timestamped device
objects) produce `retained-import.json`. It preserves exact property topics under
separate `legacy/0.1:` owners, without assigning them to new incarnations and
without requesting deletion. Point the reviewed external MQTT configuration's
`inventory` at this file on the same original broker, then request explicit
retained cleanup through the management API or retained-GC tool before republishing
new owners to overlapping topics. Every deletion still requires broker PUBACK;
failed attempts survive restart. Do not merge the imported file over an existing
0.2 inventory. The archived original retained state remains available for rollback.

Keep original state, configuration, certificates and the pinned reference revision
`2473c34683130c29ad2f07d560d15b2c94342a36`. To roll back, stop 0.2 and restart
0.1 with those originals. Never run both daemons against the same ports or state.
Rollback does not undo an LG registration/deletion performed after cutover; inspect
and reconcile those remote changes before enabling the old bridge. The migration
itself performs no network operations. Do not delete `legacy/0.1` until remaining
release acceptance gates are met.

`RUSTHINQ_SCRIPTS_CHECKOUT=/path/to/pinned/checkout scripts/check-0.2.sh` runs
formatting, workspace tests, strict Clippy, all eight bridge/scripting/gui build
combinations, GUI JavaScript syntax and the pinned upstream compatibility suite.
This automated check does not claim appliance or real-account acceptance.

There is no silent 0.1 topic alias or automatic deprecated-command forwarding in
0.2. Use the replacement commands during staged cutover; the preserved 0.1 archive
is the rollback implementation until the remaining release gates close.

The migration report includes `migratedDevices` and `retainedTopics`. Missing old
state initializes no imported entries; malformed, oversized or wildcard-bearing
inventory stops the migration and leaves the destination uncreated. Model/platform
and retained conversion are tested against production storage recovery.

## Capture ingress replay

`rusthinqctl replay DEVICE CAPTURE.jsonl --inject-ok` validates the complete
capture before submitting any input. It replays only `rx` packet records, including
legacy records without a type field, in their recorded order. Notes, sent packets,
ACKs and CLIP envelopes are omitted. Timing is immediate; it does not reproduce
historical delays or retransmit captured cloud commands to an appliance.

The command uses management `fromDevice` injection, so the server also requires
`management.raw_inject=true`. Its incarnation/session scope is captured once and
never updated during replay. Device replacement rejects subsequent input; the tool
stops at the first unconfirmed request and never retries. A loss record, malformed
hex, over 1000 receive packets, an oversized line or file prevents all submissions.
ThinQ1 packet input enters the ordinary B64 monitor adapter; ThinQ2 input enters the
ordinary raw packet adapter. Replay feeds scripts and records injected events;
it does not forge appliance delivery acknowledgements or live cloud traffic.

## Adopt archived cloud registration

After logging into the matching LG account, run
`rusthinqctl adopt DEVICE /path/to/legacy-cloud/device_DEVICE.json`. The filename
must match the device ID. The command captures its current incarnation and submits
bounded archived material over the authenticated management API. No credentials
are printed. Adopt performs a read-only LG inventory check; the same device must
exist in that account. ThinQ2 country and known local platform must match.

The daemon saves registration ownership in one atomic write, bound to the captured
account and incarnation, with enable intent false. Existing pairing intent or
registration is never overwritten. Logout/account replacement and device
replacement fence the operation. An import that finishes its durable write during
a replacement remains disabled under its original owner and reports a stale result;
it never activates a successor. Enable is a separate explicit command.

Both camelCase and snake_case archives are accepted; ambiguous duplicate aliases,
unknown keys and invalid endpoints/keys are rejected. Archived deploy information
is not used to invent a current deployment: ThinQ2 session setup still requires
actual local app/platform information. Expired but structurally valid certificates
remain available for explicit unpair/re-pair; enable rejects them. Adopt does not
create, delete or rename a remote device. Source archive files remain untouched.

The equivalent route is `POST /api/devices/{id}/bridge/adopt` with captured
`incarnation`, `archiveDevice` equal to `{id}`, and an `archive` JSON object.
The caller must select the archive corresponding to that device; LG inventory
confirms account membership, while the archive itself has no durable account ID.

For older ThinQ2 archives with no country field, adoption supplies the current
client's authenticated country before validating the material. An explicit country
in the archive must match it. ThinQ1's archived `platform:"thinq1"` discriminator
is accepted; an inconsistent discriminator is rejected. Import tests use generated
local certificates, including expired client identities, and no live LG account.
