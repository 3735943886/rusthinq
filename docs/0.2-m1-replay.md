# M1 reference replay — 2026-10-02

This increment verifies a real driver's ThinQ1 status slice and the production
external MQTT adapter. M1 remains open because the selected dishwasher is read-only:
a supported real ThinQ1 write fixture has not been identified. A separate ThinQ2

## Pinned inputs and comparison

The independent 0.1 reference is `2473c34683130c29ad2f07d560d15b2c94342a36`.
The drivers and their test inputs are pinned to rusthinq-scripts
`54292921c6edc72ea6ec901b1137845bff14e6ae`; hashes and the retained license are in
[fixture provenance](../crates/rusthinq-app/tests/fixtures/drivers/README.md).

D140110 supplies nine upstream captured AABB bodies and expected values for a
full dishwasher cycle. ThinQ1 hands B64-decoded bytes to `on_data`, so it does not
require a standalone JSON driver. The new tests construct the Mon JSON envelope
around the original bodies. They do not claim a captured ThinQ1 TLS session or
independently establish which platform the original appliance used.

The pinned scripts were exported with `git archive` into an isolated temporary
directory, without using the sibling working tree. The archived reference runner
passed **187 tests**, including D140110's expected cycle values, and checked all
**11 driver descriptors** with no problems. The new host verifies the same nine
cycle states, phase/remaining/total times, door/child-lock flags, short malformed
frames, read-only rejection and terminal availability. This is a comparison of
that status slice; it does not claim that all 187 tests run against the new host.

| Flow | New evidence | Outcome and limit |
| --- | --- | --- |
| Ready, running, child lock, rinsing, drying, door open, finished, standby, off | `tests/thinq1_driver.rs` feeds unchanged bodies through B64 decoding into D140110 | Descriptor and 16 state publications agree with pinned upstream expectations |
| ThinQ1 initial status | In-memory server + L6 runtime + automatic driver selection | ACK retains Header; buffered first status reaches the selected driver; one online device |
| No external broker | Application/event publication sink | Descriptor and values remain available; success does not imply broker delivery |
| External MQTT | Actual production adapter + bounded TCP MQTT peer, QoS1/PUBACK | 17 unique retained topics (descriptor plus 16 values), with inventory present before each publish |
| Disconnect/shutdown | Joined runtime, adapter left alive for terminal output | `available=false` is broker-confirmed before stopping MQTT |
| Restart cleanup | Adapter reopened with an empty publication cache | Exact status-topic deletion clears one; owner deletion clears the other 16; broker and durable inventory end empty |
| Supported washer control (ThinQ2) | Real Pd0F_F driver + application facade + device MQTT peer | Without remote-start grant, Rhai emits rejection and no device bytes; with grant, pause bytes match the pinned LG app control |
| Command result | Application event projection | `Sent` means transport write, with `deviceAcknowledged=false`; no response/ack is invented |
| Stale script scope | Owner checks live worker generation before submission | Known older/future generation returns Stale before occupying the worker queue; execution-time fencing remains |

Intentional improvements relative to the old composition are broker-independent
publication, durable exact-topic retained removal after restart, and explicit
transport versus appliance acknowledgment. The old raw/JSON send platform split
is preserved: a ThinQ2 raw command cannot be used to claim ThinQ1 command support.
No new IL interpretation is added to production Rust; semantic driver validation
continues to live in Rhai.

checkout, LG credentials or a live broker. The in-memory transports and bounded
local TCP broker are automated fixtures, not appliance validation.
