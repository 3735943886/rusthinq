<a id="design-reference-and-scope"></a>
### Reference and Scope

The reference is rustuya's transition from v0.3.0 to v0.4.0, especially its explicit
protocol/lifecycle core, I/O driver, owned discovery service, and documented decisions about
previously ambiguous behavior. The local reference checkout also contains subsequent 0.4.x
refinements; it is a design reference, not a dependency or an exact release specification.

Adopt the separation of decisions from execution and the practice of recording behavior
changes. Do not import its embedded/no_std requirements, library facade, outbound connection
model, or Tuya-specific response semantics. rusthinq remains a standalone server.


<a id="design-d0--new-implementation-with-staged-cutover-accepted-direction"></a>
### D0 — New Implementation with Staged Cutover (Accepted Direction)

The rethink-to-Rust lineage is a reason to reconsider inherited structure rather than
preserve it through compatibility wrappers. Build new daemon internals and retain the old
implementation as a fixed behavioral/protocol reference during development. This decision
is accepted; it does not imply any implementation work is complete.

Selectively reuse independently verified components. Preserve wire compatibility, the Rhai
script API that drivers depend on, and panic isolation where required; do not preserve internal types,
callbacks, global ownership, or factory dependencies solely for source compatibility.
Unexplained legacy behavior requires evidence under C4 before preservation or intentional change.

First relocate the tracked 0.1 project into `legacy/0.1/`, preserving its own workspace and
reference revision. The root is the new 0.2 project immediately, not a temporary second binary
inside the old architecture. Retain root Git metadata and 0.2 planning documents; archive old
project-specific hidden configuration with the old project. Exclude ignored artifacts and
personal files from the relocation. Root automation must target only the new project unless
an explicit reference comparison is requested.

The legacy workspace is a reference, never a dependency: forbid path dependencies, source
includes, and runtime fallbacks into it. Copy/adapt a component into the new tree only when
needed, with its provenance, dependency review, and validation recorded. Keep legacy edits
limited to documented relocation necessities. Verify its build from its own directory.

Compare through isolated runs or replay. Never run both control paths against the same live
device. M1 validates new ownership boundaries; subsequent milestones establish feature
coverage and documented differences. M5 gates production cutover and legacy-tree removal,
not the initial choice of root workspace. Git preserves the original reference for rollback.


<a id="design-d1--il-agnostic-host-accepted-direction"></a>
### D1 — IL-Agnostic Host (Accepted Direction)

The Rust host does not know IL. Its job is to relay communication between appliances and the
LG cloud reliably: device transport, session lifecycle, ThinQ1/ThinQ2 protocol handling, TLS,
provisioning, firmware, SNI passthrough, bridge connections, and hosting the Rhai scripts that
sit on that path.

Everything sent toward `ildevice` consumers is produced by Rhai: IL descriptors and values,
command validation and rejects, availability rules (A-2/R-4), and the `il-mqtt` topic/payload
mapping. Rhai drivers or a shared Rhai library in rusthinq-scripts own this. The host has no IL
types, schemas, vectors, or validators, and no dependency on the `ildevice` repository.

Script outputs are opaque payloads to the host. It routes them to their destination (device,
external MQTT) and enforces only device identity, script generation, ordering, and bounds.
Inbound consumer commands are delivered to the owning device's script, which accepts or rejects
them. IL conformance is tested in rusthinq-scripts beside the drivers, not in this repository.
An IL specification change therefore requires no host change unless it needs a new generic
host primitive. This applies to Rhai as well: the host bundles no helper library, has no IL
configuration, and delivers commands to `on_set_property` unvalidated. IL drivers import
rusthinq-scripts' `il_common` module, which owns the descriptor topic and validation.

### Runtime and Ownership

| ID | Current approach / problem | Decision for 0.2 | Validation |
| --- | --- | --- | --- |

<a id="design-script-output-contracts"></a>
### Script Output Contracts


<a id="design-s1--opaque-driver-sink"></a>
#### S1 — Opaque Driver Sink

Current factories receive `Arc<dyn MqttConnection>`. `ctx.publish_property` both updates the
host's `IlState` and publishes to MQTT; `publish_il` stores a descriptor and builds MQTT
bindings. The host therefore interprets IL, and transport carries the semantic state path.

Replace this on migrated paths with a device-scoped output sink that carries opaque script
outputs: device sends, timer changes, and messages for external consumers. Under D1 the host
does not parse, store, or validate IL descriptors or values. It assigns identity and generation,
keeps order, and bounds volume; a superseded script generation cannot emit. Define delivery
and failure semantics in M0. `IlState`, `publish_il`, and host-side command validation are not
carried into 0.2; their behavior moves to Rhai.

Consumer commands reach the owning device's script, serialized per device. The script
validates them against its own descriptor/state and produces the reject or the device send.
Semantic state, including what must be re-published after reconnect, lives in the script.

M1 must run one real script through this path and assert its outputs, script-side command
handling, and stale-generation rejection. Full script-service migration remains M2.


<a id="design-s2--cross-repository-compatibility"></a>
#### S2 — Cross-Repository Compatibility

The local reference repositories are `../rusthinq-scripts` and `../ildevice` relative to the
rusthinq checkout. These are external contracts, not files guaranteed to exist for every build.
Record the tested rusthinq-scripts revision and fixture provenance; CI must obtain pinned inputs
or use explicitly sourced fixtures rather than rely on sibling directories.

The 0.2 project is independent of `ildevice` (D1). No 0.2 crate, test, build script, or CI job
reads `../ildevice` or depends on its schemas or vectors. IL conformance (`il.md`,
`il-messages.md`, schemas, vectors, and the `il-mqtt.md` mapping) is verified in
rusthinq-scripts against its recorded `ildevice` revision. The legacy 0.1 sibling-path test is
not a precedent.

The host's contract with rusthinq-scripts is the Rhai API. Preserve the selected script's
observable behavior in M1 where the API remains, and coordinate required driver updates across
repositories, including moving host IL helpers into Rhai. Full driver inventory and
compatibility validation occur in M3, not as a prerequisite for M1.


<a id="design-s3--raw-mqtt-publication"></a>
#### S3 — Raw MQTT Publication

Under D1, script publication to external MQTT is the normal path for IL output, not only an
escape hatch for non-IL custom drivers. Define one publication primitive with device-scoped
topic rules, explicit retained policy, and explicit behavior when MQTT is disabled. Decided in
M3: native `ctx.publish_raw(topic, payload, retain)` is that single primitive. With external
MQTT disabled it reaches the local application/event sink and succeeds without claiming
broker delivery; during a broker outage non-retained output is dropped and counted.


<a id="design-panic-isolation--p1-preserve"></a>
### Panic Isolation — P1 (Preserve)

`panic_guard::guard` catches unwinds around per-device callbacks. Shared dispatch loops and
the release profile rely on this containment. Preserve the guarantee that a handler/script
panic does not terminate shared processing or disrupt unrelated devices.

Keep guards at migrated shared callback/script invocation boundaries unless an isolated task
boundary demonstrably provides the same guarantee. Merely spawning a task is insufficient:
its failure must be observed, outstanding callers resolved, and affected resources cleaned
up without terminating the registry or unrelated sessions. Record the choice for the M1 path.
Do not switch the release profile to panic=abort.

Containment is not recovery. Do not add application panic retries, automatic actor/script
restarts, or restart supervisors. Fix panic causes. Cancellation/join ownership in R2/R3 is
resource lifecycle management only. Existing protocol-directed reconnect after network failure
is distinct from retrying a panicked operation and must remain explicitly scoped as such.

Verification: induce a handler panic and prove another device and shared dispatch still work;
prove the failed invocation is not replayed, no replacement task is automatically spawned,
and waiting callers are not left hanging. Record the affected-device state after containment
rather than assuming partially mutated state is safe to resume.


<a id="design-thinq2-server-boundary--t1"></a>
### ThinQ2 Server Boundary — T1

The embedded `mqtt_broker.rs` is owned by the runtime/server layer, independent of the
external MQTT adapter. Keep existing broker machinery unless a demonstrated contract requires
changes. ThinQ2 device/session interpretation feeds the protocol core. Provisioning, firmware,
and SNI passthrough are separate I/O services with explicit dependencies on application state
where needed. Do not bury their migration in one protocol checkbox; use M2b's separate gates.

At M1, review whether the core actually owns protocol decisions, whether the runtime can
make progress under backpressure, and whether the host stayed IL-agnostic (D1) with GUI

<a id="contracts-structure"></a>
### Structure

| Layer | Responsibility | I/O | Depends on |
| --- | --- | --- | --- |
| L1 Protocol | Per-connection protocol decisions and `lg_compat` | None | — |
| L2 Lifecycle | Device-lifecycle decisions | None | — |
| L3 Server | Connection path: devices reach rusthinq and stay connected | Sockets, TLS | L1 |
| L4 Bridge | LG connections and remote device/firmware passthrough | Sockets, TLS | L3 |
| L5 Scripts | Rhai host for drivers; opaque primitives only. IL lives in the scripts (rusthinq-scripts), not the host (D1) | Script files | L3 |
| L6 App | Runtime: runs L2, executes its effects, persistence, `AppHandle` | Storage files | L2–L5 |
| L7 Adapters | External MQTT, GUI/management API, CLI/MCP | Network | L6 (`AppHandle`), stateless L1 codecs |
| Daemon | Composition root: configuration, construction, wiring, shutdown order | Config file | all |

L6 and the daemon are split so that dependencies stay acyclic: L7 accesses lower state only through `api::AppHandle`, while
the daemon constructs every layer including L7. The daemon holds no logic; it only
constructs and wires.

Rules:

- Dependencies point downward only. A lower layer never calls an upper one; upper layers use the
  lower layer's handle (commands in, events out).
- Decisions live in L1 and L2, which are pure. Other parts execute decisions and report results
  back as inputs.
- Only L5 Rhai code knows IL (D1).
- Each layer runs and is tested without the layers above it. Nothing depends on `legacy/`.
- The layer count is not fixed. Split a layer when it takes on an unrelated responsibility.
  Layers are module boundaries first; make one a crate when its dependency rule needs enforcing
  or it is optional (bridge, scripting, GUI remain cargo features of the daemon).
- `runtime::Handle` is for composition/embedding, not the L7 interface. L7 receives
  application results and projected events, never L3 receipts or L4/L5 actor handles.


<a id="contracts-l1--protocol"></a>
### L1 — Protocol

A pure model, one per connection. It takes input plus `now` and returns outputs plus the next
deadline. No clocks, sockets, files, configuration loading, or Tokio.

- ThinQ1 framing, parsing, and encoding; ThinQ2 message interpretation; ACK generation.
- `input(bytes | message, now) -> { frames to send, protocol events, next deadline }`.
- Invalid input yields an explicit error outcome; buffers are bounded.
- Exactly one ACK owner per frame. AABB local auto-ACK versus LG-relayed ACK is chosen by
  `lg_compat` from session input (bridge active or not), never by scripts.
- Unknown fields are recorded, not given invented meaning.

`lg_compat`: pure policy used by L1 and by L3's listeners. Each entry has a stable LG-* ID,
observed model/firmware, evidence, and a fixture. Unknown matches use the documented baseline;
never apply every workaround at once.

Verification: capture/fixture replay tests with no network, files, or real waits.
Implemented protocol contracts and bridge-generation handoff requirements are
recorded in [L1 implementation](0.2-protocol-implementation.md#l1-implementation); runtime enforcement
is pending L3/L4.


<a id="contracts-l2--lifecycle"></a>
### L2 — Lifecycle

A pure model, one per process and run by L6, with the same input/`now`/deadline shape as L1. It knows
nothing about protocol frames.

- Known devices, incarnation, current session generation, online state, offline grace.
- Inputs: session up/down, forget request, step results (closed, deregistered, persisted, failed),
  loaded ledger, `now`.
- Outputs: device-list changes, online/offline events, and effects (close session, deregister
  from LG, persist ledger, persist removal).
- A newer session generation supersedes the old one. Down events from an older generation do
  not change state.
- Grace delays only the offline report. It never keeps a closed session usable.
- Forget is a sequence of steps: quiesce → close → deregister (only when the bridge is active)
  → persist removal → removed. Each step's failure is a distinct reported outcome; the device
  stays quiesced, never reported removed. The same identity may register again later with a
  new incarnation.

Verification: event-sequence tests with no network, files, or real waits.


<a id="contracts-l3--server"></a>
### L3 — Server

Only the connection path. A device reaches rusthinq, completes its handshake, and keeps a live
session.

- 443 front door: ClientHello SNI peek. Served names go to the local TLS acceptor; other names
  go to a passthrough hook that L4 may register. Without L4 they are refused.
- TLS listeners with per-SNI certificates and the RTK_RTL8711am TLS1.0/CBC listener policy.
- ThinQ2 provisioning routes (`/route`, certificates) and the embedded device MQTT broker.
- One session task per connection, running an L1 session model.

`ServerHandle`:

| Direction | Item |
| --- | --- |
| Out | Session up / down (device id, generation); device data (device id, generation, opaque payload); cloud-bound data for L4 |
| In | `send(device, payload)` → rejected/busy, queued, sent, or device-acknowledged where the protocol supports it |
| In | `close(device)` |

- A new connection for the same device replaces the old session; the old one can no longer
  emit events.
- Per-device queues are bounded. A full queue returns busy and never blocks a shared loop; a
  stalled peer fails its own session.
- A disconnect after a partial write is an unknown outcome and is never retried automatically.
- Shutdown stops accepting, closes sessions, and joins owned tasks; its control path does not
  depend on free capacity in data queues.
- No persistence, device list, or grace. CA material and listener configuration are passed in
  at construction.

Verification: loopback/capture-replay integration tests and a standalone run in which devices
connect, get ACKed, and stay connected with nothing above L3.
The ThinQ1 runtime and TLS/SNI front door are recorded in [L3 implementation](0.2-protocol-implementation.md#l3-implementation);
CA/CSR and HTTPS provisioning services are recorded in [provisioning implementation](0.2-protocol-implementation.md#l3-provisioning);
The local ThinQ2 embedded MQTT subset and deploy/timesync execution are recorded in
[MQTT implementation](0.2-protocol-implementation.md#l3-mqtt); broader MQTT compatibility and bridge fencing remain pending.


<a id="contracts-l4--bridge"></a>
### L4 — Bridge

Every connection to servers rusthinq does not impersonate:

- Per-device LG cloud connections, LG registration lifecycle, and outbound reconnect policy.
- The device↔LG relay, using L3's cloud-bound data and `send`.
- SNI passthrough and firmware/SOTA host learning (which hosts must be spliced to the real
  server), registered as L3's passthrough hook.

The bounded firmware/SOTA host evidence core is implemented in
[L4 foundation](0.2-runtime-implementation.md#l4-implementation). Its bounded TLS passthrough hook is verified against fake endpoints; cloud
real cloud registration and application wiring are still pending. A bounded
registration ownership/management handle now fences ThinQ1 downlink dispatch and
connects validated command evidence to firmware learning.

`BridgeHandle` exposes per-device enable/disable, deregistration, and status events.

- Enabling keeps an existing LG registration (as 0.1 does since upstream PR #107).
- Outbound reconnect is a transport policy with backoff. It is not a panic retry, and an inbound
  device replacement never triggers a dial.
- The relay does not interpret payloads beyond what L1 needs to decide ACK ownership.
- Bridge disabled or LG unreachable leaves L3 and local operation unaffected.

Verification: relay and passthrough tests against fake endpoints; real-LG validation is
recorded per device.


<a id="contracts-l5--scripts"></a>
### L5 — Scripts

The [bounded Rhai host foundation](0.2-runtime-implementation.md#l5-implementation) now implements opaque
ordered outputs, execution limits, fault isolation and explicit generation reload.
A bounded blocking worker now serializes calls/reloads and joins on shutdown.
L6 now owns device/session-bound workers and joins them on normal runtime shutdown.
Explicit live attachment, Response/Ready/Data callbacks (UTF-8 or hex) and fenced ordered
output dispatch exist. Automatic model selection, lifecycle/timer callbacks,
production MQTT adapters and real-driver acceptance remain pending.

Live reload now accepts precompiled replacements through bounded L6 commands;
captured session/script generation fence admission and result dispatch. Callback
configuration is retained and faults recover only through explicit reload.

Mixed runtime send selects the codec from a captured session in one shared registry;
device MQTT downlinks remain non-retained.

An opt-in bounded ctx/text callback subset provides device metadata, per-generation
state and opaque publish/send/send_json. Target ID checks run at L6 attachment/reload.
Legacy IL/property/raw MQTT APIs and complete driver compatibility remain pending.

Explicit caller-supplied bounded module bundles now support imports without filesystem
lookup. Prepared entry imports survive callback calls without repeating initialization
or resetting mutable scope; real-model/module API acceptance remains incomplete.

- One worker per device, one invocation at a time, run off transport loops, with Rhai
  operation/memory limits. Native host functions are bounded and nonblocking.
- Inputs: device data, online/offline (from the lifecycle model, via L6), consumer
  commands, timers.
- Outputs are opaque: device send through `ServerHandle`, publication to a consumer sink, timer
  changes. The host checks only identity, generation, and bounds, never IL content (D1).
- Reload compiles outside the worker. Compile failure keeps the old generation; success cancels
  old timers and starts fresh state. Outputs from a replaced generation are discarded.
- Script error or panic is contained: timers are cancelled, a health event is published, and
  the generation stays faulted until an explicit reload. No automatic retry or restart.
- The consumer sink is implemented above L5. With no sink attached, publication returns an
  explicit disabled error.

Verification: real-driver runs against captured input. IL conformance itself is tested in
rusthinq-scripts.


<a id="contracts-l6--app"></a>
### L6 — App

- Runs the L2 lifecycle model: feeds it L3 session events, step results, and `now`; arms its
  deadlines; forwards online/offline to L5.
- Executes its effects: `close` on L3, deregistration on L4, ledger writes through a small
  storage module. Each result goes back to the model as an input.
- Loads the ledger at startup.
- `AppHandle` for L7: device list and change events, forget, script reload, consumer commands
  routed to L5, and the L5 consumer sink.
- Thin: executes L2 lifecycle, L4 connection/account and L5 execution decisions;
  it does not introduce another lifecycle, retry, reload, preparation or timer policy.
  L6 owns effect tasks, persistence and cross-layer scope authentication. L5 Scheduler,
  Preparation and driver modules own invocation ordering, resource admission,
  timer decisions and script filesystem preparation.

Verification: integration tests over fake L3/L4/L5 handles and a temporary storage directory.


<a id="contracts-l7--adapters"></a>
### L7 — Adapters

- External MQTT: broker connection, delivery, retained cleanup, and routing inbound consumer
  commands to L5. Optional; nothing below is affected when it is disabled or the broker is down.
- GUI/management API: device list and status from `AppHandle`; works without an external
  broker. Property-value screens are out of scope.
- CLI/MCP: online paths use the management API; offline tools reuse L1 codecs.


<a id="contracts-daemon"></a>
### Daemon

- Loads configuration and constructs L3, L6, and L4/L5/L7 when enabled.
- Wires handles between layers. No other logic.
- Owns shutdown order: stop admission, then adapters, app, scripts, bridge, server.


<a id="contracts-cross-cutting"></a>
### Cross-Cutting

- Panic isolation (design P1): guard per-device handler and script boundaries so one device
  cannot stop shared processing or other devices. No supervisors, panic retries, or
  `panic=abort`.
- Every task has an owner that cancels and joins it at shutdown or device removal.
- Exact queue sizes, method names, and storage encoding are implementation details.


<a id="contracts-intentional-changes-from-01"></a>
### Intentional Changes from 0.1

- ACK policy moves from scripts (`ctx`) to `lg_compat`.
- IL handling moves from the host to Rhai (D1): `IlState`, `publish_il`, host-side command
  validation, and host-applied availability are removed.
- A script fault stops that script until reload instead of continuing with possibly corrupt state.
- Forget closes live sessions and reports each step's outcome instead of unconditional success.
- With no consumer sink, publication returns an explicit error. An application/event
  sink can observe output without external MQTT; that success is not broker delivery.
- SNI passthrough is available only with the bridge; without L4, unserved names are refused.


<a id="contracts-open-items"></a>
### Open Items

- Script fault and IL availability: the host cannot publish IL unavailable for a faulted
  script. Decide whether consumers rely on the health event or Rhai provides a fallback.
- Whether firmware passthrough is ever needed without the bridge. Firmware URLs arrive in
  cloud→device messages, so this document assumes not.
- Crate names and which layers start as crates rather than modules.


<a id="contracts-mapping-from-the-previous-draft"></a>
### Mapping from the Previous Draft

<a id="contracts-retained-publication-deletion-requirement"></a>
### Retained publication deletion requirement

Every retained MQTT publication must have an explicit removal route before it is
enabled: a recorded owner and exact topic, individual deletion, owner-wide cleanup
for device/adapter removal, and complete namespace cleanup. MQTT remote deletion
uses an empty-payload PUBLISH with RETAIN=1. Local map deletion, unsubscribe,
connection closure, and device offline do not prove remote retained deletion.
Removal work must survive remote failure and restart until delivery is confirmed;
persistent adapters must store the cleanup inventory/pending tombstones durably.
Device retained ownership includes lifecycle incarnation. Cleanup begins only from
the durable `Removed` action; offline state alone never deletes retained values.
A QoS0 socket write alone is not broker confirmation. Reconnect, mapping changes,
and disable/remove flows must drain or recover cleanup work, not silently abandon it.

`rusthinq-server::retained::Store` now provides bounded owner/topic inventory,
empty-payload removal, individual/owner/all cleanup manifests, and owner-scoped
replay. Tombstones encode empty RETAIN=1 packets. It is an in-memory foundation,
not a remote publisher or durable cleanup queue. Owned retained network publication now goes through the durable inventory and
matching PUBACK path in L6; daemon lifecycle orchestration remains pending. Will retain metadata likewise remains an observation
until this publication/deletion path exists.

<a id="architecture-review-invocation-and-failure-review-h2h3h4h5"></a>
#### Invocation and failure review (H2/H3/H4/H5)

L5 Scheduler owns admission until ordered completion release, including buffered
results. Wrong-device, duplicate and late completion cannot replace pending data.
Different devices release independently. L5 owns timer replacement, cancellation,
per-device limits and due ordering; L6 only waits, supplies current scope and
executes invocations. Due callbacks are consumed once; overload is explicit and
never an automatic replay. L5 Preparation owns two-job admission, same-attempt
non-retry and bounded pre-attachment data. Stale completion cannot take a successor's
buffer. Replaced buffers release their old byte budget before accepting new data.

L6 still owns JoinSets, scope projections and lifetime fences because it composes
lifecycle and worker effects. Those checks authenticate inputs/results; they do not
select a second offline, retry, reload or timer policy. Preparation catches an
unwind at its owned job boundary and reports compile failure without retrying a
panicked job. Initial failed preparation does not retry on every frame; a new
session/model attempt or explicit attachment is required. File watch/reload of an
existing worker is an explicit configured trigger. Broader GUI recovery controls
remain M3 work.

error handling. Exact reproduction of quirks is not required. Every retained MQTT publication

<a id="plan-goals-and-scope"></a>
### Goals and Scope

rusthinq remains a standalone daemon. Separate protocol/lifecycle decisions from I/O using

External MQTT becomes an optional integration. Device-facing ThinQ2 MQTT remains necessary
transport. GUI and management API must work without an external broker; CLI and MCP reuse
application services and codecs. Consolidate tools after their actual usage is reviewed.


<a id="plan-implementation-strategy"></a>
### Implementation Strategy

Build the 0.2 daemon internals afresh rather than progressively reshaping the existing daemon
in place. The current implementation carries architectural choices inherited from rethink
and its Rust port. Treat it as a protocol reference and behavioral comparison baseline, not
as the architecture that the new implementation must preserve.

Write new application ownership, session lifecycle, script-host sink, and adapter wiring.
Selectively reuse verified codecs, framing, TLS compatibility handling, useful GUI assets,
drivers, captures, and tests after reviewing their dependencies. Reuse device knowledge and
necessary external contracts without importing the old callback, global-state, or MQTT-based
ownership structure.

Begin the implementation phase by relocating the complete tracked 0.1 project tree into
`legacy/0.1/`. This includes its source, manifests, assets, tests, configuration examples,
build/deployment scripts, documentation, and project-specific hidden configuration. Keep Git
metadata at the repository root and retain the 0.2 planning documents under root `docs/`.
Do not move local secrets, ignored build output, or other untracked personal files as part of
the tracked-source relocation.

The repository root then becomes the new 0.2 project from its first implementation commit.
Keep the legacy Cargo workspace independent and excluded from the new workspace and default
CI. Record the original 0.1 revision and explicit legacy build/run commands. Adjust only paths
needed to run the relocated reference, documenting those adjustments separately.

Bring code from `legacy/0.1/` into the new tree only when a slice needs it, after reviewing its
responsibility and dependencies. No new crate may depend on legacy by path, include its source,
or call a legacy fallback. Record the source revision/path and verification for reused code.
Compare implementations through capture replay or isolated runs, never simultaneous control
of the same live device. Production readiness remains gated by M5 even though the repository
root targets 0.2 from the start. Remove the legacy tree after the release gates pass; the
original revision remains available in Git. No permanent dual implementation is intended.


<a id="plan-architecture-overview"></a>
### Architecture Overview

```text
Device transport <-> Session runtime <-> Protocol/lifecycle core
                           |
                     Rhai driver host  <- IL lives here (D1)
                           |
                Opaque driver output sink
                    /                 \
          External MQTT        Application lifecycle state
                                       |
                           Shared application interface
                              /                 \
                          GUI/API          CLI/MCP via API
```

The host is IL-agnostic (design D1): Rust relays communication between appliances and the LG
cloud reliably and hosts the scripts on that path. The protocol core produces protocol events
and outbound messages, not semantic appliance properties. Rhai drivers interpret device data
and produce everything sent toward ildevice consumers: descriptors, values, events, command
rejects, and their MQTT mapping. The host routes these as opaque outputs and owns only device
identity, sessions, lifecycle, and script health, which the GUI consumes.

The application also owns the device registry, management operations, and persistence
orchestration. Session runtimes own connections and core instances. The embedded device MQTT
broker is runtime-owned; provisioning, firmware, and SNI passthrough remain explicit server
services. Detailed ownership and error contracts belong in the design record.


<a id="plan-first-working-slice"></a>

(no ThinQ1 appliance exists, so ThinQ1 is verified at the protocol level; see the M1 gate revision):

1. Accept a connection and process protocol messages in the new core/runtime boundary.
2. Feed status to one selected driver from rusthinq-scripts.
3. Emit its IL descriptor, values, and events from Rhai through the opaque sink to the MQTT adapter.
4. Serve the existing device-list projection to the GUI.
5. Deliver one supported command to the script and verify its accept/reject and result semantics.

The GUI part needs only the existing devlist projection. Verify semantic values in the
script outputs and MQTT output; a new GUI property editor is not required.

remain on the reference implementation in a separate deployment; the new daemon does not
