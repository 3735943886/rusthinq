# L5 — Bounded Rhai host foundation

`rusthinq-scripting` is a new workspace crate with no legacy dependency, MQTT
factory, IL types, network transport or filesystem module resolver. `Compiled`
creates one bounded Rhai engine/AST outside the running generation. `Host` owns
its mutable scope and accepts one invocation at a time through an exclusive
mutable reference. The worker API now serializes calls off transport loops;
L6 now has a bounded device/session owner and runtime lifecycle/shutdown attachment;
explicit live attachment, transport callbacks and fenced output dispatch now exist.
Automatic model selection and production MQTT adapters remain open.

Native `publish(string)` and `send(string)` append opaque ordered outputs. The
host does not parse or validate their contents. Publication with no consumer
enabled returns an explicit script error. Consumer enablement does not prove
delivery: an upper-layer sink must route outputs and report its result. No retained
MQTT packet is emitted here; future retained adapters must use durable ownership
inventory and acknowledged deletion routes before publishing values.

Defaults bound source to 64 KiB, strings/inputs to 16 KiB, each evaluation to
100,000 operations, arrays to 1,024 entries, maps to 256 entries and calls to 32
levels. An invocation emits at most 64 outputs/64 KiB, including initialization.
Limits are provisional until real-driver acceptance. Initialization and callback
each have the engine operation budget. Print/debug callbacks perform no I/O;
imports have an empty static resolver and cannot read arbitrary files.

Outputs retain their emitted prefix when execution fails or a native callback
panics. No replay or restart occurs. The host stays faulted until explicit reload;
unrelated hosts continue. A caller must fence the returned script generation and
device/session context before effects. Successfully compiled reload increments
generation and creates fresh scope; compile failure leaves the old host untouched.
Old-generation invocations are rejected. Timer APIs are not present yet.

Five tests cover opaque non-JSON output order and mutable scope, bounded output
prefix/fault/reload behavior, compile failure, disabled consumer, operation/input
limits, forbidden filesystem imports and injected native panic isolation.
This does not complete the L5 contract or M1: production sink integration, timers, existing
ctx compatibility, module libraries, real model fixture replay, L6 output dispatch,
MQTT adapter and GUI still require implementation.

## Serialized worker

`worker::Worker` owns a Tokio blocking task and one host. Its handle admits calls
without waiting; overload returns `Busy`. Default capacity is 16 and includes
queued/current requests and completed results whose receipts have not been
consumed or dropped. Dropping a queued receipt does not release its capacity until
that request finishes. Input/function bounds reject requests before script execution.

Reload accepts an already compiled replacement and an expected generation. FIFO
queue order defines the replacement boundary; stale calls/reloads are rejected.
Compilation failure leaves the worker untouched. A watch snapshot reports running,
faulted or stopped status; script/native failures preserve emitted outputs and require
explicit reload. Results confirm execution only; L6 must fence device/session and
script generation before dispatching outputs.

`request_stop` rejects further admission. `shutdown` finishes the current call,
cancels unstarted calls/reloads with `Stopped`, and joins without waiting for held
receipts. Dropping the owner only signals stop; callers must await shutdown to
confirm completion. Each worker uses a blocking task. L6 enforces a worker budget per script owner;
a daemon-wide admission policy remains open. Retired workers keep their slots until joined.

Six worker tests cover ordered reload/stale rejection, outstanding-result bounds,
independent progress after faults, input rejection, deterministic current-call
completion with queued cancellation, and native panic execution off the async thread.

## L6 device/session ownership

`rusthinq-app::scripts::Owner` binds each worker to device incarnation, transport
generation and a unique attachment token. Completion fields are private; acceptance
also checks the current script generation and L2 snapshot. The caller must accept
and dispatch in one actor turn before any await. Faulted invocations can deliver
their emitted prefix if all fences pass. Four tests cover reconnect, removal,
reload, same-session reattachment and retirement capacity.

`Runtime::with_scripts` takes ownership, invalidates workers on lifecycle changes
and joins them during normal shutdown. `Handle::attach_script` accepts compiled
generations bound to the current incarnation/session, using a one-entry command
mailbox. Model selection remains explicit. Response/Ready callbacks receive their
JSON value serialized as a string. Optional Data callbacks select UTF-8 or lowercase
hex encoding; UTF-8 rejects invalid input before execution and hex preserves every
byte without IL interpretation. Callback names/encoding are configured per attachment.
An opt-in ctx/text callback subset now exists below; timer/start/online/offline
callbacks and complete legacy ctx compatibility remain open.

`Handle::reload_script` uses the same one-entry command mailbox as attachment.
The caller compiles the replacement before admission and supplies captured session
and expected script generation. Stale sessions/generations are rejected. Reload is
serialized by the existing worker; success returns the new generation and fresh
scope while preserving callback names/encoding. Publication enablement is set from
the actual sink. Initialization runs on the next invocation, so a successful compile
does not certify runtime behavior. Pending old-generation completions are fenced
before output dispatch; already delivered outputs are not replayed or retracted.

The runtime waits for the bounded current invocation/reload and revalidates the L3
snapshot and stop state before replying. This may delay other L6 work; transport
tasks remain independent. Losing/cancelling a reply does not roll back an accepted
reload and must not cause automatic retry. A shutdown closes/cancels queued commands
explicitly. Four live tests cover compile-failure scope preservation, fresh scope
and generation rejection, explicit fault recovery without prefix replay, old-session
protection across reconnect, and shared mailbox overload/shutdown cancellation.

Completion tasks and buffered out-of-order results share the runtime event-capacity
limit. Device callbacks dispatch in invocation order; separate devices do not wait
for each other's completion. Results reconcile the latest L3 snapshot before L2
fencing. Stop drops undispatched outputs explicitly and joins workers/result tasks
and accepted transport receipts. Retired workers are joined during live attachment
before successor admission; this can delay the actor while a bounded call finishes.

`send` uses the configured ThinQ1 or ThinQ2 transport handle with the captured
session, then reports `ScriptDelivery` when its receipt resolves. `Sent` means frame
write completion, not appliance ACK. `Runtime::new_mixed` validates a shared L3
registry and chooses the codec from the captured session's protocol. `publish`
invokes an explicitly attached bounded/nonblocking
`PublishSink`; runtime sets native publication enablement from actual sink presence.
Sink admission is not MQTT delivery acknowledgement. A sink error stops remaining
outputs; no replay occurs. Asynchronous sink implementations must fence context
again at their effect boundary. Retained adapters must durably inventory ownership
and provide acknowledged removal routes before publishing; no retained packet is
introduced by this implementation.

Five real-frame ThinQ1 runtime tests cover opaque publication/exact JSON send,
receipt and shutdown, disabled consumer faults, sink overload/fault-prefix handling,
stale attachment/successor reaping and ordered callback bursts. These scripts are
synthetic, and do not satisfy the real-driver M1 gate.

Four additional MQTT/mixed tests cover binary hex input, same-TCP redeploy and
successor reaping, both outbound codecs, registry identity rejection, non-retained
MQTT script downlinks and UTF-8 rejection without changing script scope. The mixed
TLS supervisor and plain mixed example use this routing; TLS service builders can
attach the script owner/sink explicitly. Existing ctx-based real drivers still need
compatible APIs/modules and acceptance fixtures.

## Bounded context subset

`Compiled::with_context` opts into `(ctx, text)` callbacks. Ordinary compiled hosts
keep their single-text signature. Context metadata supplies `id()`/`model_id()`;
model identity remains caller-selected, not inferred or appliance-verified. L6 owner
attachment/reload rejects context device IDs that differ from the target device.

`state_get`/`state_set`/`state_has`/`state_remove` retain per-generation state.
Defaults allow 64 keys and 64 KiB of logical key/value cost, including a 16-byte
charge per value; this is not an exact heap-memory bound. Values support unit,
booleans, integers, floats, strings, arrays and maps. Traversal rejects depth over
16, more than 4,096 nodes per value, shared references that reach the native call,
ctx/function-pointer/custom values and capacity overflow before mutation. Rhai
may flatten a shared argument into a copied value; tests verify subsequent source
mutation cannot alter stored state. Replacement/removal reclaim their accounted
budget and getters return independent values. Each compiled context is isolated;
reload starts a fresh one.

`ctx.publish`/`ctx.send`/`ctx.send_json` append the same bounded opaque string outputs
as plain functions. `send_json` neither parses JSON nor wraps appliance envelopes;
L3 validates/framing remains unchanged. Consumer absence returns the same script
error. No IL types/descriptor validation, property/event topic construction, raw
MQTT/retain, timers, JSON-library helpers or module filesystem resolver are added.
Existing `publish_property`/`publish_il`/`publish_raw` drivers still need Rhai-side
adaptation and supported sink APIs; this is not full legacy compatibility.

Five context tests cover nested state, per-host isolation/reload, key/value budgets,
replacement/removal/getter independence, reference/custom-value rejection, shared
argument copy behavior and consumer/output limits. One real-frame L6 test checks
ctx/text callback state, metadata/target identity, exact JSON send and reload.
The model/callback examples remain synthetic; real-model M1 acceptance stays open.

## Explicit module bundles

`Compiled::with_modules` prepares one caller-supplied ordered bundle before runtime
admission. At most 16 modules are accepted; names are 1–64 ASCII letters/digits,
underscore or hyphen, with no duplicates or filesystem paths. Entry source plus
all module names/sources share the configured source-byte budget. Dependencies must
precede importers. No directory scans, file resolver or implicit library lookup occurs.

Each module is compiled/evaluated under the existing engine limits. Initializer
publish/send fails before buffering outputs; module preparation errors/panics cannot
replace a running generation. Callbacks may invoke module helpers that call the
same bounded native functions. Top-level entry imports are evaluated for each call
using an imports-only AST; ordinary entry initialization still runs once and mutable
scope survives calls. This uses Rhai's `internals` AST API, pinned to tested version
1.26.1 to avoid silently changing that contract. Limits apply per module initialization,
not one aggregate operation budget for the whole bundle.

Six module tests cover dependency order/ctx output, source/count/name limits,
forbidden initialization output/filesystem lookup, operation limits, failed
preparation/explicit replacement and preservation of initialization/mutable scope.
The real-frame L6 ctx test also imports a prepared output helper across reload.

One test uses an unchanged `aabb_common.rhai` fixture from rusthinq-scripts revision
`54292921c6edc72ea6ec901b1137845bff14e6ae` (GPL-2.0); SHA-256:
`fa6431795f3c6ba58234a59c65dcc02740696336fd89bbd9a9b7ee077abf776c`.
Only its pure `bit`/`on_off` helpers are accepted here. Other helper paths still need
framing/numeric APIs and Rhai-side IL/property/event adaptation. This is real helper
evidence, not full real-model/appliance acceptance. Fixture provenance lives beside
the copied source; unrelated script-repository changes remain untouched.
