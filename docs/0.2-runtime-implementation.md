## 0.2 L4 bridge foundation

> Implementation record: progress paragraphs and test totals below belong to their
> recorded checkpoints. For current acceptance use [milestones](0.2-validation.md#milestones);
> for configuration use [runtime](0.2-runtime.md#runtime) and [operations](0.2-operations.md).

The new `rusthinq-bridge` workspace crate begins with firmware/SOTA host evidence
in `firmware::Hosts`. The host-evidence core uses L1, serde_json and the URL parser;
it has no legacy dependency, network access, global state, mutex, logging or wall
clock. Network adapters in the same crate own their transports separately.
Its application/bridge owner supplies monotonic milliseconds and serializes calls.
The decision core is now connected to the L3 passthrough hook by `passthrough::Relay`.


<a id="l4-implementation-firmwaresota-host-evidence"></a>
### Firmware/SOTA host evidence

The reference does not serve firmware images itself. It learns download hosts
and routes TLS to their actual servers so appliance root/certificate checks work.
There are three evidence tiers:

- `Command`: HTTP(S) URL observed anywhere in an actual cloud-to-device JSON
  command; does not expire and cannot be weakened by reactive evidence.
- `Suspected`: URL inferred by a caller from a classified TLS failure; expires
  after 60 seconds. A live route hit renews the lease to ten minutes. Expiration
  removes the entry and allows a later local termination attempt.
- `Local`: proven local TLS/provisioning endpoint, or explicit local policy;
  overrides both remote tiers and prevents later misclassification. Successful
  local provisioning can protect HTTP(S) and `ssl://` endpoint URLs.

The core does not classify arbitrary TLS failures itself. A route hit preserves
the reference's renewal rule; it is not proof that an outbound download succeeded.
Command learning must only receive real bridge downlink traffic. Local data and
unvalidated deploy metadata are not sufficient evidence.


<a id="l4-implementation-bounds-and-intentional-changes"></a>
### Bounds and intentional changes

The caller chooses a nonzero capacity. All tiers share that capacity, including
local protection records. A full registry rejects new names explicitly; local
protection and command evidence are never silently evicted. Local protection can
replace an existing remote record at capacity. Expired suspicions free capacity.
Snapshots remove expired entries without renewing leases.

JSON scans are iterative, with limits of 4096 nodes, depth 64, and 4096 bytes per
string. Learning commits all discovered hosts together; payload/capacity failure
does not commit partial learning. Time advancement and expiry still occur before
the scan. Callers can log/report rejected learning rather than silently truncating.
Backwards or overflowing time is rejected without changing state. DNS names are
normalized to lowercase with a trailing dot removed; malformed names, IP literals,
and URLs with user credentials are ignored/rejected. URL schemes and structure
are parsed using `url`, including IDNA normalization. Nothing is dialed here.

Compared with the reference, storage and scan work are bounded, local/remote
evidence lives in one serialized state map, and expiry actually removes records.
No CDN is hardcoded, and no state is persisted automatically. Non-HTTP remote
URLs remain ignored. Applications must treat protected endpoints as policy and
must not discard the registry during ordinary session replacement.

Reference snapshot: `99c48ccc33bfc602626e0b9151b98de442185c2f`,
`legacy/0.1/crates/rusthinq-cloud/src/thinq2/firmware.rs`. Confidence precedence,
60/600-second leases, arbitrary-field URL scanning, and deploy endpoint protection
are selectively adapted. Dependencies on legacy utility locks/core logging and
Instant-based timing are removed. The reference documents false passthrough
incidents involving `kic-common.lgthinq.com`; model/firmware versions are unrecorded.
No real-device or LG-cloud validation is claimed.

Five pure tests verify nested command URLs and normalization, unsupported URLs,
lease expiry/renewal, evidence precedence, local endpoint protection, independent
registries, atomic admission, depth/node/string limits, capacity reclamation, and
clock/hostname errors. They use injected time and require no network or sleeps.


<a id="l4-implementation-tls-passthrough-transport"></a>
### TLS passthrough transport

`passthrough::Relay` implements L3's `Passthrough` hook. It owns a serialized host
registry, a monotonic epoch, and a shared nonblocking semaphore. Clones share the
same policy and capacity. Evidence updates are explicit methods; no inference is
automatically made from arbitrary TLS errors or device data. Configured L3 local
identities retain priority over passthrough regardless of remote evidence.

Defaults: 256 total host records, 64 simultaneous connections, 10-second outbound
connect timeout (including DNS), and no default transfer deadline. The caller
can opt into an absolute transfer timeout using Some(duration); this is not an
idle timeout. Long healthy firmware downloads are not cut off by a default deadline. Admission at capacity fails immediately without
waiting or dialing. Policy rejection fails before outbound work. A live suspected
routing hit renews its lease even if the subsequent dial fails, preserving the
reference rule. Existing relays are not forcibly closed when evidence changes;
new connections use current evidence.

`HttpsConnector` resolves the selected SNI DNS name and connects to port 443.
Firmware URL path, credentials, and port do not override the SNI transport target.
A caller can supply a `Connector` for another destination policy or a fake endpoint;
its future must not spawn detached work. Normalized names are passed to it.
`copy_bidirectional` uses bounded internal buffers, relays opaque bytes, and
propagates half-close while retaining the reverse direction. L3's PrefixedStream
replays routing bytes exactly once. No TLS termination, byte retry, or firmware
image interpretation occurs on the relay path.

L3 owns and joins the returned future. Dropping it on listener shutdown drops both
sockets and releases the semaphore permit, including during a pending connect.
No relay tasks are spawned by L4. Timeout and I/O failure release capacity and
close both sides. The front door currently reports hook errors as `Failure::Io`;
detailed policy/connect/transfer errors remain in the hook's io::Result and are
not exposed as separate front-door rejection variants.

Six tests cover configuration validation, exact fragmented ClientHello/post-hello
replay, reverse bytes after half-close, unlearned/protected host refusal without
dialing, configured local routing priority, capacity rejection, connect/transfer
timeouts, admission after timeout, and cancellation/join of established and pending
connections. Endpoints are local TCP fakes; the ClientHello is synthetic (the same
wire construction as the L3 TLS tests), not a capture or a complete firmware TLS
handshake. The host evidence tests remain pure and independent of transport.

A harness combines local ThinQ1 TLS with explicitly seeded passthrough:

```sh
cargo run -p rusthinq-bridge --example firmware_tls -- \
  127.0.0.1:8443 local.example ca.crt ca.key https://cdn.example/fw.bin
```

It loads an existing CA, protects local.example, seeds the URL as operator policy,
and exits on Enter. It neither creates CA files nor automatically contacts the CDN;
an inbound allowed SNI connection triggers the dial. Real daemon wiring must learn
from actual cloud downlink commands and confirmed local provisioning.


<a id="l4-implementation-remaining-integration"></a>
### Remaining integration

Cloud command learning and successful local proof must be wired by the daemon.
Real LG registration/reconnect, device-to-cloud relay, application wiring,
structured transport failure events, and real-device/cloud validation remain
pending. Firmware transport has a validated fake-endpoint path; the complete

<a id="l4-implementation-device-registration-ownership-and-thinq1-downlink"></a>
### Device registration ownership and ThinQ1 downlink

`devices::BridgeHandle` now provides a bounded shared registration inventory and
status events. The cloud adapter calls `registered` only after establishing a
registration. Its token includes device ID, lifecycle incarnation and a separate
bridge generation. Re-enabling the same incarnation keeps the registration;
disable does not deregister it. Local bind/replacement never initiates a cloud dial.
A conflicting incarnation requires confirmed deregistration before replacement.
`deregistered` is a confirmation entry point, not an outbound LG request.

Local session bindings retain their generation high-water mark even after unbind.
Late unbind cannot clear a replacement, and an old bind cannot resurrect a closed
target. Downlinks require both the captured registration token and exact captured
local session; callers must never relabel delayed traffic with current tokens.
After confirmed deregistration, a late result cannot remove a newer registration.
The inventory is process-local: its owner must stop cloud tasks before replacing
the entire registry; tokens are not restart-persistent capabilities.

ThinQ1 downlink validates enabled state, binding, current L3 session, bounded JSON
and any provided Header device ID before dispatch. JSON objects retain their
original bytes and unknown fields. A supplied firmware Relay learns only through
this validated cloud-adapter context. Host evidence admission failure is explicit
and prevents dispatch; capacity must be assessed against real appliances. Learning
proves observation of a command, not successful device delivery: later transport
queue/write failure may leave legitimate command evidence in the registry.

Dispatch uses L3's generation-targeted bounded send queue and returns its receipt.
Sent means a complete frame write, not device acknowledgement. Offline, disabled,
stale, malformed and capacity failures are explicit; no buffering, retry, reconnect
or remote dialing is hidden in this API. Cloud authentication remains the calling
adapter's responsibility. This path does not emit retained MQTT publications.

Four tests cover shared bounded state, disable/re-enable registration preservation,
replacement and late-result fencing, offline high-water marks, broadcast loss and
snapshot recovery, real framed local transport byte preservation, invalid/disabled
targets and firmware learning admission. Tests use duplex local transports and
synthetic JSON; no LG cloud or real-device compatibility is claimed.
Actual cloud transport, uplink ACK ownership and provisioning
proof integration remain pending. M1/M2b remain incomplete.

L4 now defines a cancellation-safe `Deregistration` adapter boundary. L6 executes
it during bridge-aware Forget and applies successful confirmation to the captured
registration token before durable device removal. Error/timeout preserves the
registration and quiesced device for explicit retry. The adapter implementation
for actual LG requests is still pending; integration tests use fake cloud adapters.


<a id="l4-implementation-l6-completed-provisioning-local-proof"></a>
### L6 completed-provisioning local proof

Runtime::with_firmware and tls_runtime::Service::with_firmware share the exact
L4 Relay used by the HTTPS front door. Current Ready observations are checked
against the L2 session and current L3 snapshot before the completed deploy payload
protects its HTTP(S)/ssl endpoint URLs. Pending provisioning and HTTP metadata
alone do not establish proof. Host-evidence capacity errors are reported through
L6 Rejected events rather than silently discarded. Relay::snapshot exposes bounded
current diagnostics without renewing suspected leases.

The composed Daemon protects its configured served name at startup and installs
this same relay on the HTTPS front door. Its embedding API exposes a cloned relay
for validated cloud downlink learning; the CLI still has no real LG cloud adapter
and does not learn URLs from arbitrary local commands. An integration test completes
actual MQTT provisioning through the owned L6 runtime, verifies local endpoint
immunity to later cloud URL learning, and admits an unrelated CDN as Command.
All fixtures are synthetic. ThinQ2 bridged ACK ownership/downlink transport and
actual cloud registration/reconnect remain open; generic local send is not treated
as a substitute for a proper bridge-state transition.


<a id="l4-implementation-lg-http-and-oauth-adapter"></a>
### LG HTTP and OAuth adapter

`cloud::Client` now implements gateway discovery, the LG sign-in URL and signed
EMP authorization-code/refresh/profile requests, staged account authentication,
client registration, current-home selection, device listing/registration/removal,
and ThinQ2 certificate OTP retrieval. The request fields and EMP signature are
based on the archived 0.1 adapter; the new crate has no legacy dependency.

The production client permits HTTPS only, verifies certificates and hostnames,
and refuses redirects. Each request has a 15-second total deadline and a 1 MiB
streaming response limit; token strings, device metadata and list sizes are
bounded separately. Gateway endpoints cannot contain credentials, query strings
or fragments. Credentials are marked sensitive in headers and redacted from
`Token` debugging. HTTP/API errors do not include response bodies or request URLs.
Read-only ThinQ GET operations retry transient failures at most three times;
mutating and OAuth token requests are sent once, so ambiguous failures are never
silently replayed. Cancellation drops the owned HTTP future.

Authentication replaces the previous account only after profile, client
registration and home selection all succeed. Device registration preserves
`initDevice=false` and treats LG's typed `0125` already-registered response as
success without destructive re-registration. Removal requires an actual success
response, correcting the reference's best-effort success. `CloudDeregistration`
implements L6's existing confirmed-removal interface with a captured authenticated
account; account replacement cannot redirect an admitted operation.

Local HTTP fixtures verify signed request bytes, form encoding, token parsing
and redaction, account staging, home/device path escaping, registration/removal,
mutation non-replay, response limits, rejected redirects, gateway retry/cache,
and the L6 deregistration interface. Plain HTTP is used only inside these test
fixtures; the public production constructor forbids it.

The daemon now exposes this adapter through its optional `cloud_account` owner,
L6-owned durable country/refresh-token checkpoint and management/GUI account login/logout.
The L4 account actor now renews authentication before expiry with bounded transient backoff,
priority logout cancellation and expired-token rejection. Refresh preserves the
LG client ID. Per-device pairing management, owned ThinQ1/ThinQ2 cloud connections/reconnect
and automatic bridge-state wiring remain to implement.
No live LG-account requests are part of automated verification.


<a id="l4-implementation-pairing-primitives-and-durable-ownership"></a>
#### Pairing primitives and durable ownership

`Client::pair_device` now supports ThinQ1 registration and ThinQ2 regional routing,
server CA retrieval, P-256 key/CSR generation, RSA-encrypted OTP envelopes,
certificate issuance and registration. Existing device aliases are preserved;
registration does not delete an existing device or replay an uncertain mutation.
Native OpenSSL performs cryptography without subprocesses. Endpoint, key, certificate
and topic inputs are bounded. Returned material has redacted Debug output.

Client certificates must match the generated private key and be currently valid.
The returned server CA is kept for server TLS verification; it is not assumed to
issue the client certificate. AWS explicitly supports client certificates issued
by other CAs ([AWS certificate documentation](https://docs.aws.amazon.com/iot/latest/developerguide/x509-client-certs.html)).
Stored material can be structurally restored after expiry so cleanup ownership is
preserved; operational validation still rejects an expired certificate.

L6 `pairing_storage::Store` durably records account/device/incarnation ownership and
a monotonic attempt before a caller starts remote mutations. Completion accepts
only that pending attempt once. Unknown outcomes survive restart and block implicit
retry; removal requires explicit confirmed remote removal for the exact attempt.
Atomic private checkpoint writes use an exclusive lock, file and directory sync;
uncertain write failures block further writes until reopening. Credential-bearing
records are internal material, not management API responses.

Tests decrypt the actual OTP envelopes and verify CSR signatures, exercise ThinQ1
registration, and use a CA-verified fake HTTPS service to issue a ThinQ2 client
certificate from a different CA. Restart, stale attempt, repeated completion,
unconfirmed removal, private file mode, corrupt checkpoint preservation and write
failure tests cover the store. These primitives are not yet wired into daemon
device controls or an owned cloud socket/reconnect loop; that integration remains
the next M2 deliverable. This change introduces no retained MQTT publications.


<a id="l4-implementation-outbound-tls-foundation--2026-10-02"></a>
### Outbound TLS foundation — 2026-10-02

L4 `transport::Connector` prepares verified outbound TLS from validated pairing
material. ThinQ1 uses OS roots or an explicit trust override and requires an RTI
port. ThinQ2 uses the regional server root, client key and certificate chain; the
server root and client certificate issuer may differ. Both verify the endpoint
identity and require TLS 1.2 or newer. Client certificate validity is checked at
preparation and before each connection attempt. Debug output omits credentials.

One timeout covers TCP connection and TLS handshake. The caller owns the future
and returned stream; cancellation closes the socket, with no application retry or
detached connection task. Preparation belongs on a caller-owned blocking task.
Five local TLS tests cover both protocols, distinct certificate authorities,
wrong trust/hostname, invalid and expired identities, timeout and cancellation.
These tests establish socket behavior, not real LG compatibility.

RTI/MQTT session frames, reconnect policy, pairing owner integration and daemon
bridge controls remain pending. No retained MQTT publication is introduced.


<a id="l4-implementation-thinq1-rti-framed-stream--2026-10-02"></a>
### ThinQ1 RTI framed stream — 2026-10-02

`rti::Session` owns a caller-supplied asynchronous stream, including the stream
returned by `transport::Connector::connect`. It reads and writes signed big-endian
length-prefixed JSON objects while preserving original payload bytes. Frame bounds
are checked before receive allocation or outbound JSON parsing. One deadline covers
an entire read or write. EOF between frames is distinct from truncated EOF.

An error or cancelled operation permanently fences the session; the owner must drop
it to close the socket. Partial writes are never retried, and success denotes a
complete frame write rather than an appliance ACK. Invalid outbound input is
rejected before touching the stream and preserves the session. No detached task,
queue, implicit ACK, Start/Stop interpretation or reconnect is introduced.

Five local duplex tests cover fragmented input, byte preservation, lack of implicit
ACKs, malformed/oversized/truncated frames, clean EOF, stalled writes, whole-frame
timeouts, cancellation fencing and recoverable local input rejection. RTI Alive,
Start/Stop/status interpretation, HTTP device-info setup, full-duplex orchestration,
owned reconnect and daemon bridge integration remain pending; these tests do not
establish live LG or appliance compatibility.

<a id="l5-implementation"></a>
## L5 — Bounded Rhai host foundation

> Implementation record: progress paragraphs and test totals below belong to their
> recorded checkpoints. For current acceptance use [milestones](0.2-validation.md#milestones);
> for configuration use [runtime](0.2-runtime.md#runtime) and [operations](0.2-operations.md).

`rusthinq-scripting` is a new workspace crate with no legacy dependency, MQTT
factory, IL types, network transport or filesystem module resolver. `Compiled`
creates one bounded Rhai engine/AST outside the running generation. `Host` owns
its mutable scope and accepts one invocation at a time through an exclusive
mutable reference. The worker API now serializes calls off transport loops;
L6 now has a bounded device/session owner and runtime lifecycle/shutdown attachment;
explicit live attachment, transport callbacks and fenced output dispatch now exist.
Automatic model selection and production MQTT adapters remain open.

Native `publish(string)` and `send(string)` append opaque ordered outputs. The
host does not parse or validate their contents. Publication with no consumer
enabled returns an explicit script error. Consumer enablement does not prove
delivery: an upper-layer sink must route outputs and report its result. No retained
MQTT packet is emitted here; future retained adapters must use durable ownership
inventory and acknowledged deletion routes before publishing values.

Defaults bound source to 64 KiB, strings/inputs to 16 KiB, each evaluation to
100,000 operations, arrays to 1,024 entries, maps to 256 entries and calls to 32
levels. An invocation emits at most 64 outputs/64 KiB, including initialization.
Limits are provisional until real-driver acceptance. Initialization and callback
each have the engine operation budget. Print/debug callbacks perform no I/O;
imports have an empty static resolver and cannot read arbitrary files.

Outputs retain their emitted prefix when execution fails or a native callback
panics. No replay or restart occurs. The host stays faulted until explicit reload;
unrelated hosts continue. A caller must fence the returned script generation and
device/session context before effects. Successfully compiled reload increments
generation and creates fresh scope; compile failure leaves the old host untouched.
Old-generation invocations are rejected. Timer APIs are not present yet.

Five tests cover opaque non-JSON output order and mutable scope, bounded output
prefix/fault/reload behavior, compile failure, disabled consumer, operation/input
limits, forbidden filesystem imports and injected native panic isolation.
This does not complete the L5 contract or M1: production sink integration, timers, existing
ctx compatibility, module libraries, real model fixture replay, L6 output dispatch,
MQTT adapter and GUI still require implementation.


<a id="l5-implementation-serialized-worker"></a>
### Serialized worker

`worker::Worker` owns a Tokio blocking task and one host. Its handle admits calls
without waiting; overload returns `Busy`. Default capacity is 16 and includes
queued/current requests and completed results whose receipts have not been
consumed or dropped. Dropping a queued receipt does not release its capacity until
that request finishes. Input/function bounds reject requests before script execution.

Reload accepts an already compiled replacement and an expected generation. FIFO
queue order defines the replacement boundary; stale calls/reloads are rejected.
Compilation failure leaves the worker untouched. A watch snapshot reports running,
faulted or stopped status; script/native failures preserve emitted outputs and require
explicit reload. Results confirm execution only; L6 must fence device/session and
script generation before dispatching outputs.

`request_stop` rejects further admission. `shutdown` finishes the current call,
cancels unstarted calls/reloads with `Stopped`, and joins without waiting for held
receipts. Dropping the owner only signals stop; callers must await shutdown to
confirm completion. Each worker uses a blocking task. L6 enforces a worker budget per script owner;
a daemon-wide admission policy remains open. Retired workers keep their slots until joined.

Six worker tests cover ordered reload/stale rejection, outstanding-result bounds,
independent progress after faults, input rejection, deterministic current-call
completion with queued cancellation, and native panic execution off the async thread.

<a id="l5-implementation-l6-devicesession-ownership"></a>
### L6 device/session ownership

`rusthinq-app::scripts::Owner` binds each worker to device incarnation, transport
generation and a unique attachment token. Completion fields are private; acceptance
also checks the current script generation and L2 snapshot. The caller must accept
and dispatch in one actor turn before any await. Faulted invocations can deliver
their emitted prefix if all fences pass. Four tests cover reconnect, removal,
reload, same-session reattachment and retirement capacity.

`Runtime::with_scripts` takes ownership, invalidates workers on lifecycle changes
and joins them during normal shutdown. `Handle::attach_script` accepts compiled
generations bound to the current incarnation/session, using a one-entry command
mailbox. Model selection remains explicit. Response/Ready callbacks receive their
JSON value serialized as a string. Optional Data callbacks select UTF-8 or lowercase
hex encoding; UTF-8 rejects invalid input before execution and hex preserves every
byte without IL interpretation. Callback names/encoding are configured per attachment.
An opt-in ctx/text callback subset now exists below; timer/start/online/offline
callbacks and complete legacy ctx compatibility remain open.

`Handle::reload_script` uses the same one-entry command mailbox as attachment.
The caller compiles the replacement before admission and supplies captured session
and expected script generation. Stale sessions/generations are rejected. Reload is
serialized by the existing worker; success returns the new generation and fresh
scope while preserving callback names/encoding. Publication enablement is set from
the actual sink. Initialization runs on the next invocation, so a successful compile
does not certify runtime behavior. Pending old-generation completions are fenced
before output dispatch; already delivered outputs are not replayed or retracted.

The runtime waits for the bounded current invocation/reload and revalidates the L3
snapshot and stop state before replying. This may delay other L6 work; transport
tasks remain independent. Losing/cancelling a reply does not roll back an accepted
reload and must not cause automatic retry. A shutdown closes/cancels queued commands
explicitly. Four live tests cover compile-failure scope preservation, fresh scope
and generation rejection, explicit fault recovery without prefix replay, old-session
protection across reconnect, and shared mailbox overload/shutdown cancellation.

Completion tasks and buffered out-of-order results share the runtime event-capacity
limit. Device callbacks dispatch in invocation order; separate devices do not wait
for each other's completion. Results reconcile the latest L3 snapshot before L2
fencing. Stop drops undispatched outputs explicitly and joins workers/result tasks
and accepted transport receipts. Retired workers are joined during live attachment
before successor admission; this can delay the actor while a bounded call finishes.

`send` uses the configured ThinQ1 or ThinQ2 transport handle with the captured
session, then reports `ScriptDelivery` when its receipt resolves. `Sent` means frame
write completion, not appliance ACK. `Runtime::new_mixed` validates a shared L3
registry and chooses the codec from the captured session's protocol. `publish`
invokes an explicitly attached bounded/nonblocking
`PublishSink`; runtime sets native publication enablement from actual sink presence.
Sink admission is not MQTT delivery acknowledgement. A sink error stops remaining
outputs; no replay occurs. Asynchronous sink implementations must fence context
again at their effect boundary. Retained adapters must durably inventory ownership
and provide acknowledged removal routes before publishing; no retained packet is
introduced by this implementation.

Five real-frame ThinQ1 runtime tests cover opaque publication/exact JSON send,
receipt and shutdown, disabled consumer faults, sink overload/fault-prefix handling,
stale attachment/successor reaping and ordered callback bursts. These scripts are
synthetic, and do not satisfy the real-driver M1 gate.

Four additional MQTT/mixed tests cover binary hex input, same-TCP redeploy and
successor reaping, both outbound codecs, registry identity rejection, non-retained
MQTT script downlinks and UTF-8 rejection without changing script scope. The mixed
TLS supervisor and plain mixed example use this routing; TLS service builders can
attach the script owner/sink explicitly. Existing ctx-based real drivers still need
compatible APIs/modules and acceptance fixtures.


<a id="l5-implementation-bounded-context-subset"></a>
### Bounded context subset

`Compiled::with_context` opts into `(ctx, text)` callbacks. Ordinary compiled hosts
keep their single-text signature. Context metadata supplies `id()`/`model_id()`;
model identity remains caller-selected, not inferred or appliance-verified. L6 owner
attachment/reload rejects context device IDs that differ from the target device.

`state_get`/`state_set`/`state_has`/`state_remove` retain per-generation state.
Defaults allow 64 keys and 64 KiB of logical key/value cost, including a 16-byte
charge per value; this is not an exact heap-memory bound. Values support unit,
booleans, integers, floats, strings, arrays and maps. Traversal rejects depth over
16, more than 4,096 nodes per value, shared references that reach the native call,
ctx/function-pointer/custom values and capacity overflow before mutation. Rhai
may flatten a shared argument into a copied value; tests verify subsequent source
mutation cannot alter stored state. Replacement/removal reclaim their accounted
budget and getters return independent values. Each compiled context is isolated;
reload starts a fresh one.

`ctx.publish`/`ctx.send`/`ctx.send_json` append the same bounded opaque string outputs
as plain functions. `send_json` neither parses JSON nor wraps appliance envelopes;
L3 validates/framing remains unchanged. Consumer absence returns the same script
error. No IL types/descriptor validation, property/event topic construction, raw
MQTT/retain, timers, JSON-library helpers or module filesystem resolver are added.
Existing `publish_property`/`publish_il`/`publish_raw` drivers still need Rhai-side

Five context tests cover nested state, per-host isolation/reload, key/value budgets,
replacement/removal/getter independence, reference/custom-value rejection, shared

The model/callback examples remain synthetic; real-model M1 acceptance stays open.


<a id="l5-implementation-explicit-module-bundles"></a>
### Explicit module bundles

`Compiled::with_modules` prepares one caller-supplied ordered bundle before runtime
admission. At most 16 modules are accepted; names are 1–64 ASCII letters/digits,
underscore or hyphen, with no duplicates or filesystem paths. Entry source plus
all module names/sources share the configured source-byte budget. Dependencies must
precede importers. No directory scans, file resolver or implicit library lookup occurs.

Each module is compiled/evaluated under the existing engine limits. Initializer
publish/send fails before buffering outputs; module preparation errors/panics cannot
replace a running generation. Callbacks may invoke module helpers that call the
same bounded native functions. Top-level entry imports are evaluated for each call
using an imports-only AST; ordinary entry initialization still runs once and mutable
scope survives calls. This uses Rhai's `internals` AST API, pinned to tested version
1.26.1 to avoid silently changing that contract. Limits apply per module initialization,
not one aggregate operation budget for the whole bundle.

Six module tests cover dependency order/ctx output, source/count/name limits,
forbidden initialization output/filesystem lookup, operation limits, failed
preparation/explicit replacement and preservation of initialization/mutable scope.
The real-frame L6 ctx test also imports a prepared output helper across reload.

One test uses an unchanged `aabb_common.rhai` fixture from rusthinq-scripts revision
`54292921c6edc72ea6ec901b1137845bff14e6ae` (GPL-2.0); SHA-256:
`fa6431795f3c6ba58234a59c65dcc02740696336fd89bbd9a9b7ee077abf776c`.
Only its pure `bit`/`on_off` helpers are accepted here. Other helper paths still need
framing/numeric APIs and Rhai-side IL/property/event adaptation. This is real helper
evidence, not full real-model/appliance acceptance. Fixture provenance lives beside
the copied source; unrelated script-repository changes remain untouched.

<a id="l6-implementation"></a>
## 0.2 L6 application foundation

> Implementation record: progress paragraphs and test totals below belong to their
> recorded checkpoints. For current acceptance use [milestones](0.2-validation.md#milestones);
> for configuration use [runtime](0.2-runtime.md#runtime) and [operations](0.2-operations.md).

`rusthinq-app` begins with caller-owned durable retained deletion work in
`retained_cleanup::Ledger`. L3 provides the pure deletion ledger; L6 owns file
I/O and commit ordering. No device registry, daemon composition, script host, or
general network publisher is implied by this foundation.

Ledger::open requires an existing parent directory, locks a persistent sidecar
file for the owner's lifetime, and bounds checkpoint reads before parsing. Missing
checkpoint means a new empty ledger; invalid data is rejected without overwriting
it. Do not remove the lock file while a process may own it. Use a single canonical
configured checkpoint path; arbitrary aliases to a checkpoint are not supported.

Each mutation stages a clone of the pure ledger. Commit writes a uniquely named
temporary file in the same directory, syncs the file, atomically replaces the
checkpoint, then syncs the directory. Only successful commit updates live state.
Temporary files use tempfile's restricted default permissions and are removed on
pre-rename failure. The sidecar is deliberately retained so later owners lock the
same inode. No directory or personal configuration file is created implicitly.

enqueue durably records deletions. begin returns an attempt token only after the
inventory and token high-water mark are committed. complete persists matched
results; only explicit broker-confirmed success removes work. Failed/unknown
delivery remains pending. A crash after remote deletion but before completion
commit safely repeats empty-payload deletion after recovery. Restored attempts
are invalidated while their high-water mark is preserved.

Any commit I/O error marks the owner uncertain and blocks further mutations until
drop/reopen. This includes directory-sync failure after rename: the caller must
not assume either the old or new disk image won. pending is the last committed
in-memory view, not authoritative disk state when requires_reopen is true. Failed
begin never authorizes network work. Atomic rename/directory-sync behavior is
validated on Linux; remote/network filesystems and power-loss fault injection
are unverified. The daemon must run these synchronous operations on an owned
blocking worker, not an async protocol I/O task.

Three filesystem tests cover restart recovery and stale result fencing, exclusive
ownership and invalid checkpoint preservation, and failed save blocking subsequent
sends while preserving pending memory/recoverable prior contents. Workspace
tests, formatting and warning-free Clippy remain required.

Retained value publication inventory,
device-removal orchestration and full application persistence are still pending.
The deletion file does not inventory every remote retained topic automatically;
publishers must record ownership before enabling retained values and route removals
through this owner. Retained value publication now uses this inventory, as described below.


<a id="l6-implementation-acknowledged-remote-deletion"></a>
### Acknowledged remote deletion

`cleanup_mqtt::Session` uses a caller-supplied AsyncRead/AsyncWrite transport and
an exclusive clean MQTT 3.1.1 connection. It performs CONNECT/CONNACK, then sends
only zero-payload QoS1 RETAIN=1 deletion packets. It does not dial, subscribe,
relay device traffic, or accept unrelated publishers
on the same connection. Transport TLS/authentication is caller-owned; MQTT username
and password configuration is not implemented in this foundation.

Each attempt gets a monotonic, non-reused packet ID in this connection. A matching
PUBACK is the only network success signal. Unexpected acknowledgement, EOF, write
failure or timeout poisons the connection; reconnect before retry. Exhausted packet
IDs also require reconnect. The bounded exchange timeout covers write/flush/read;
responses are four-byte bounded packets. Broker PUBACK confirms receipt, not a
promise that arbitrary remote broker storage is durable against power loss.

`delete_one` takes exclusive ownership of Ledger, runs begin on spawn_blocking,
awaits the exact PUBACK, and durably commits completion on spawn_blocking. It returns
the ledger on success. On error the ledger is dropped and must be reopened from
its checkpoint; unconfirmed work remains pending. Future cancellation may leave a
blocking commit finishing, so wait for ownership/lock release before reopening;
no network send is authorized until begin returns. Cancellation after PUBACK can
leave a completion commit finishing or a safe replayable deletion. The caller owns
this future, transport shutdown and joining its task; no reconnect loop is spawned.

Two duplex fake-broker tests cover exact QoS1 retained deletion bytes, durable
completion/reopen, wrong packet-ID PUBACK, missing-ACK timeout and poisoned-connection
retry refusal with recovered pending work. There is no live broker/device test.
Owned retained publication and explicit startup/removal draining are now implemented;
automatic daemon orchestration remains pending.


<a id="l6-implementation-startupremoval-cleanup-draining"></a>
### Startup/removal cleanup draining

`cleanup_mqtt::Session::drain` consumes a recovered Ledger and sends pending
empty retained QoS1 deletions sequentially. Matching PUBACK and a durable
completion commit precede each next send. On error it stops immediately; the
caller reopens the checkpoint and supplies a fresh connection. Acknowledged and
committed entries stay removed, failed/unsent entries stay queued. No detached
retry or reconnect task is created. Future cancellation follows delete_one's
ownership/lock-release rules. The returned completed count applies to this run,
not historical removals; successful drain returns the still-owned empty ledger.

A fake-broker restart test confirms a, drops before b's PUBACK, verifies only b/c
survive recovery, then drains them on a fresh connection and reopens empty state.
This supplies the cleanup execution path for future startup/device-removal wiring;
credentials/TLS dialing and automatic daemon
lifecycle orchestration remain pending and are not implicitly enabled.


<a id="l6-implementation-durable-lifecycle-ledger"></a>
### Durable lifecycle ledger

`lifecycle_storage::Storage` persists the L2 device ledger with an explicit schema
version and a separate generation_floor. The floor is the maximum generation ever
successfully saved by this storage owner, including generations of devices later
removed. Startup must pass it to L3 Config::generation_floor and load the saved
ledger into L2. Loaded devices remain offline until a fresh session is observed.
This does not reserve generations of admitted sessions that crashed before saving;
durable allocation before admission remains a composition requirement.

The file owner holds a persistent sidecar lock, bounds reads and device count,
validates the checkpoint using L2, and commits through a same-directory temporary
file, file sync, atomic replacement and directory sync. Invalid recovery input
is preserved and rejected. Stale revisions, conflicting same-revision contents,
and decreasing incarnation counters are rejected without changing the file.
Identical retries are allowed. A commit I/O error blocks further writes until
reopen, including uncertain post-rename failures. The storage API is synchronous
and belongs on the application-owned blocking worker.

Storage::execute handles PersistLedger and the PersistRemoval ForgetStep and returns
their correlated LedgerResult/StepResult input. It reports success only after the
file commit. Other lifecycle actions are left to their respective owners. Tests
execute actual L2 persistence effects, restore offline devices, preserve counters
after removing all devices, reject concurrent owners/corrupt state/invalid writes,
handle failed commits, and show that Removed is emitted after durable removal.
Close completion is simulated in that storage test; the runtime integration tests
below now exercise the real ThinQ1 transport completion barrier. Five tests cover
the storage boundary.

The format is new 0.2 storage; 0.1 migration, production daemon startup/admission, the complete
application effect loop and cross-store atomic removal remain incomplete. The
lifecycle and retained inventories are separate files: recovery must clean retained
topics for removed owners if a crash occurs between device removal and cleanup.


<a id="l6-implementation-owned-retained-value-publication"></a>
### Owned retained value publication

Session::publish_owned_retained registers the owner and exact topic in the durable
cleanup inventory before writing a nonempty QoS1 RETAIN=1 value. Value PUBACK does
not erase the inventory. An unknown publication result also preserves it, including
when the peer received bytes before disconnect. Payloads are bounded at 1 MiB;
empty payload must use the acknowledged deletion route. Owner conflicts, invalid
topics, inventory capacity and failed commits prevent untracked publication.

Every inventoried topic is eligible for deletion; it is not automatically scheduled
for deletion while an active value is in use. Explicit delete_one removes one;
remove_owner removes only that device/adapter's topics; drain clears all recorded
topics for startup resynchronization, disable, namespace cleanup or removal. Each
operation removes only broker-confirmed work and persists progress before advancing.
The single-owned ledger serializes publication and cleanup. Mapping changes must
clean the previous topics before recording/publishing their replacements; changing
an existing topic's owner is refused until prior ownership is removed.

On restart the inventory contains all possibly published topics, including active
values and uncertain sends. The owner decides when to drain and republish desired
state. Payload values are not persisted by this ledger; scripts/adapters must
reconstruct them. No automatic lifecycle/device-forget hook, credentials configuration,
TLS dialing or external MQTT adapter is implied. Checkpoint deletion by an operator
loses the inventory and requires separate broker cleanup; it is never automatic.

Three additional tests verify durable inventory before network publication, success
and unknown-result recovery, owner-isolated removal, and zero publication bytes
when inventory admission fails. Together with deletion/recovery tests these cover
individual, owner-wide and complete removal routes.


<a id="l6-implementation-lifecycle-removal-correlation"></a>
### Lifecycle removal correlation

`lifecycle_cleanup::apply` accepts L2 actions and triggers retained cleanup only
for `Action::Removed`, which L2 emits after close/deregister and durable device
removal succeed. Offline, Changed, ForgetStep and ForgetFailed do not erase retained
state. Remote cleanup failure does not resurrect an already durably removed device;
the separate retained checkpoint keeps its work for reconnect/startup retry.

Device retained owners use `device/{id_length}:{id}/{incarnation}`. Including the
incarnation prevents a delayed cleanup for an old device from deleting topics
published by a new device with the same ID. Length-prefixing makes IDs containing
separators unambiguous. Device publishers must use `device_owner` rather than a
bare device ID; arbitrary adapter owners remain responsible for their own stable,
bounded owner namespace.

The hook processes one lifecycle action and returns an explicit Ignored or Removed
outcome with the number of confirmed topic deletions. The future owns the ledger
during cleanup. On failure the caller drops/reopens the ledger and schedules retry;
there is no hidden retry task. The complete daemon and reconnect scheduler remain
pending. Optional runtime orchestration is described below. Tests verify that
only Removed triggers deletion and that old
incarnation cleanup preserves a newer incarnation's inventory.


<a id="l6-implementation-thinq1-lifecycle-runtime"></a>
### ThinQ1 lifecycle runtime

`runtime::Runtime` now owns L2, durable lifecycle storage and a subscription to the
ThinQ1 server. Real session Up/Down events drive the model; persistence runs on a
serialized blocking worker and returns correlated results. Superseded generations
are fenced, restored devices start offline, and offline grace deadlines run even
without further traffic. Capacity rejection closes the rejected session explicitly.
Ordinary persistence failure is reported through lifecycle events without silently
rolling back live sessions or retrying a poisoned store.

The caller must configure the server generation floor from opened storage, or
use a durably reserved block as described below, before admission. Broadcast loss emits `Lost`
and reconciles against the authoritative server snapshot. Lost raw messages are
not replayed. Observers can subscribe before reading the bounded device snapshot;
this API does not yet provide an atomic snapshot/event revision cursor.

Shutdown must stop admission, await `Server::shutdown`, signal the runtime stop
watch, then await the runtime task. It reconciles final sessions and joins started
close workers and coalesced writes before releasing storage ownership. Aborting
the task is not this shutdown protocol. Bridge deregistration,
scripts and management adapters remain pending. Retained cleanup can now be
attached through the optional worker below.
The server's Down notification alone does not prove its session task has joined.

Six integration tests exercise real framed ThinQ1 sessions, replacement and
offline restore, broadcast loss recovery, grace expiry, storage failure reporting,
and shutdown lock release. A plain loopback harness is available as:

```sh
cargo run -p rusthinq-app --example thinq1_lifecycle -- 127.0.0.1:9001 /existing/state/devices.json
```

Press Enter to stop. The parent directory must exist. This harness uses plain TCP;
production admission still requires the TLS front door and provisioning wiring.

`Handle::forget` submits a bounded local-device removal request. L2 quiesces the
device immediately; L6 closes the exact generation and waits for its transport
future to finish before acknowledging Close. Even an already offline device checks
its last generation's completion. L3 keeps a bounded completion receiver per task;
Down alone remains insufficient. The Server owner reaps completed JoinSet tasks on
admission or shutdown. Cancellation/panic without a completion signal fails the
close step instead of confirming deletion while completion is unknown.

L6 then executes PersistRemoval on the same serialized storage worker. Only its
successful durable commit emits Removed. A failed commit keeps the quiesced device
and emits ForgetFailed. Connections arriving while removal is active are rejected;
after Removed the same ID obtains a new incarnation. Tests check peer EOF, the
committed empty ledger, incarnation reuse and absence of Removed on failed commit.
This API supports ThinQ1 devices; optional bridge deregistration is described below.
Without the optional retained worker, consumers must
route Removed through the incarnation-scoped cleanup hook and recover inventory.


<a id="l6-implementation-optional-runtime-retained-cleanup"></a>
### Optional runtime retained cleanup

`Runtime::with_retained_cleanup` attaches one exclusive connected MQTT session
and its durable retained ledger. A separate worker compares canonical device
owners in that inventory with the latest lifecycle snapshot on startup and each
state change. Known offline and quiesced/failed-removal devices preserve inventory;
only an absent ID/incarnation qualifies for remote deletion. L2 removes that entry
only after its durable removal commit. Older incarnations and crash gaps between
device removal and remote cleanup are therefore recovered at startup.

Snapshots use a watch channel, so coalescing cannot discard a deletion request:
the durable inventory remains the pending-work source. This path does not rely on
the lossy observer broadcast. Arbitrary adapter owners and noncanonical device
owner strings are preserved. Publishers must use `device_owner`; adapter-wide or
namespace cleanup continues to use explicit `remove_owner`/`drain` routes.

Each deletion requires the matching PUBACK and durable completion before advancing.
On network/storage failure the worker stops, drops its exclusive ownership and
emits `CleanupFailed`; it does not resurrect the removed device or discard pending
inventory. Restart with a reconnected session and reopened ledger retries remaining
orphan owners. Same-process recovery can now use `Handle::attach_retained_cleanup`
with a fresh session and reopened ledger after failure. A bounded attachment queue
is owned by the runtime; it rejects a second running worker without aborting the
first, releases rejected resources, and rejects attachment after shutdown. Caller
cancellation before acceptance does not launch the worker. Once accepted, the
runtime owns it until failure or normal shutdown. Automatic transport dialing and
reconnect scheduling remain pending.
Shutdown sends a final snapshot and awaits the worker, including in-flight remote
confirmation and storage commits. Individual exchanges have the session deadline.

Four integration tests cover runtime Forget-to-cleanup, shutdown ownership release,
adapter/noncanonical-owner preservation, failed remote confirmation and startup
recovery, same-process reattachment, rejection while running/after shutdown, and
resource release. `Handle::cleanup_status` exposes Disabled/Running/Failed through
a watch receiver; late observers can inspect current health without relying on
the lossy event broadcast. The session is supplied by the caller; credential/TLS dialing and live
retained publication commands in the runtime remain pending. The full M1 daemon
flow is still incomplete.


<a id="l6-implementation-bridge-aware-forget"></a>
### Bridge-aware Forget

`Runtime::with_bridge` supplies the L4 registration inventory, a cancellation-safe
`Deregistration` cloud adapter and a nonzero operation deadline. Forget captures
the exact device/incarnation/bridge-generation token and disables its downlinks.
Disabled registrations still require deregistration; absence of a registration
allows the ordinary local-only path. Conflicting incarnations or a changed token
on retry are rejected without changing a successor registration.

After local transport completion, L2 issues Deregister. L6 awaits the adapter,
confirms the exact token in L4, and only then executes durable PersistRemoval.
Only Removed permits retained cleanup through the existing inventory worker.
Remote error/timeout leaves the device quiesced and reports ForgetFailed;
another explicit Forget retries the captured registration. No implicit retries
or successful removal are reported for unknown outcomes. The adapter must make
repeated deregistration safe after an uncertain result.

The runtime owns and joins deregistration futures alongside close workers during
shutdown. Timeout drops the future; adapters must cancel on drop and must not
spawn detached work. Three tests cover remote failure then explicit retry,
disabled registration removal, durable-write ordering, timeout cancellation and
late confirmation/retry protection of a successor. They use fake cloud adapters.
Actual LG deregistration requests, registration recovery across restart, automatic
retry policy and cloud uplink/local binding orchestration remain pending. This
execution boundary does not claim real LG-cloud compatibility.


<a id="l6-implementation-durable-generation-reservation"></a>
### Durable generation reservation

`Storage::reserve_generations(count)` commits an exclusive `(floor, ceiling]`
range before any transport admission. The returned floor and inclusive ceiling
must configure L3 together. The storage checkpoint retains the ceiling even if
no identified session or ledger update ever commits. Restart reserves above that
ceiling, intentionally skipping all unused numbers in the previous block.
Ordinary ledger saves never lower the reservation high-water mark.

ThinQ1 admission and ThinQ2 admission/redeploy enforce `generation_ceiling` and
fail explicitly when exhausted. The default ceiling remains `u64::MAX` for
standalone transport users; that default alone supplies no durable crash guarantee.
Zero/overflow reservation fails without writing. A commit I/O failure returns no
usable block and poisons storage until reopen, including uncertain rename outcomes.
Reservation runs on the application-owned blocking worker.

The lifecycle example reserves one million generations before constructing L3.
This is a harness budget, not a production limit chosen from appliance evidence.
Optional in-process block extension is described below; exhaustion must not wrap
or silently resume admission. Three storage/admission tests cover restart without any
session ledger save, preserved ledger/counters, exhausted ranges and commit failure;
one MQTT test covers redeploy and admission exhaustion.

This closes generation reuse across admission-to-save crashes only for callers
using this reservation path. Durable incarnation reservation, unfinished Forget
journaling and restart restoration of cloud registrations remain pending. No
complete crash-recovery or M2a acceptance is claimed.

`Runtime::with_generation_refill(count, low_water)` now opts the ThinQ1 runtime
into automatic extension. Initial persisted ceiling must match L3's configured
ceiling; count is nonzero and low_water is smaller than count. The runtime checks
the current budget at event boundaries and at most 100 ms idle intervals. It uses
the existing serialized blocking storage worker to commit the next block, then
extends L3 only with that exact contiguous floor/ceiling. Existing sessions remain
connected. Repeated/stale/gapped/shrinking extensions and stopped owners are rejected.
The MQTT handle exposes the same extension primitive; its automatic L6 budget
supervision is now available through `Runtime::new_mqtt` below.

While a reservation is in flight, one L2 storage action may wait in a deferred
slot; L2 continues coalescing subsequent updates. On completion, that action runs
before another refill. No independent storage owner or growing effect queue is
introduced. Shutdown joins reservation work and deferred lifecycle writes. A
failed commit or application of the range reports GenerationRefillFailed and
disables automatic refill; the previous ceiling remains in force. GenerationExtended
reports success. After uncertain storage I/O, reopen/recovery is still required.

The example enables million-number refills with a ten-thousand-number low-water
margin. Two integration tests exercise repeated extension alongside live ThinQ1
traffic and lifecycle writes, unchanged live connection, durable range recovery,
invalid/stopped extension and failed-commit fencing. Proactive refill cannot
guarantee admission under arbitrarily rapid churn or slow storage: exhaustion
remains explicit, and production margin selection requires appliance evidence.


<a id="l6-implementation-thinq2-mqtt-lifecycle-runtime"></a>
### ThinQ2 MQTT lifecycle runtime

`Runtime::new_mqtt` connects the local ThinQ2 broker to the same L2 lifecycle,
serialized storage, grace timers, optional retained cleanup and generation-refill
execution loop. Generation fencing applies to Up/Down and forwarded transport
events; redeploy on one TCP stream changes the session generation while preserving
device incarnation. Its transport adapter uses only lifecycle/control operations;
it does not frame ThinQ1 commands on MQTT connections.

MQTT tracks a completion receiver for each active transport. Redeploy moves it to
the new logical generation instead of accumulating historical entries.
`Handle::close_and_wait` closes the exact target and awaits broker connection
future completion; early Down alone is insufficient. MQTT tasks remain owned by
the caller/front door. Stop admission, call `Broker::stop`, join transport tasks,
then signal and await the application runtime. Abort/panic without a completion
signal is not a successful close barrier.

Two integration tests send actual CONNECT/SUBSCRIBE/deploy/completion packets over
duplex streams. They cover raw cloud-bound forwarding, redeploy/incarnation
preservation, automatic durable generation refill, Forget after redeploy with peer
EOF, ledger removal, EOF/grace handling and offline restore. No appliance capture
or real cloud validation is claimed.

Independent runtimes must not share a ledger or treat their counters as a shared
namespace. The mixed service path below now uses one owner. ThinQ2 cloud bridge,
production daemon and management/script integration remain pending.
M1/M2a/M2b remain incomplete.


<a id="l6-implementation-shared-thinq1thinq2-ownership"></a>
### Shared ThinQ1/ThinQ2 ownership

`Broker::sharing(server.handle(), clock)` now attaches MQTT to the ThinQ1 server's
transport registry, generation allocator, completion inventory, aggregate connection
bound and stop signal. One `Runtime::new` subscribes to their common events and
snapshot and owns one L2 model, device ledger and optional retained cleanup worker.
Generation reservation/refill covers both admissions and MQTT redeploy atomically.
Each protocol still owns its codec and connection execution; no lifecycle or
persistence responsibilities move into L3.

Every entry records its protocol. ThinQ1/MQTT send handles reject the other
protocol with WrongTransport before writing; ThinQ1 bridge downlink also rejects
MQTT targets before firmware learning. Generic snapshot/close/allocator operations
apply to the shared registry. The same ID replaces its prior connection across
protocols, keeping its lifecycle incarnation. This provides fencing, not evidence
that every 0.1 multi-socket appliance tolerates replacement.

Stop admission on both listeners before shutdown. The shared stop signal wakes
both protocols; `Server::shutdown` joins only its own ThinQ1 tasks. The caller/front
door must also join MQTT tasks before stopping and awaiting L6. Dropping/stopping
either shared transport owner stops the shared service; independent deployments
must use independent constructors and ledgers.

Two additional mixed integration tests cover cross-protocol replacement,
generation uniqueness/refill, unchanged incarnation, codec rejection, Forget
isolation, one durable ledger, aggregate admission bounds and MQTT wake/join on
server-owner shutdown. A plain TCP harness owns both listeners and task sets:

```sh
cargo run -p rusthinq-app --example mixed_lifecycle -- 127.0.0.1:9001 127.0.0.1:1883 /existing/state/devices.json
```

Press Enter to stop. The parent directory must exist. TLS/provisioning composition,
production configuration, scripts, management API and real appliance validation
remain pending. This harness does not complete M1 or production readiness.


<a id="l6-implementation-supervised-mixed-tls-service"></a>
### Supervised mixed TLS service

`tls_runtime::Service` now constructs one shared ThinQ1/MQTT transport owner and
L6 lifecycle runtime and supervises two prepared TLS front doors. Its handle
exposes lifecycle snapshots/events and existing management/retained-cleanup
attachment operations. Caller-selected identities, CA lifetime, provisioning and
TLS compatibility policy remain separate configuration responsibilities.

External stop, stop-sender disappearance, listener termination or runtime
termination triggers shutdown of both listeners. The service signals the shared
transport stop, requests front-door shutdown, awaits both front-door task sets
(including pending TLS handshakes and MQTT transport futures), then signals and
awaits L6's final reconciliation/storage workers. Failure is returned after this
cleanup. A previously true stop also drains ownership. Callers must signal and
await the service rather than abort its future; abort is not this join protocol.

Two integration tests verify CA/hostname-authenticated TLS handshakes, real ThinQ1
Mon and MQTT CONNECT/SUBSCRIBE/deploy packets, shared lifecycle/generations,
partial ClientHello shutdown, persisted offline devices and released storage lock.
They also cover an already-stopped service. The CA is ephemeral test-only state;
no production CA files are created or overwritten.

The runnable harness loads an existing persistent CA and commits a generation
reservation before admission:

```sh
cargo run -p rusthinq-app --example mixed_tls -- 127.0.0.1:9001 127.0.0.1:8883 thin.example mqtt.example /existing/ca.crt /existing/ca.key /existing/state/devices.json
```

Press Enter to stop. This harness uses baseline TLS identities for the exact
provided SNI names. Explicit RTK/no-SNI configuration remains available through
the existing FrontDoor/identity APIs; it is not inferred automatically here.
TLS/provisioning HTTP composition, metadata delivery, persistent configuration,
cloud transport, scripts and GUI remain pending. M1/production acceptance and
real-appliance non-inferior validation are not complete.


<a id="l6-implementation-https-services-and-thinq1-metadata-delivery"></a>
### HTTPS services and ThinQ1 metadata delivery

`tls_runtime::Service::with_local_service` now adds up to four prepared L3 HTTPS
service listeners to the same supervisor. ThinQ1 HTTP and ThinQ2 provisioning can
use their existing LocalService implementations. Any listener failure stops the
entire service; normal shutdown stops admission and joins all extra listeners
and their HTTP futures before final L6 shutdown. CA/signing-worker construction
and signing-worker stop/join remain caller-owned; supplying a provisioning service
does not silently create or detach a signer.

`with_metadata` attaches the ThinQ1 HTTP service's bounded receiver to L6.
`Handle::metadata_snapshot` exposes latest observations by device ID, and
`Event::Metadata` reports updates. Metadata does not itself create a lifecycle
device or mark it online. The snapshot uses the configured device capacity;
updates of an existing ID remain possible at capacity, while a new ID is explicitly
rejected without eviction. This additional inventory is bounded independently of
the lifecycle ledger. Durable Removed clears that ID's metadata; otherwise unknown
observations remain until process restart. TTL/explicit metadata-only removal and
capacity validation against appliance populations remain pending.

After metadata producers are stopped/joined, runtime shutdown drains observations
already accepted into the receiver. HTTP 200 means L3 validated/queued the observation,
not that L6 durably stored it: a full L6 inventory can still report Rejected.
Metadata is currently in-memory and ID-scoped, without durable persistence,
incarnation/session correlation or automatic script/model binding. Caller-supplied
metadata receivers must come from the validated L3 service and be quiesced before
runtime shutdown.

Three additional tests cover real TLS ThinQ1 XML metadata delivery, provisioning
route advertisement of the actual MQTT port, four-listener shutdown, signer join,
bounded metadata update/rejection and final queue drain. Metadata remains an
observation even when received before the first device session. Provisioning
certificate routes/CSR behavior remain covered by L3 tests; production config,
model/driver binding, metadata migration/persistence and M1 script/GUI acceptance
are still pending.



<a id="l6-implementation-script-worker-ownership-foundation"></a>
### Script worker ownership foundation

`Runtime::with_scripts` owns an optional `scripts::Owner`. Every lifecycle update
reconciles its device/session bindings; shutdown signals and joins all workers.
The owner bounds active plus retiring workers and requires explicit reaping before
successor admission. Private completion tokens fence incarnation, transport session,
attachment identity and script generation. Accept and dispatch must occur in the
same runtime actor turn. Four tests cover stale completion and retirement bounds.
Live attachment commands, configured Response/Ready/Data callbacks, ordered fenced
output dispatch, explicit publication sinks and transport send receipts now exist.
Five synthetic-script tests exercise real ThinQ1 frames, sink absence/overload,
fault-prefix handling, reconnect reaping and ordered bursts. Automatic model
selection, start/online/offline/timers,
production retained adapters and real-driver acceptance remain open. See
[L5 implementation](0.2-runtime-implementation.md#l5-implementation) for bounds and delivery semantics.

`Runtime::new_mixed` requires ThinQ1/MQTT handles to share the same registry by Arc
identity. Common lifecycle operations use that registry; script send queries the
captured session's protocol and delegates to the matching codec. Each send still
validates the exact session, so replacement between lookup and send rejects rather
than writing to a successor. The TLS supervisor and mixed plain example now use
this constructor; TLS builders forward optional script owner/sink configuration.
Data callback encoding is explicit UTF-8 (default) or lowercase hex. Four tests
cover mixed writes, binary MQTT data/redeploy, unrelated registry rejection and
UTF-8 admission errors that leave script state healthy. Device MQTT downlinks are
non-retained; the external retained publication adapter remains unimplemented.

Live `Handle::reload_script` now shares bounded command admission with attachment.
It accepts precompiled replacements and captured session/script generation, uses
the existing serialized worker, keeps callback configuration and returns the new
generation only after replacement. L3/L2 session and stop state are rechecked after
the worker wait. Compile failure happens outside admission and leaves scope intact;
runtime faults require explicit reload. Four tests verify scope/generation boundaries,
fault recovery, successor protection and mailbox overload/queued shutdown cancellation.
The actor currently awaits bounded reload completion; transport tasks stay separate.
See L5 for lost-reply and initialization semantics. No retained publications are added.

L5 now supports opt-in ctx/text callbacks with bounded per-generation state and
opaque publish/send/send_json methods. L6 owner attachment/reload verifies the ctx
device ID matches its target. One ThinQ1 real-frame test verifies metadata/state,
ID mismatch rejection, exact send bytes and fresh context after reload. Model
metadata is caller-selected; full legacy ctx/IL-helper compatibility, modules,
start/lifecycle/timers and real-driver fixtures remain pending. See L5's context
section for value types, budget accounting and reference rejection.

Precompiled script generations can now carry an explicit bounded Rhai module bundle.
L6 does not load files or compile modules: preparation occurs before attach/reload.
The ctx real-frame test imports a module helper for output and verifies replacement
still resets context. Six L5 module tests cover dependency order, admission limits,
initializer isolation, import-only callback evaluation and replacement. A pinned
real aabb_common fixture exercises pure helper functions, not full driver acceptance.
See L5 for AST/version pinning and remaining unsupported helper APIs.


<a id="l6-implementation-full-device-id-retained-cleanup-coverage"></a>
### Full device-ID retained cleanup coverage

Canonical retained device ownership now accepts the same 256-byte device ID limit
as transport identity, including UTF-8 IDs. The retained owner budget is 512 bytes
so namespace, byte-length prefix and a maximum u64 incarnation do not truncate or
reject valid identities. Previously the cleanup formatter limited IDs to 220 bytes,
creating a removal gap for accepted long device IDs. Topic and total ledger/store
budgets remain independently enforced. Existing checkpoint data remains valid.

An integration test persists a 256-byte UTF-8 device owner with u64::MAX incarnation,
reopens it, identifies it as absent through startup recovery, sends an exact retained
QoS1 tombstone, confirms PUBACK, and reopens an empty ledger. This validates the
owner parser and removal route rather than only the formatter's acceptance.

<a id="refactoring"></a>
## 0.2 Refactoring and Ownership

This refactoring covers storage, task ownership, notification buffers, capture and
protocol utilities across the seven workspace crates and the GUI. `legacy/0.1`
remains the comparison and migration reference. No Rhai functions, driver files or
supported models are added by this work.


<a id="refactoring-shared-checkpoint-owner"></a>
### Shared checkpoint owner

`rusthinq-app/src/checkpoint.rs` centralizes the storage procedure used by account,
lifecycle, pairing and retained-cleanup stores:

- Hold the sidecar file lock for the owner's lifetime; never delete the lock file.
- Read one byte beyond the size limit to detect oversized input.
- Write a temporary file in the same directory, sync it and atomically replace the destination.
- Update domain state only after parent-directory synchronization succeeds.
- Refuse subsequent writes after a failure until the store is reopened. Replacement
  may have succeeded before directory synchronization failed, so the owner cannot
  assume which disk image won.

The file owner and `tempfile` handle locks and temporary files through RAII.
Schemas, validation, generation reservation, pairing ownership and deletion
confirmation remain in their domain modules. The checkpoint utility does not
interpret device semantics.


<a id="refactoring-async-task-ownership"></a>
### Async task ownership

`OwnedTask` in `rusthinq-app/src/task.rs` wraps `JoinHandle`. Normal paths explicitly
await completion. If the owning future is cancelled or returns early, `Drop`
requests task abortion to prevent detached work. `Shutdown` sends the watch-based
stop signal on both explicit shutdown and owner release.

The owners cover the daemon signer/core, TLS lifecycle runtime, management name
refresh and LG observer, per-device cloud supervisors and lifecycle cleanup.
Normal shutdown preserves the order: device terminal output, external MQTT flush,
then auxiliary-service shutdown. Tasks already owned by `JoinSet` retain that
ownership.

`Drop` cannot asynchronously join and therefore does not guarantee completion.
Aborting cannot forcibly stop an already running `spawn_blocking` task. Existing
explicit await paths own normal completion of file, cryptographic and script work.


<a id="refactoring-notification-and-diagnostic-caches"></a>
### Notification and diagnostic caches

LG records store their integer sequence and serialized size alongside JSON. Paging
avoids repeatedly parsing sequence strings, and eviction avoids reserializing
records. REST and WebSocket use the same device filter; internal status uses an
enum while external strings and decimal-string sequence IDs remain unchanged.

Record/reset state changes and broadcasts occur within the same mutex section.
This removes the race where an old record could be broadcast after reset. Limits
apply to the completed envelope; invalid input does not consume a sequence.

The publication cache stores scope and per-entry size. Updates, deletion, scope
replacement and device removal adjust accounting incrementally. Replacing a topic
subtracts its old size before checking the new value, preventing valid updates near
the limit from being rejected and clearing the device cache.


<a id="refactoring-cli-and-capture"></a>
### CLI and capture

`rusthinq-tools/src/capture.rs` separates wire/LG capture and observation from the
crate root, which reexports the existing public functions. `EventStream` defines
the WebSocket type once. JSONL write/flush and LG continuity checks are shared.
Capture writes and adoption-archive reads use Tokio file APIs.

LG stream EOF, Close, WebSocket errors, invalid messages and status/loss changes
flush a loss record before returning a capture error. Wire-stream behavior is
preserved. CLI argument and flag lookup use shared helpers, nested branches are
flattened, and WebSocket close waits have a shutdown deadline.


<a id="refactoring-smaller-shared-utilities"></a>
### Smaller shared utilities

Uppercase/lowercase hex output uses one alphabet-based encoder; script binary
output uses the same protocol utility. MQTT filter validation avoids an
intermediate vector. Script invocation/completion store the existing `Context`
instead of duplicating device, session and generation fields. The GUI shares one
LG-record reset method.


<a id="refactoring-verification"></a>
### Verification

Regression checks cover storage locking/restart/failure preservation, task
cancellation, cache update/scope replacement, notification size/filter/sequence and
capture loss handling. `scripts/check-0.2.sh` runs workspace tests, strict Clippy,
eight feature combinations, formatting and JavaScript syntax checks. The browser
checks in `scripts/check-gui.cjs` cover control, diagnostics, generation fencing,
LG timelines and export.

Live LG accounts and appliance connections are outside this refactoring validation.
