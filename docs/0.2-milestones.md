# rusthinq 0.2 Milestones

See the [overview](0.2-plan.md) for scope and the [design record](0.2-design.md) for contracts
and rationale. Check items only after their artifacts and validation exist.

## M0 — Harden and Review the Architecture

- [ ] Review H1/H7 ownership and dependency direction for every authoritative state store.
- [ ] Review H2/H3 script output ordering, command validation, generation replacement, reload, and panic isolation.
- [ ] Review H4/H5 subscriptions, overload, shutdown, forget, and partial failure outcomes.
- [ ] Review H6's classification of actual LG exceptions and the information available when selecting a policy.
- [ ] Resolve or accept each intentional behavior change listed in the contracts; record remaining structural blockers.
- [ ] Walk through connection/state publication, command/no response, reconnect/late close, reload/panic, forget failure, and unknown compatibility-profile scenarios against the ownership tables.

Exit criteria: each scenario has an unambiguous owner, ordered inputs/outputs, and failure
outcome. No unresolved structural blocker remains. New contracts are reviewed, not merely
written. Implementation details and full tool inventories may remain open.

## Preparation — After M0, Archive 0.1 and Start the New Root Project

- [ ] Record the original 0.1 revision and relocate the tracked tree to `legacy/0.1/`, retaining Git metadata and 0.2 planning documents at root (D0).
- [ ] Verify the independent legacy workspace build/run commands and document relocation-only adjustments.
- [ ] Establish the root project at `0.2.0-dev`, excluding legacy from workspace membership and default automation.
- [ ] Verify no legacy source dependencies, personal files, or ignored build artifacts enter the new project/archive.
- [ ] Select the real ThinQ1 script, pin fixture/spec revisions, and record its existing harness baseline before M1.

Keep relocation separate from implementation changes. No relocation is authorized merely by
completion of a draft design document; this checklist describes the planned implementation order.

## M1 — ThinQ1 Plus One Real Script

- [ ] Create the new 0.2 execution path; implement ThinQ1 processing/ACK contracts using selectively reused TLS/framing components (D0, C2).
- [ ] Implement the new IL-agnostic script-host path with an opaque sink and no MqttConnection factory dependency (D1, S1).
- [ ] Feed a real script's status input and observe its descriptor, values, and events as script outputs; IL conformance is checked in rusthinq-scripts (S2).
- [ ] Route those outputs through the MQTT adapter; verify defined behavior with external MQTT disabled (S3).
- [ ] Connect the existing devlist projection to the GUI through the application handle; no new property UI is required.
- [ ] Deliver one supported command to the script, with script-side validation and device transmission and explicit result semantics (A3).
- [ ] Verify stale-generation rejection, single ownership, bounded output behavior, stalled writes, and shutdown (R1–R2).
- [ ] Verify panic containment without replay or restart, including unrelated-device progress (P1).
- [ ] Compare the new slice with the fixed reference using replay or isolated runs; record differences and review boundaries before expansion (D0).

Exit criteria: captured ThinQ1 input passes through a real script into MQTT output, and the
device appears in the existing GUI device-list projection. Core tests require no real network
or waits. The host contains no IL types or validation. Preserve or explicitly document any
changed behavior.

## M2a — Shared Lifecycle and Script Services

- [ ] Move device replacement/offline policy to its explicit owner and verify late close/timer sequences (C3, R1).
- [ ] Migrate script timer/runtime ownership and reload ordering; reject outputs from replaced script generations (R3, S1).
- [ ] Move IL helpers, command validation, and descriptor/value state from the host into Rhai (D1); coordinate the rusthinq-scripts changes.
- [ ] Connect persistence/recovery and removal operations; specify failure outcomes and durable versus live state.
- [ ] Connect bridge management and outbound reconnect policy without adding panic recovery machinery (R4, P1).
- [ ] Verify new paths have no dependencies on legacy callbacks, global mutable lifecycle services, or state owners.

Exit criteria: migrated sessions and script services have explicit lifecycle owners and pass
replacement, reload, persistence failure, and shutdown tests. Broader script compatibility is
verified in M3, rather than assumed from one script.

## M2b — ThinQ2 Server Paths

- [ ] Migrate device/session interpretation and ACK policy with representative input fixtures.
- [ ] Wire the embedded device MQTT broker to session runtimes and verify its lifecycle independently of external MQTT.
- [ ] Audit and migrate provisioning dependencies; verify representative provisioning requests.
- [ ] Audit and migrate firmware service dependencies; verify existing response behavior.
- [ ] Audit SNI passthrough ownership/routing/shutdown and verify the preserved path.
- [ ] Exercise local-only and bridge-enabled ThinQ2 paths and record any unavailable real-device validation.

Exit criteria: each server service has a documented owner and a validated retained or migrated
path. No service is considered complete merely because ThinQ2 packet processing moved.
M2a and M2b may proceed independently where their contracts permit; both gate M3 completion.

## M3 — Complete Adapters, GUI, and Compatibility Review

- [ ] Inventory full MQTT/configuration/persistence/Rhai/capture compatibility; classify changes and write migration notes (C4, S2–S3).
- [ ] Complete external MQTT mapping, retained cleanup, and resynchronization (A2).
- [ ] Migrate existing GUI query/control/device/bridge/monitor functionality; keep property-value screens and editors out of the baseline.
- [ ] Finalize snapshot/subscription handoff, loss indicators, and slow-consumer recovery (A3).
- [ ] Verify management API authentication, command failures, and operation results; serve it without GUI assets.
- [ ] Verify daemon/GUI/API operation without an external broker and continued operation during broker failure.
- [ ] Run cross-repository script compatibility checks against recorded rusthinq-scripts revisions; IL conformance runs in rusthinq-scripts.
- [ ] Decide and test the raw-MQTT script escape hatch behavior, including MQTT-disabled operation (S3).

Exit criteria: existing GUI functionality uses shared application services, full compatibility
changes are explicit, and device semantics are produced only by scripts (D1).

## M4 — CLI, MCP, and Tool Consolidation

- [ ] Inventory usage and unique capabilities; finalize keep/consolidate/remove decisions.
- [ ] Assess retained-gc for retirement after adapter cleanup and migration/repair needs are covered.
- [ ] Migrate online tools and MCP to the management API; retain shared offline codecs and analysis.
- [ ] Verify capture compatibility and replay, existing MCP functionality, and injection restrictions.
- [ ] Document replacement commands, removals, and deprecation periods.

Exit criteria: retained tools have explicit use cases and use common command/result semantics.
No tool is removed solely because its name overlaps with an adapter responsibility.

## M5 — Release Validation

- [ ] Audit design decisions against implementation: dependency direction, state owners, queue/task lifetime, and panic isolation.
- [ ] Run core sequence tests and runtime/adapter failure scenarios specified in the design record.
- [ ] Pass required workspace checks and supported bridge/scripting/gui build combinations.
- [ ] Perform available real-device validation and document unverified environments.
- [ ] Verify migration/rollback from 0.1 configuration, saved state, scripts, and tools.
- [ ] Update README, operations/development documentation, and release notes.
- [ ] After release gates pass, validate production cutover and remove legacy/0.1, temporary wiring, and unused dependencies (D0). Preserve the reference revision and rollback instructions.

Exit criteria: supported functionality has migrated, intentional changes are documented, and
broker-independent operation and migration are verified. No no_std or public-library stability
requirement applies.

## Working Principles

- Reference decision IDs in implementation changes instead of repeating their rationale here.
- Import legacy components only as needed, recording provenance and verifying their new dependencies.
- Keep the new root entry point runnable as features land; retain the fixed reference for comparison rather than refactoring it in parallel (D0).
- Separate selective component reuse from intentional behavior changes in reviews.
- Resolve structural uncertainty in M0; use implementation evidence to refine details without silently changing accepted contracts.
- Estimate the remaining work after M1 demonstrates the actual migration cost.
