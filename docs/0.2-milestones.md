## Working Principles

- Reference decision IDs in implementation changes instead of repeating their rationale here.
- Import legacy components only as needed, recording provenance and verifying their new dependencies.
- Keep the new root entry point runnable as features land; retain the fixed reference for comparison rather than refactoring it in parallel (D0).
- Separate selective component reuse from intentional behavior changes in reviews.
- Resolve structural uncertainty in M0; use implementation evidence to refine details without silently changing accepted contracts.
- Estimate the remaining work after M1 demonstrates the actual migration cost.

### Explicit management driver recovery — 2026-10-02

The dashboard and `POST /api/devices/{id}/reload` now request configured-driver
preparation through AppHandle. Healthy/faulted workers survive bad source; explicit
recovery replaces and initializes a fresh generation. Old session/script/model
scopes are fenced, and external MQTT is optional. Automatic attachment and manual
reload share L5's preparation budget; L6 joins started jobs on shutdown. No
automatic panic retry or extra retained publisher is added. This closes the explicit
GUI/API recovery capability, not the pending bridge controls or M1 ThinQ1 write gate.
