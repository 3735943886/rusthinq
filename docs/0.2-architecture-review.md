# 0.2 boundary audit — 2026-10-02

M0 technical review is closed in the closure section below. Repeated user instructions authorized implementation,
but they did not establish completion of the architecture review. Preparation and
implementation proceeded before the planned M0 gate. This sequencing deviation is
recorded here rather than treating existing code as approved contracts or marking
M0 complete retrospectively.

## Configuration and build contract

Daemon user configuration is UTF-8 TOML, bounded to 64 KiB. Duplicate keys,
unknown fields and invalid types are rejected. Parse errors do not echo source
text or secrets. Paths remain relative to the configuration file. JSON configuration
is rejected; JSON management payloads and existing internal checkpoint encodings
are unchanged. Translate the configuration into TOML before using the new binary.
See [runtime](0.2-runtime.md) and [operations](0.2-operations.md) for examples.

The supported compile-time capabilities are `bridge`, `scripting` and `gui`,
independently selectable and all enabled by default. The eight combinations are
core, each single feature, each two-feature pair and all three. Use
`--no-default-features --features bridge,scripting` for the full API-only daemon;
use `--no-default-features` for local transports/management/retained cleanup without
LG account policy, firmware relay, Rhai workers or GUI assets.

`drivers` is rejected when scripting is absent, `cloud_account` when bridge is
absent, and explicit `management.gui = true` when GUI is absent. Embedding through
Daemon::prepare enforces the same capability checks before opening checkpoints or
listeners. Context/publication scope and configuration types remain lightweight
application types without loading a Rhai engine. Disabled script invocation has an
explicit application result rather than a fake execution success. Account routes
remain available to report absent ownership. Without bridge, the HTTPS front door
has no remote passthrough and refuses unserved names.

Runtime effect branches are separated at compilation while retaining one lifecycle
select loop and authoritative owner. Core model projection cleanup runs even with
scripting absent. Tests exercise model restart/rebinding and confirmed removal in
both builds. No retained publish or cleanup path was bypassed by the feature split.

Feature validation and test results are recorded in the milestone verification
paragraph. This resolves the optional dependency blocker, but did not by itself close the
M0 ownership/policy/scenario review or establish full M5 release acceptance.

Verification after the feature split: 265 workspace tests and 51 core app tests
passed, including composed TLS/provisioning/shutdown, metadata removal, management
and durable retained cleanup. All eight combinations passed all-target Clippy
with warnings denied; workspace Clippy, formatting and diff checks passed.
The added capability tests cover TOML and embedding preflight, relative account
checkpoint paths and disabled API results. `cargo tree` confirms the core daemon's
normal dependency graph excludes rusthinq-bridge, rusthinq-scripting, Rhai and
reqwest. Real LG-account/appliance validation remains excluded.

## M0 technical review closure — 2026-10-02

This closes the six technical review items after correcting the reported boundaries.
It is an implementation/architecture review, not a claim of separate user sign-off,
release acceptance, or completed M1–M5 functionality. The earlier sequencing
violation remains in this record. Missing cloud sockets, pairing management,
representative replay and compatibility tooling remain implementation gates with
explicit owners; they do not require constructing those later milestones before
reviewing their architecture.

### Authoritative owners and dependency review (H1/H7)

| State or decision | Sole owner | Inputs and execution boundary |
| --- | --- | --- |
| Framing, ACK ownership and compatibility selection | L1 connection model/`lg_compat` | L3 supplies captured bridge/session inputs; account login alone never makes a relay active |
| Known devices, incarnation, replacement, grace and forget stages | L2 Model | L6 feeds transport/tick/effect receipts and executes returned actions; cached lists and files do not decide lifecycle |
| Live socket registry, current protocol codec and write receipts | L3 | Generation-targeted commands; L6 resolves receipts into application Delivery, which does not imply appliance acknowledgement |
| LG account authentication, expiry, retry and cancellation | L4 account actor | L6 supplies CredentialStore; priority logout fences owned HTTP work and awaits started filesystem work |
| Registration/relay fencing and cloud-confirmed deregistration | L4 BridgeHandle | Exact captured Registration; future account/pairing wiring must also preserve account identity and attempt ownership |
| Script generation, fault, bounded invocation/order/timers and preparation | L5 worker/Scheduler/Preparation/drivers | L6 supplies current scopes and clocks, runs/join effects, and fences results before dispatch. Driver filesystem reads/module preparation now live in L5 |
| Checkpoint locks, atomic durability and generation reservations | L6 storage modules | A single joined writer; uncertain writes refuse continuation. Results return to L2/L4 rather than asserting success |
| Broker inventory, PUBACK delivery/deletion and reconnect cache | L7 MQTT adapter through L6 Ledger | Durable inventory precedes every retained publish; exact-topic, owner, all and restart cleanup remain available in every feature build |
| HTTP authorization, origin checks and presentation | L7 management | AppHandle only; no separate cloud actor, L3 receipt, transport handle or Rhai worker is passed to adapters |
| Construction, capability preflight, task lifetime/shutdown wiring | Daemon | Creates lower services, binds the account owner once, and passes AppHandle to adapters |

`api::AppHandle` is now an explicit restricted facade without Deref. It exposes
application delivery/rejection, projected events, metadata DTOs and account results.
`runtime::Handle` remains an embedding/composition interface for supplying workers,
transport plumbing and tests; it is not the L7 AppHandle. L7 owns its own broker
connection/codec and can use pure L1 codecs; the dependency rule prohibits access
to lower state owners rather than reuse of stateless encoding functions. L4's
remote connection responsibility covers LG/device relay, not the separate consumer
MQTT transport explicitly assigned to L7.

### Invocation and failure review (H2/H3/H4/H5)

L5 Scheduler owns admission until ordered completion release, including buffered
results. Wrong-device, duplicate and late completion cannot replace pending data.
Different devices release independently. L5 owns timer replacement, cancellation,
per-device limits and due ordering; L6 only waits, supplies current scope and
executes invocations. Due callbacks are consumed once; overload is explicit and
never an automatic replay. L5 Preparation owns two-job admission, same-attempt
non-retry and bounded pre-attachment data. Stale completion cannot take a successor's
buffer. Replaced buffers release their old byte budget before accepting new data.

L6 still owns JoinSets, scope projections and lifetime fences because it composes
lifecycle and worker effects. Those checks authenticate inputs/results; they do not
select a second offline, retry, reload or timer policy. Preparation catches an
unwind at its owned job boundary and reports compile failure without retrying a
panicked job. Initial failed preparation does not retry on every frame; a new
session/model attempt or explicit attachment is required. File watch/reload of an
existing worker is an explicit configured trigger. Broader GUI recovery controls
remain M3 work.

### Scenario walk (sixth M0 item)

| Scenario | Owner/input → ordered result | Failure outcome and evidence |
| --- | --- | --- |
| Connect and status | L3 admits a generation → L2 accepts/replaces → L6 projects scope → L5 callback emits opaque outputs | Old generation rejected; ACK owner belongs to L1. `runtime.rs`, `runtime_scripts.rs`, `runtime_mqtt.rs` integration suites |
| Consumer command, no response | L7 sends captured session/script generation through AppHandle → L5 admits a sequence or rejects → L3 reports write result | Admission, execution, write delivery and appliance ACK remain distinct. Timeout/Unknown is not success and is not retried automatically. `management.rs`, `mqtt_commands` tests |
| Reconnect and late close | L3 registry publishes the new generation → L2 closes only the superseded target → L5 old binding retires | Old callbacks, timers, closes and downlinks cannot affect the successor. `scripts.rs`, `runtime_scripts.rs`, L3 transport/MQTT tests |
| Reload failure or panic | L5 compiles before replacement; successful replacement creates a fresh generation and fences old work | Compile failure keeps old scope. Execution fault remains faulted until explicit reload; no retry/restart loop. `runtime_reload.rs`, L5 worker/host tests |
| Sink overload or absent sink | L5 emits ordered opaque outputs → L6 dispatches to the configured sink | Failed dispatch stops the remaining prefix and reports health; no prefix replay. A local observation sink can succeed without claiming broker delivery. `runtime_scripts.rs`, `runtime_mqtt.rs` |
| Forget succeeds or fails | L6 quiesces captured registration → L2 requests close/deregister/persist stages → confirmed receipts advance L2 | Unconfirmed removal keeps ownership; failed persistence never emits Removed. Delayed ACK cannot deregister a successor. `runtime_bridge.rs`, `runtime.rs`, `pairing_storage` tests |
| Broadcast loss/slow observer | Subscribe before snapshot; L6 reconciles the authoritative L3 registry and projects a loss event | Adapter clients resynchronize snapshots, not replay commands. `runtime.rs`, `management.rs` tests |
| Shutdown during work | Daemon stops admission/core, joins lifecycle/script effects while output services remain available, then stops adapters/signing | Accepted FS work and worker tails are joined; blocked terminal PUBACK is awaited. `daemon.rs`, `tls_runtime.rs`, worker tests |
| Unknown compatibility profile | L1 chooses baseline ACK/provisioning rules; operator explicitly opts into the observed TLS profile before identity is known | No SNI-based model guess or blanket workaround. L1 ThinQ2 tests and L3 TLS profile tests |
| Future outbound reconnect/pairing composition | L4 will own sockets/reconnect, captured account/session/registration fences and unknown mutation outcomes; L6 persists intent before a remote mutation | No queued appliance-command replay or cleanup ownership erasure. Foundation fixtures test crypto, HTTP mutation non-replay and restart intent; composed transport acceptance remains M2 |

No unresolved state-owner or failure-outcome ambiguity is retained as an M0 blocker
in this review. Remaining appliance/script conformance, cloud composition, tool
migration, rollback and release evidence stay in their respective milestone gates.
Non-inferiority is not asserted for the unfinished complete release.

Closure verification: 269 workspace tests and 51 core app tests passed. All eight
feature combinations and the workspace passed all-target Clippy with warnings
denied; formatting and diff checks passed. Added L5 tests cover ordered budget
retention, duplicate/foreign/late completion, timer scope/limits, non-retry of failed
preparation, successor-buffer protection and global/per-device input budgets.

Snapshots are projections, not an atomic second lifecycle store. Script state is
filtered by the captured session; operation admission rechecks authoritative
scope, so an observer race produces an explicit stale rejection rather than an
operation on a successor. Broader presentation/compatibility acceptance remains M3.
