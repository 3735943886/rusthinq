# rusthinq 0.2 Development Plan

- Status: planning; implementation has not started
- Branch: `dev/0.2`
- Strategy: a new daemon implementation with selective component reuse and staged cutover
- Decisions: [design record](0.2-design.md)
- Proposed structural contracts: [design hardening](0.2-contracts.md)
- Execution and acceptance: [milestones](0.2-milestones.md)

## Goals and Scope

rusthinq remains a standalone daemon. Separate protocol/lifecycle decisions from I/O using
rustuya 0.4 as a design reference, without adopting its no_std, embedded, or public-library
goals. Reuse verified codecs and device compatibility handling. Review existing behavior as
preserve, intentionally change, or retire rather than copying every implementation detail.

External MQTT becomes an optional integration. Device-facing ThinQ2 MQTT remains necessary
transport. GUI and management API must work without an external broker; CLI and MCP reuse
application services and codecs. Consolidate tools after their actual usage is reviewed.

## Implementation Strategy

Build the 0.2 daemon internals afresh rather than progressively reshaping the existing daemon
in place. The current implementation carries architectural choices inherited from rethink
and its Rust port. Treat it as a protocol reference and behavioral comparison baseline, not
as the architecture that the new implementation must preserve.

Write new application ownership, session lifecycle, script-host sink, and adapter wiring.
Selectively reuse verified codecs, framing, TLS compatibility handling, useful GUI assets,
drivers, captures, and tests after reviewing their dependencies. Reuse device knowledge and
necessary external contracts without importing the old callback, global-state, or MQTT-based
ownership structure.

Begin the implementation phase by relocating the complete tracked 0.1 project tree into
`legacy/0.1/`. This includes its source, manifests, assets, tests, configuration examples,
build/deployment scripts, documentation, and project-specific hidden configuration. Keep Git
metadata at the repository root and retain the 0.2 planning documents under root `docs/`.
Do not move local secrets, ignored build output, or other untracked personal files as part of
the tracked-source relocation.

The repository root then becomes the new 0.2 project from its first implementation commit.
Keep the legacy Cargo workspace independent and excluded from the new workspace and default
CI. Record the original 0.1 revision and explicit legacy build/run commands. Adjust only paths
needed to run the relocated reference, documenting those adjustments separately.

Bring code from `legacy/0.1/` into the new tree only when a slice needs it, after reviewing its
responsibility and dependencies. No new crate may depend on legacy by path, include its source,
or call a legacy fallback. Record the source revision/path and verification for reused code.
Compare implementations through capture replay or isolated runs, never simultaneous control
of the same live device. Production readiness remains gated by M5 even though the repository
root targets 0.2 from the start. Remove the legacy tree after the release gates pass; the
original revision remains available in Git. No permanent dual implementation is intended.

## Architecture Overview

```text
Device transport <-> Session runtime <-> Protocol/lifecycle core
                           |
                     Rhai driver host
                           |
               Adapter-neutral driver output sink
                           |
              Application-owned IL state and events
                           |
                  Shared application interface
                    /           |           \
                GUI/API    External MQTT    CLI/MCP via API
```

The protocol core produces protocol events and outbound messages, not semantic appliance
properties. Rhai drivers interpret device data and produce descriptors, values, and events.
The host routes these through an adapter-neutral sink into authoritative application state;
MQTT and GUI consume projections of that state. Driver-local decoding state may remain in
Rhai, but a second independently writable property store must not remain behind MQTT.

The application also owns the device registry, management operations, and persistence
orchestration. Session runtimes own connections and core instances. The embedded device MQTT
broker is runtime-owned; provisioning, firmware, and SNI passthrough remain explicit server
services. Detailed ownership and error contracts belong in the design record.

## First Working Slice

M1 includes one real ThinQ1 script path, not only a raw-packet demonstration:

1. Accept a connection and process protocol messages in the new core/runtime boundary.
2. Feed status to one selected driver from rusthinq-scripts.
3. Publish its IL descriptor, values, and events through the new sink into application state.
4. Serve the existing device-list projection to the GUI and publish through the MQTT adapter.
5. Send one supported command through the shared path and verify its actual result semantics.

The GUI part needs only the existing devlist projection. Verify semantic values in the
application snapshot/test harness and MQTT output; a new GUI property editor is not required.
One implementation owns each migrated device and its outbound actions. Devices outside the validated 0.2 scope
remain on the reference implementation in a separate deployment; the new daemon does not
need an internal bridge back to the old state owners.

## Cross-Repository Contracts

Rhai compatibility is a contract with the separate `rusthinq-scripts` repository. IL model
and message semantics must conform to `ildevice`; MQTT formatting is its separate transport
mapping. Record the exact revisions used by the slice and its fixtures. See design S1–S3
for normative documents, ownership, and compatibility handling for non-IL scripts.

## Delivery Scope

- Preserve panic isolation per device/handler, without adding panic retries or restart supervisors.
- Keep current GUI functionality. Property-value screens/editors are outside the 0.2 baseline.
- Preserve or explicitly migrate MQTT, configuration, persisted state, scripts, and captures.
- Keep MCP as a thin adapter; substantial feature expansion is outside this release.
- Do not require a universal effect interpreter for storage, authentication, or script execution.
- Avoid new device features, a full GUI redesign, and a general plugin system in this migration.

## Tool Direction

These are candidates, not authorized deletions; M4 records usage and replacement decisions.

| Tool | Direction |
| --- | --- |
| packet-parser | Consolidate shared packet encode/decode |
| packet-sender | Consolidate device send/raw inject after reviewing semantics |
| capture | Keep; migrate online access and preserve useful replay fixtures |
| retained-gc | Retirement candidate: retained cleanup belongs to the MQTT adapter; retain only if migration/repair needs justify it |
| lgcloud-monitor | Keep unique development functionality, consolidate duplication |
| rusthinq-mcp | Keep entry point, use management API and shared codecs |
| setup / script-test | Review separately according to purpose |

M0 reviews ownership, dependencies, execution ordering, failure semantics, and LG compatibility
boundaries before legacy relocation and implementation. The contracts document contains concrete
proposals and explicitly identifies intentional behavior changes requiring review. Full tool
inventories and nonstructural implementation details remain in their respective milestones.
