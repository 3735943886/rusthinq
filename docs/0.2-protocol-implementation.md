<a id="l1-implementation-implemented-boundary"></a>
### Implemented boundary

`thinq1::Session` consumes bytes, tick, or end-of-stream plus caller-supplied
monotonic elapsed time. It returns ordered actions, an explicit terminal error,
and the next deadline. No sockets, TLS, clocks, Tokio, application state, or IL
are present. A runtime must execute actions in order and close on an error.
Actions preceding an invalid later frame in the same chunk remain valid.
An end-of-stream closes the model, with truncation reported for incomplete frames.

Incoming retained bytes never exceed one bounded payload plus its four-byte
header. Actions scale with the caller's input chunk; L3 must bound read chunks
and its outbound queues. The model does not implement a runtime queue.
Every original valid JSON payload is emitted verbatim, retaining unknown fields.
Response bodies are observed, never interpreted as arbitrary command completion.
The caller supplies the payload bound and timeout (the reference uses 1,000,000
bytes and 90 seconds). Input at the deadline expires the session before processing.

<a id="l1-implementation-thinq2-boundary"></a>
### ThinQ2 boundary

`thinq2::Session` consumes a device topic/JSON payload with a caller-supplied
outbound message ID, a cloud payload, or end-of-stream plus monotonic elapsed time.
It retains one bounded deploy envelope and session identity, not a process-wide
device registry. Outcomes expose ordered actions, errors, and whether the session
is closed. No deadline is invented: MQTT keepalive belongs to L3's broker.

Provisioning requests produce a `Provision` action for L3's response service;
each request carries an operation ID. L3 reports `ProvisionResult` only after the
response is sent or definitively failed. A matching send success plus the device
completion produces a single `Ready` event carrying the original deploy metadata.
Early completion is latched; stale/duplicate results are ignored. A failed send
closes the session. Repeated deploy replaces the pending operation. Device packets
before send success return nonterminal Busy without buffering or ACK; L3 must
report send completion before dispatching subsequent device packets.
`device_packet` produces decoded bytes and the original cloud-bound CLIP payload.
Local AABB ACKs precede data events, use uppercase hex and the injected outbound
ID, and are sent under `cmd=ack`, not `cmd=packet`. Bridged sessions generate no
local ACK; incoming cloud messages retain their original bytes, ID, and unknown
fields. Unknown device commands remain opaque cloud-bound messages. A timesync
request is an action for L3 to answer from its wall clock, not a clock read in L1.

Cloud input rejection never faults a healthy local device. Malformed device input,
topic/identity mismatches, data before provisioning, and backwards time are terminal
with explicit errors. Topics and payloads are bounded before copying/parsing.

ACK ownership follows explicit `BridgeState { generation, active }` inputs.
Generation starts at 1 and each bridge disconnect, reconnect, or enable/disable
must advance it. Stale/equal updates return a nonterminal StaleBridge error.
Device identity and provisioning remain intact during bridge transitions.

Cloud input carries its originating connection generation; old input is rejected
even after the bridge is re-enabled. Cloud-origin Send actions and cloud-bound
outputs carry the same generation. Local cloud-bound outputs carry None and must
never be replayed to a later bridge. L3/L4 must check `accepts_bridge_generation`
before starting queued cloud writes or relays and discard stale items. Transport
callbacks must retain their original generation, not read the latest generation
at delivery time. No old connection's buffered input may be relabeled as new.

A partial write that started before a transition is an unknown outcome: the
runtime must finish it or close that transport, never restart or replay it.
These are protocol decisions and runtime contracts; actual queue fencing and
connection cancellation still require L3/L4 integration tests. A frame already
sent to the device cannot be undone by changing generations.

<a id="l1-implementation-additional-behavior-changes"></a>
#### Additional behavior changes

- ACK policy is now L1-owned rather than script-owned, as specified by the L1
  contract. No script `auto_ack` setting is imported.
- First-packet provisioning fallback is restricted to the observed model rather
  than applied to all models. Unknown models use explicit completion.
- Invalid device JSON, identity/topic mismatches, malformed hex, or pre-provision
  data now have explicit terminal outcomes instead of silent drops.
- Topic normalization recognizes `/clip/` boundaries, not arbitrary substrings
  like `/clipwrong/`. Device IDs containing MQTT delimiters/wildcards are rejected.
- Rejected cloud input returns an error without closing the device session.

## L2 lifecycle foundation

> Implementation record: progress paragraphs and test totals below belong to their
> recorded checkpoints. For current acceptance use [milestones](0.2-validation.md#milestones);
> for configuration use [runtime](0.2-runtime.md#runtime) and [operations](0.2-operations.md).

`rusthinq-lifecycle` is a new independent workspace crate with no dependencies.
It does not use the L1 crate or legacy source. `Model` loads a supplied ledger,
consumes lifecycle inputs with monotonic elapsed time, and returns ordered
actions, an explicit error, and the earliest offline deadline. L6 will run it and
execute its effects. No clocks, files, sockets, threads, waits, or executors are
present in the model.


<a id="l2-implementation-session-and-availability-decisions"></a>
### Session and availability decisions

Each device has a persistent incarnation and generation high-water mark. New
generations replace the current session and emit a close effect targeting the
old session. Stale down events must match both incarnation and generation and
otherwise do nothing. An equal/older session-up is rejected. The runtime must
assign generations greater than the loaded ledger's high-water mark; a counter
resetting to zero at process startup is not compatible with this contract.

A matching down event clears the usable session immediately and schedules the
offline report after the configured grace. Reconnection before expiry cancels
the deadline without an offline/online transition. At the exact deadline, offline
is emitted before processing the incoming event. Zero grace reports offline in
the same input. Loaded devices start offline without sessions. Backwards time
returns an error without mutating state; counters are checked for overflow.

The ledger retains the next-incarnation high-water mark even when empty, so a
forgotten identity can later register with a new incarnation. Live snapshots
include current session, reported online state, grace deadline, and removal
progress; ledger snapshots contain only persistent identity/generation data.


<a id="l2-implementation-forget-sequence-and-results"></a>
### Forget sequence and results

Forget immediately quiesces the device: clears its usable session, cancels grace,
and reports offline. It then emits correlated effects in this order:

1. Close the captured session (or perform an idempotent close when already offline).
2. Deregister from LG only if the initial forget request captured an active bridge.
3. Persist a removal ledger.
4. Emit Removed only after the matching persistence success result.

Results must match device ID, incarnation, operation ID, and step. Duplicate,
late, wrong-step, and previous-incarnation results are ignored. Every step has
a distinct failure event and a visible failed state; the device stays quiesced.
No timer retries it. A new explicit forget request retries only the failed step
with a fresh operation ID and the original bridge choice. An overlapping request
returns Busy. New sessions for a quiesced device are rejected and receive a close
effect targeted to their generation. Other devices continue normally.


<a id="l2-implementation-persistence-contract-for-l6"></a>
### Persistence contract for L6

Storage effects have one model-owned in-flight slot. Registration/replacement
marks the ledger dirty; updates arriving during a write coalesce into one dirty
flag. Pending removals remain in per-device state and dispatch by operation order,
with priority over a general dirty snapshot. Snapshots are constructed only when
dispatched. A removal snapshot excludes only its own target, retaining other
pending or failed removals. A matching result frees the slot; unissued, stale,
and duplicate results cannot advance the sequence.

After a failed removal write, a later ordinary snapshot includes the failed
quiesced device. Another device's update cannot silently confirm that removal.
After a successful removal, subsequent snapshots exclude the removed device.
Failures never trigger automatic retries; a new explicit forget request retries
its failed step. Ordinary write failures do not roll back live sessions.

L6 must execute emitted storage effects once, use atomic replacement, and report
completion only when no write for that effect is still in flight. An unknown
outcome may still differ from live state until a later successful write. The
model bounds pending storage correlation to one slot plus one dirty flag; no
per-update queue or growing set of pending revisions remains.

Quiescence before the storage step is live state only. Restart restores the last
successfully written ledger, not an unfinished close/deregistration operation.
Crash recovery of unfinished forget operations and migration from 0.1's storage
format remain L6/M2a work, rather than an implied guarantee of this model.


<a id="l2-implementation-verification-and-scope"></a>
### Verification and scope

L6 now provides [durable lifecycle storage](0.2-runtime-implementation.md#l6-implementation) and correlated
execution of PersistLedger/PersistRemoval effects. The L6 runtime now connects real
ThinQ1 Up/Down events, replacement, grace timers and ordinary ledger persistence.
Local ThinQ1 Forget now waits for transport completion and durable removal.
Bridge/script execution and the complete daemon remain pending.

Eleven deterministic sequence tests cover session replacement and late close,
offline grace and exact deadlines, local/bridged forget ordering, every failure
and explicit retry, result correlation, independent-device progress, ledger load
and write failure, incarnation reuse protection, serialized concurrent removal snapshots, coalesced updates, unissued results,
invalid ledgers, and counter/time errors. All workspace tests, formatting, and

L2 is a new implementation of the L2 contract in the [structural contracts](0.2-architecture.md#contracts). No code was
copied from legacy. The contract's explicit quiescence, conditional deregistration,

is not claimed to be preserved. Storage and ThinQ1 runtime ownership are implemented;
real appliance validation remains pending. M0/M1/M2a remain incomplete.

## L3 implementation — Server foundations

> Implementation record: progress paragraphs and test totals below belong to their

> for configuration use [runtime](0.2-runtime.md#runtime) and [operations](0.2-operations.md).

`rusthinq-server` depends on L1, Tokio, serde_json, OpenSSL, and tokio-openssl,
plus HTTP dependencies listed in [the provisioning implementation](0.2-protocol-implementation.md#l3-provisioning).
It owns one task per admitted transport, including unidentified peers.
`Server::admit` accepts an established `AsyncRead + AsyncWrite` transport; the
new `tls::FrontDoor` routes and handshakes TCP peers before handing local TLS
streams to this same session path. There is no legacy dependency or copied
runtime code. Building L3 now requires the system OpenSSL development library. The reviewed ThinQ1 runtime reference is
`legacy/0.1/crates/rusthinq-cloud/src/thinq1/connection.rs` at
`99c48ccc33bfc602626e0b9151b98de442185c2f`.


<a id="l3-implementation-implemented-behavior"></a>
### Implemented behavior

- Bounded read chunks feed L1 using monotonic elapsed time. Protocol actions execute
  in order, including ACK write/flush before the associated data event. Earlier
  valid actions survive a later malformed frame in the same read.
- A connection receives a checked global generation at admission. Construction
  takes the lifecycle ledger's generation floor; restarting from zero is not an
  acceptable application integration. A newer identified connection replaces the
  old transport. Old tasks cannot publish subsequent events or remove the new entry.
  Generation history also fences older delayed handshakes after the newer session
  has closed. History is pruned when no older admitted connection can use it.
- `ServerHandle` exposes generation-tagged events, a current-session snapshot,
  nonblocking bounded `send`, and generation-targeted `close`. No lifecycle grace,
  device registry, persistent identity, bridge, script, or IL state is owned here.
- Commands are JSON payloads, bounded before framing. Queue admission returns a
  receipt or explicit rejection/busy. A receipt reports `Sent` after full frame
  write and flush, `Failed` after a known zero-byte failure or queued cancellation,
  and `Unknown` after a partial write or lost task completion. `Sent` does not
  mean device acknowledgement. Response events remain observations for drivers.
- Write timeout or failure closes only that session. Interrupted frames are never
  retried. Fair read/command selection prevents command traffic from starving reads.
- Close immediately removes the usable session and signals transport cancellation
  through a separate watch channel. Its Down event reports unavailability, not a
  joined-task completion. L6's correlated close-result integration is still pending.
- Shutdown stops admission, signals every task independently of outbound capacity,
  and joins them. Dropping the owner cancels tasks; callers requiring joined cleanup
  use `shutdown`. Task panics run ownership cleanup and do not restart the device.
- Events use a bounded broadcast ring: slow subscribers receive explicit `Lagged`
  errors and must resnapshot. Previously queued events retain their original
  generation. L6 must fence consumption and implement its snapshot/change handoff.

Concurrent transports and retained identity history are each capped by
`max_connections`. A slow unidentified peer may pin history; when that bound is
full a new identity is closed instead of allocating unlimited tombstones. Idle
expiration eventually releases that peer. Admission capacity includes finished
tasks until the next admission reaps them. Payload/read/queue capacities and
inactivity/write timeouts are constructor inputs.

<a id="l3-implementation-tlssni-front-door"></a>
### TLS/SNI front door

`FrontDoor` owns the TCP listener, bounded pending handshake/passthrough tasks,
and the supplied session server. It routes served names to prebuilt per-name
OpenSSL acceptors. Caller-supplied chains/keys are checked at construction for
matching keys and an exact served DNS SAN. Names are case-insensitive; wildcards
and IP literals are not supported. No CA or certificate is created from peer
input. Missing SNI is refused unless a served default is explicitly configured.
Unknown names are refused without a passthrough hook. The L4 hook receives the
normalized name and the original TLS byte stream, and owns destination policy
and outbound dialing; L3 creates no outbound connection itself.

ClientHello interpretation lives in the pure L1 `client_hello` module. The parser
checks nested lengths and duplicate extensions/names, handles handshake headers
and bodies fragmented across TLS records, and distinguishes incomplete input,
malformed input, and exceeded bounds. Routing buffers are capped (64 KiB default),
with one timeout spanning initial input and the local TLS handshake. Bytes read
for routing are replayed exactly once to TLS or passthrough; the prefix allocation
is released when consumed. This is a buffered peek, preserving bytes visible to
the next consumer rather than relying on a single socket peek. Format references:
[RFC 8446 ClientHello](https://www.rfc-editor.org/rfc/rfc8446#section-4.1.2) and
[RFC 6066 server_name](https://www.rfc-editor.org/rfc/rfc6066#section-3).

The pending-task cap covers both uncompleted handshakes and active passthroughs;
local sessions have the separate runtime cap. Rejections use a bounded broadcast
channel with peer and reason; slow consumers see `Lagged`. Shutdown drops the
listener, cancels and joins pending work/relays, then closes and joins local
sessions. A peer/hook panic is reported and contained without a restart.


<a id="l3-implementation-tls-policy-and-provenance"></a>
#### TLS policy and provenance

The baseline requires TLS 1.2 or newer with OpenSSL's intermediate-v5 suites.
L1 exposes an explicit `lg_compat::TlsPolicy::RtkRtl8711am` profile (LG-005).
Only that profile permits TLS 1.0, `DEFAULT:@SECLEVEL=0` CBC suites, server cipher
preference, and disabled tickets. SNI does not identify a device module, so the
caller must choose the observed profile for the configured served name/listener.
No client certificate is requested, preserving the reviewed listener behavior.

Reference snapshot: `99c48ccc33bfc602626e0b9151b98de442185c2f`.
Reviewed paths:

- `legacy/0.1/crates/rusthinq-cloud/src/certs.rs`: device acceptor options,
  RTK_RTL8711am behavior (upstream PR #131), certificate chains and ticket policy.
- `legacy/0.1/crates/rusthinq-cloud/src/thinq2/sni_passthrough.rs`: front-door
  routing and its synthetic ClientHello builder. The builder's comment labels it
  captured, but it constructs bytes; the new tests do not claim it is a capture.

Model evidence is the RTK_RTL8711am module name; firmware is unrecorded. A synthetic
TLS 1.0/AES128-SHA client is the new LG-005 fixture, not a real-device validation.
TLS options are selectively adapted; the router/parser/task ownership are new.
Intentional changes from the reference: unrecognized/malformed names are refused
without L4, fragmented input is awaited within bounds, served certificates are
preconfigured, and legacy TLS is explicitly selected rather than globally applied.
Dynamic CA-signed leaf minting and the old cache-full default-certificate fallback
are not imported.

<a id="l3-mqtt"></a>
## L3 — Local ThinQ2 MQTT foundation

> Implementation record: progress paragraphs and test totals below belong to their
> recorded checkpoints. For current acceptance use [milestones](0.2-validation.md#milestones);
> for configuration use [runtime](0.2-runtime.md#runtime) and [operations](0.2-operations.md).

L6 mixed script routing uses `Handle::shares_registry` to verify the exact shared
registry before selecting ThinQ1/MQTT codecs by captured session protocol. Script
device downlinks use existing non-retained MQTT publishes; this does not implement
an external retained publication sink. Binary callback input can be encoded as hex
without changing L1 framing or ACK behavior.

L6 now connects this broker to lifecycle, durable storage and automatic generation
refill through `Runtime::new_mqtt`; see [runtime integration](0.2-runtime-implementation.md#l6-implementation).
Generation-targeted close completion tracks redeploy on the same physical stream.
The caller/front door still owns and joins broker transport tasks.

`Broker::sharing` can now reuse ThinQ1's registry, generation allocator, aggregate
connection limit and shutdown signal for one mixed L6 owner. Send operations
reject sessions of the other protocol; snapshot/close/allocator operations span
the shared registry. See the mixed harness and shutdown contract in L6 docs.

The pure L1 `mqtt` module supplies bounded MQTT framing and device packet codecs.
L3 `mqtt::Broker` implements `tls::LocalService`, so the existing TLS/SNI front door
owns MQTT connection tasks, cancellation, and joins. `Broker::run` also accepts
caller-owned generic transports for replay/integration testing. This service
uses no external MQTT broker and interprets no IL. L3 adds chrono for UTC and
base64 for the reviewed timesync wire format; L1 retains only serde_json.


<a id="l3-mqtt-supported-device-connection-path"></a>
### Supported device connection path

- MQTT 3.1.1 CONNECT with a clean session and optional empty client ID, with optional
  username/password fields parsed but not authenticated (matching the reference).
- SUBSCRIBE/UNSUBSCRIBE with correlated SUBACK/UNSUBACK; at most sixteen filters
  per connection, each at most 1024 bytes. Valid `+` and trailing `#` filters match
  only outputs to that same device; this is not a cross-device MQTT fanout broker.
  SUBACK always grants QoS 0. PINGREQ/PINGRESP and clean DISCONNECT are supported.
- QoS 0/1/2 incoming publish, including DUP. QoS1 PUBACK retains its packet ID;
  QoS2 uses PUBREC/PUBREL/PUBCOMP and dispatches only on release.
  Device-facing outputs are QoS 0, non-retained. Malformed flags/lengths/IDs/UTF-8,
  unknown packet types, and unsupported features close that connection.
- MQTT packet allocation is bounded before reading the declared body. The frame
  cap is the configured CLIP payload limit plus 4096 bytes of envelope allowance;
  CLIP input/output payloads retain the stricter payload limit. Packet reads stay
  alive across outbound selection, so a partially read header/body is not lost.
- Complete received packets refresh the broker deadline. A nonzero CONNECT
  keepalive uses the maximum of 1.5 times the declared interval, 300 seconds,
  and the configured inactivity timeout. Zero keepalive uses the same grace floor.
  Before CONNECT the configured timeout applies (90 seconds by default).
  Partial-byte traffic and outbound writes do not refresh the receive deadline.
  Format reference: [MQTT 3.1.1](https://docs.oasis-open.org/mqtt/mqtt/v3.1.1/os/mqtt-v3.1.1-os.html).


<a id="l3-mqtt-thinq2-execution-and-readiness"></a>
### ThinQ2 execution and readiness

Each connection runs its own L1 ThinQ2 session with bridging disabled. Device
MQTT publishes feed topic/payload and an injected outbound message ID to L1.
A deploy action claims a bounded, generation-fenced transport identity before
writing its response, replacing and closing any old connection. The new entry
is pending: it is absent from the public snapshot and cannot receive application
commands. Replacement reports the old session down immediately. A delayed older
deploy is rejected even if the newer transport has since closed; the shared
runtime's bounded generation history protects that transition.

The response preserves the reviewed `completeProvisioning` fields, `type: 0`,
`host: message`, message/provisioning publication topics, provisioningType, and
600-second deployInterval. It is sent only when the connection subscribed to the
applicable `lime/devices/{did}` topic. Full write/flush success is reported to L1
with the matching operation ID before another device packet is dispatched.
Absent subscription, encoding bounds, or write failure report provisioning failure
and close the pending transport. No failed/pending provisioning is published as Up.

Only L1 Ready makes the session usable and emits ordered Up and Ready events with
the original deploy metadata. Explicit completion and LG-002's observed-model
first-packet fallback stay L1-owned. Repeated deploy on the same transport
allocates a new logical generation and stays pending until completion, preserving
the transport and subscriptions. See the reprovisioning section below.

Timesync actions use an injected L3 clock. The default reads UTC and milliseconds
since Unix epoch. The response preserves `resp_timesync`, `type: 1`, and the seven
base64-encoded bytes: year modulo 100, zero-based month, day, hour, minute, second,
and Sunday-based weekday. Fixed clocks make the integration tests reproducible.
Clock errors fail the connection; clock panics are contained by the owned task.

L1 local ACK actions are written before Data and CloudBound events. Binary data
and original unknown CLIP fields remain opaque. CloudBound is a local-only
observation: it must not be queued/replayed to a subsequently enabled LG bridge.
There is no bridge input API, cloud-origin send queue, bridge-generation update,
or LG connection in this implementation. L1's bridge contracts are unchanged,
and their L3/L4 runtime enforcement remains pending.


<a id="l3-mqtt-runtime-ownership-and-handles"></a>
### Runtime ownership and handles

`mqtt::Handle` exposes ready-session snapshots, generation-tagged bounded broadcast
events, targeted close, and bounded nonblocking command admission. Queued receipts
report Sent after write/flush, Failed for unsent cancellation or missing subscription,
and Unknown for partial writes/lost completion. None implies a device ACK.
Subscribe changes cannot redirect another device's frames to this connection.
Queued work is never retried. Slow event consumers receive Lagged and must recover
through a snapshot/generation fence above L3.

The service reuses the ThinQ1 runtime's generation-history/cleanup guard and entry
representation, with a readiness bit for pending MQTT provisioning. ThinQ1
behavior remains unchanged. `Broker::stop` marks admission stopped and signals
all connections independently of queue capacity; their caller/front door owns
joining them. Front-door shutdown cancels and joins all MQTT TLS tasks before
returning. Independent MQTT replay callers must likewise stop and join owned tasks.
Connection and generation bounds are checked; caller-supplied generation floors
must respect the loaded lifecycle ledger. Unified generation allocation and
ownership when composing ThinQ1 and ThinQ2 with L6 are still integration work;
standalone independent brokers must not be wired to one lifecycle identity store
with colliding/reset counters.


<a id="l3-mqtt-deliberate-limits-and-changes"></a>
### Deliberate limits and changes

This is a local device transport foundation, not a complete general MQTT broker.
Retained input/store/replay and persistent sessions
are explicitly unsupported and close the peer. Outbound QoS 1/2 and broker-to-broker relay are
absent. The legacy appliance-tested five-minute keepalive minimum is preserved;
a larger declared or configured interval extends it.
The MQTT client ID is parsed but does not own replacement: validated ThinQ2
identity owns device-session replacement, as in the reviewed reference.
Additional capabilities require device evidence/replay fixtures and tests before
expanding the supported subset. No real-appliance compatibility is claimed.

<a id="l3-mqtt-qos1-retransmission-compatibility"></a>
### QoS1 retransmission compatibility

QoS1 PUBLISH with DUP is now admitted instead of disconnecting the session.
Both first-seen DUP and retransmissions get PUBACK and enter the same L1 path as
fresh messages. This preserves the reference broker's at-least-once ingress;
packet IDs are reusable after acknowledgement and do not establish CLIP command
identity. Repeated opaque traffic is forwarded for every arrival. No MQTT-level
exactly-once promise or application deduplication is introduced. Existing L1
state checks still apply. Same-transport redeploy now gets a fresh logical generation.

Reference: the fixed 0.1 `mqtt_broker.rs` Publish handler acknowledges and forwards
incoming QoS1 regardless of DUP. New tests cover first-seen DUP, repeated payload,
packet-ID reuse with new payload, PUBACK for each arrival, subsequent PING, stable
session identity, and clean shutdown. Pure codec tests reject zero IDs and QoS0
DUP. These are synthetic tests, not appliance captures.


<a id="l3-mqtt-same-transport-reprovisioning"></a>
### Same-transport reprovisioning

Repeated deploy/preDeploy uses the existing MQTT transport and subscriptions.
The runtime allocates a fresh registry generation, removes the prior ready entry,
reports its Down, and admits the replacement as pending. Queued old-generation
commands fail rather than being replayed into the replacement. Old send/close
handles become stale. Once the provision response is written and L1 accepts
completion, the new identity publishes Up/Ready. Pending redeploy can itself be
replaced without disconnecting, and generation exhaustion remains terminal.

The fixed reference `thinq2/device.rs` replaces deploy metadata and sends a new
response for each deploy/preDeploy. New transport tests exercise ready-to-pending
replacement, a second pending deploy, stale handles, new-generation sends, and
shutdown. Internal write-result operation correlation is preserved by L1.
Device completion ACKs do not carry enforced operation correlation in this slice;
an indistinguishable delayed completion ACK can still satisfy the current pending
operation, as in the existing protocol path. No stronger wire-level correlation
is claimed. Cloud/bridge generations remain a separate integration requirement.


<a id="l3-mqtt-empty-clean-session-client-ids"></a>
### Empty clean-session client IDs

The broker now accepts an empty MQTT client ID for clean sessions. Its transport
admission generation distinguishes connections, and validated ThinQ2 `did`
continues to own device identity/replacement. Two empty-ID clients can provision
separate devices and receive isolated outbound traffic; neither replaces the
other merely because their MQTT IDs match. No persistent session or client-ID
recovery is implied. Non-clean CONNECT is still explicitly unsupported.

The fixed reference `mqtt_broker.rs::decode_connect` skips the client ID and
accepts empty values. A pure codec test covers empty clean versus unsupported
non-clean CONNECT; a runtime test provisions two distinct devices with empty
IDs, verifies targeted commands on both, and joins shutdown. Fixtures are
synthetic and do not establish real-device compatibility for other CONNECT flags.


<a id="l3-mqtt-last-will-ingress-and-observations"></a>
### Last Will ingress and observations

CONNECT now accepts a bounded Will topic and binary payload, validating QoS and
retain flags before consuming authentication fields. Nonempty wildcard-free topics
are required; QoS 0/1/2 metadata is preserved (this does not implement downstream QoS2
Will delivery). On EOF, transport/protocol failure or idle expiry, a current connection
emits Event::Will before Down. The event carries its admission generation, optional
validated device session, and original topic/payload/QoS/retain. Pre-provisioning
connections can therefore report Will without inventing a device identity.

Normal MQTT DISCONNECT suppresses Will. Application close, broker stop, replaced
sessions and front-door cancellation suppress it as intentional administrative
shutdown. This improves the reference broker's unconditional cleanup publication,
which also published on clean disconnect. No Will is synthesized on panic or
aborted futures. Current-generation checks and event emission share the registry
lock so late failures cannot publish a replaced session's Will.

This is an observation interface for future application/broker publication.
Subscriber fanout, retained storage/replay and Will delivery QoS handshakes remain
unimplemented, so complete Will feature parity is still an open acceptance gate.
Tests cover binary payload and flag validation, first connection EOF observation,
clean-disconnect suppression and administrative shutdown suppression. No actual
appliance Will fixture or downstream delivery is claimed.


<a id="l3-mqtt-qos2-ingress"></a>
### QoS2 ingress

QoS2 PUBLISH is stored per connection and acknowledged with PUBREC. Retransmission
with the same packet ID/topic/payload repeats PUBREC without running L1. A changed
payload under an outstanding ID is rejected. PUBREL removes the stored packet,
processes it once, and sends PUBCOMP before executing protocol actions. Repeated
or unknown PUBREL sends PUBCOMP without processing again. Packet identifiers are
reusable after completion. All operations stay inside the owned connection task.

Outstanding records are bounded by configured outbound_capacity; each payload is
bounded by max_payload. Capacity/payload violations close only that connection.
Records carry their admission generation so releases from an earlier logical
session do not dispatch into a redeployed device. Pending records expire with
connection closure; this is clean-session ingress, not durable exactly-once across
reconnect, downstream QoS2, or persistent MQTT sessions.

The reference `mqtt_broker.rs` PUBACKs all positive incoming QoS values, including
QoS2; this incomplete exchange is intentionally corrected. Synthetic codec tests
validate PUBLISH/PUBREL flags and IDs. Runtime tests cover delayed dispatch,
retransmission, repeated release, ID reuse, and bounded outstanding storage.


<a id="l3-mqtt-retained-ownership-and-deletion-foundation"></a>
### Retained ownership and deletion foundation

`retained::Store` requires an explicit owner for every topic, prevents ownership
collisions, and bounds records and logical owner/topic/payload bytes. Replacement
admission is atomic. Empty payload deletes rather than remaining replayable.
Individual removal, remove_owner, and clear return exact-topic tombstone manifests;
an empty put for an unknown topic still yields a tombstone to clean remote state
that outlived process memory. Wildcard replay is owner-scoped and deduplicated.

Tombstone::frame encodes a zero-payload RETAIN=1 PUBLISH. The caller owns reliable
remote delivery and must persist retry inventory before enabling retained remote
publication. This module emits no network messages and does not yet enable retained
broker ingress/fanout or external MQTT. Four pure tests verify cleanup routes,
remote tombstone bytes, empty deletion, owner isolation, and bounded atomic updates.


<a id="l3-mqtt-recoverable-retained-cleanup-ledger"></a>
### Recoverable retained cleanup ledger

`retained::Cleanup` atomically admits bounded tombstone batches and allocates a
fresh attempt token for each send/retry. Failed/unknown results retain work;
only matching broker-confirmed completion removes it. Replacement, retry, and
recovery invalidate older results. Empty-payload remote deletion remains explicit.
Checkpoints contain a schema version, token high-water mark, and owner/topic work
inventory. Restore rejects malformed, oversized, duplicate, and invalid-topic
records; interrupted attempts are never resumed as confirmed.

This ledger is pure. L6 must durably commit admission and token checkpoints before
remote sends, and commit completion afterward. A failed completion checkpoint can
safely replay deletion after restart. It does not own atomic file writes or validate
that a caller's boolean actually represents broker acknowledgement. Remote retained
publication now goes through L6 durable ownership and correlated PUBACK; the device
broker still does not accept retained ingress/fanout. Three tests cover failure/retry/late results, restart token fencing,
and atomic capacity/recovery rejection.

L6 checkpoint file ownership is now implemented in
[application foundation](0.2-runtime-implementation.md#l6-implementation), including commit-before-send
and recovery fencing. Remote publishing and acknowledgement wiring remain pending.


<a id="l3-mqtt-thinq2-bridge-control-and-cloud-origin-ingress"></a>
### ThinQ2 bridge control and cloud-origin ingress

Handle::bridge_state targets an exact ready SessionId and a strictly increasing
bridge generation (L1 starts at 1, so the first live transition must exceed 1). Its receipt Sent means the connection actor applied the state,
not an MQTT wire write. Handle::cloud validates matching CLIP did and payload
bounds, queues a captured bridge generation, and dispatches through L1 Cloud.
Stale/disabled cloud messages return Failed without closing healthy local sessions;
wrong device IDs are rejected before queue admission. Control/cloud inputs use a
bounded queue separate from local commands. Partial device packet reads survive
control processing. No retained publication is added.

The actor serializes transition and writes: old writes already started may complete
before a queued disable is applied. After the disable receipt, no older generation
can start a cloud write. This is not an immediate interrupt of a partial TLS write;
shutdown cancellation and existing write timeout still bound such work. Failed
partial writes report Unknown and close without replay. Shutdown explicitly fails
unsent bridge work. Redeploy disables inherited bridge ACK ownership and advances
its bridge generation; adapters must issue a newer generation to reactivate it.

Active device data emits BridgedCloudBound(session, bridge_generation, raw_payload)
so upstream adapters can fence delayed relay work. Local-only CloudBound remains
unchanged. BridgeChanged observations carry the target session. L6 fences both new
event variants like existing session events. Local CLIP ACKs are suppressed during
active bridging and resume after disable; MQTT PUBACK/PUBREC remain transport-owned.
Synthetic integration evidence covers exact downlink bytes, actual AABB status ACK
suppression/resumption, generation rejection, wrong did rejection, and a usable
PING path after rejected cloud messages. Real cloud registration, automatic bridge
state wiring, reconnect/backoff and authenticated outbound transport remain pending.

Cloud ingress preserves the LG-003 single trailing NUL during validation and
byte relay; the integration downlink fixture includes it. Redeploy also emits
BridgeChanged for the new pending session with its advanced disabled generation
so a controller can allocate a newer activation without guessing a reset floor.

## L3 — Certificate and ThinQ2 HTTPS provisioning foundation

> Implementation record: progress paragraphs and test totals below belong to their
> recorded checkpoints. For current acceptance use [milestones](0.2-validation.md#milestones);
> for configuration use [runtime](0.2-runtime.md#runtime) and [operations](0.2-operations.md).

This extends [the L3 runtime](0.2-protocol-implementation.md#l3-implementation) with caller-owned CA
material, a bounded signing worker, and real HTTPS routes. It adds Hyper HTTP/1,
hyper-util, http-body-util, and percent-encoding to `rusthinq-server`;
no application, lifecycle, MQTT adapter, or legacy dependency is introduced.


<a id="l3-provisioning-certificate-material-and-execution"></a>
### Certificate material and execution

`certificates::Authority::load/from_pem` loads exactly the supplied certificate
and key. It checks key matching and verifies a probe chain using that issuer,
including validity, CA suitability, and self-signature checking. Parse errors,
expired/unsuitable material, and mismatched keys fail startup. No existing key or
certificate is replaced as a side effect. `generate` is a separate explicit
startup operation: validated DNS name, caller-selected RSA 2048/3072/4096, random
serial, SHA-256 signature, CA constraints/key usages, and 3650-day validity.
Private-key and CA persistence are the caller's responsibility; no new storage
format, file overwrite, or automatic CA migration is implemented.

`server_identity` builds an ECDSA P-256 server leaf (as 0.1's rcgen leaves) for a name and
returns a leaf-plus-CA chain suitable for `tls::Identity`. Its subject is distinct
from the issuer even when both names match; server-auth/key-usage/SAN extensions
are supplied. This is startup issuance, not dynamic certificate creation from
arbitrary SNI names. The existing TLS compatibility policy remains explicit.

`Signer::new` returns an owner and cloneable `SigningHandle`. The owner runs in a
caller-owned task. Requests use a nonblocking bounded queue (32 by default),
with four concurrent blocking signing tasks and a 16 KiB CSR limit. Device IDs
are bounded to 256 bytes and cannot contain MQTT path/wildcard/NUL delimiters.
Native signing is run outside I/O loops and guarded against panics. CSR public
keys over 8192 bits or invalid proof-of-possession signatures are rejected.
Only subject and public key are copied; requested extensions, including SAN and
CA constraints, are dropped. Certificates have random serials and 3650-day
validity, and signing failures never substitute the CA certificate.

Successful results are cached for the exact device ID and a SHA-256 digest of
CSR bytes. The cache holds at most 128 entries, expires after 60 seconds, and
evicts the oldest entry when full. Sequential identical requests reuse the same
certificate. Simultaneous duplicate requests and saturated concurrency return
Busy rather than accumulating unbounded waiter lists. Invalid results are not
cached. These limits are configurable within the documented constructor bounds.

On explicit stop or stop-sender disappearance, queued requests receive Stopped.
Started native signing is joined and its result reported; HTTP cancellation does
not detach, cancel, retry, or duplicate native work. The composition root must
signal and await the signing owner, rather than abort its future: already-running
blocking OpenSSL work cannot be forcibly cancelled. There is no signing retry or
restart supervisor.


<a id="l3-provisioning-https-routes"></a>
### HTTPS routes

`provisioning::Service` implements the new L3 `tls::LocalService` interface.
`FrontDoor::serve_service` hands locally terminated TLS to that service instead
of a ThinQ1 session, owns its per-connection task, and cancels/joins it at shutdown.
Pending handshakes, active HTTP connections, and passthroughs share the front-door
connection cap. The signing worker is separately owned and stopped by the caller.

| Request | Response |
| --- | --- |
| `GET /route` | `resultCode: "0000"`, `apiServer: https://host:port`, `mqttServer: ssl://host:port` |
| `GET /route/certificate` | `common-server`, `aws-iot` name list |
| `GET /route/certificate?name=...` | Supplied trust certificate PEM; default is signing CA |
| `POST /device/{id}/certificate`, JSON `csr` | Signed PEM with `0000`, or signing failure with `9999` and no result |
| Unknown route | Legacy-compatible HTTP 200 and empty XML body |

Advertised ports are explicit, including default 443/8883, matching the reference.
Optional requested-host advertisement strips a valid numeric port, validates a
DNS hostname, and falls back to the configured host for addresses or malformed
values. It remains disabled by default. Callers using this mode must configure
TLS identities/routing for the names they advertise. Custom root PEM is parsed
and bounded at construction and served verbatim; it does not change the signing
worker's CA. Full custom advertised URLs/configuration migration are pending.

The HTTP implementation allows at most 32 headers and an 8 KiB read buffer,
64 KiB collected bodies by default, and configurable header/body/sign-request
and connection timeouts. Content-length and streamed/chunked body bounds are
both enforced. Oversized bodies return 413, body timeout 408, invalid JSON 400,
missing/non-string CSR 422, wrong content type 415, and wrong methods 405.
Signer overload/stopping returns HTTP 503 with `9999`; invalid CSR/signing failure
returns HTTP 200 with `9999`, matching the reference's wire failure envelope.
A signing-response timeout also returns `9999`; native work remains owned until
completion. Each connection serves one response with keepalive disabled; this
bounds connection lifetime and is an explicit change from the old HTTP server.
There is no OTP check or binding of CSR subject to device ID, preserving the
reviewed local provisioning behavior.

## 0.2 L3 ThinQ1 HTTPS/XML foundation

> Implementation record: progress paragraphs and test totals below belong to their
> recorded checkpoints. For current acceptance use [milestones](0.2-validation.md#milestones);
> for configuration use [runtime](0.2-runtime.md#runtime) and [operations](0.2-operations.md).

`rusthinq-server::thinq1_http::Service` implements POST routes through the TLS
front door. Each connection serves one HTTP response and closes. The standalone service
is now also routed alongside ThinQ2 provisioning by `https::Service` on one listener.

- `/lgehadm/api/Device/TotalDeviceInfoSvc`: default `0000/OK`,
  `DM_SETTING_INFO_GET_URI` BlackBox=N, and `THINQ_TIME_SYNC_URI` UTC time with
