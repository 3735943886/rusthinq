# 0.2 Architecture Contracts

Status: proposals for review. They describe neither implemented behavior nor user approval.
Implementation stays minimal: each part does only what is listed here, and nothing is built
ahead of a milestone that needs it. See [decisions](0.2-design.md) and [milestones](0.2-milestones.md).

## Structure

| Layer | Responsibility | I/O | Depends on |
| --- | --- | --- | --- |
| L1 Protocol | Per-connection protocol decisions and `lg_compat` | None | — |
| L2 Lifecycle | Device-lifecycle decisions | None | — |
| L3 Server | Connection path: devices reach rusthinq and stay connected | Sockets, TLS | L1 |
| L4 Bridge | Every connection to real LG or third-party servers | Sockets, TLS | L3 |
| L5 Scripts | Rhai host and drivers; all IL lives here (D1) | Script files | L3 |
| L6 App | Runtime: runs L2, executes its effects, persistence, `AppHandle` | Storage files | L2–L5 |
| L7 Adapters | External MQTT, GUI/management API, CLI/MCP | Network | L6 (`AppHandle`) |
| Daemon | Composition root: configuration, construction, wiring, shutdown order | Config file | all |

L6 and the daemon are split so that dependencies stay acyclic: L7 uses only `AppHandle`, while
the daemon constructs every layer including L7. The daemon holds no logic; it only
constructs and wires.

Rules:

- Dependencies point downward only. A lower layer never calls an upper one; upper layers use the
  lower layer's handle (commands in, events out).
- Decisions live in L1 and L2, which are pure. Other parts execute decisions and report results
  back as inputs.
- Only L5 Rhai code knows IL (D1).
- Each layer runs and is tested without the layers above it. Nothing depends on `legacy/`.
- The layer count is not fixed. Split a layer when it takes on an unrelated responsibility.
  Layers are module boundaries first; make one a crate when its dependency rule needs enforcing
  or it is optional (bridge, scripting, GUI remain cargo features of the daemon).

## L1 — Protocol

A pure model, one per connection. It takes input plus `now` and returns outputs plus the next
deadline. No clocks, sockets, files, configuration loading, or Tokio.

- ThinQ1 framing, parsing, and encoding; ThinQ2 message interpretation; ACK generation.
- `input(bytes | message, now) -> { frames to send, protocol events, next deadline }`.
- Invalid input yields an explicit error outcome; buffers are bounded.
- Exactly one ACK owner per frame. AABB local auto-ACK versus LG-relayed ACK is chosen by
  `lg_compat` from session input (bridge active or not), never by scripts.
- Unknown fields are recorded, not given invented meaning.

`lg_compat`: pure policy used by L1 and by L3's listeners. Each entry has a stable LG-* ID,
observed model/firmware, evidence, and a fixture. Unknown matches use the documented baseline;
never apply every workaround at once.

Verification: capture/fixture replay tests with no network, files, or real waits.
Implemented protocol contracts and bridge-generation handoff requirements are
recorded in [L1 implementation](0.2-l1-implementation.md); runtime enforcement
is pending L3/L4.

## L2 — Lifecycle

A pure model, one per process and run by L6, with the same input/`now`/deadline shape as L1. It knows
nothing about protocol frames.

- Known devices, incarnation, current session generation, online state, offline grace.
- Inputs: session up/down, forget request, step results (closed, deregistered, persisted, failed),
  loaded ledger, `now`.
- Outputs: device-list changes, online/offline events, and effects (close session, deregister
  from LG, persist ledger, persist removal).
- A newer session generation supersedes the old one. Down events from an older generation do
  not change state.
- Grace delays only the offline report. It never keeps a closed session usable.
- Forget is a sequence of steps: quiesce → close → deregister (only when the bridge is active)
  → persist removal → removed. Each step's failure is a distinct reported outcome; the device
  stays quiesced, never reported removed. The same identity may register again later with a
  new incarnation.

Verification: event-sequence tests with no network, files, or real waits.

## L3 — Server

Only the connection path. A device reaches rusthinq, completes its handshake, and keeps a live
session.

- 443 front door: ClientHello SNI peek. Served names go to the local TLS acceptor; other names
  go to a passthrough hook that L4 may register. Without L4 they are refused.
- TLS listeners with per-SNI certificates and the RTK_RTL8711am TLS1.0/CBC listener policy.
- ThinQ2 provisioning routes (`/route`, certificates) and the embedded device MQTT broker.
- One session task per connection, running an L1 session model.

`ServerHandle`:

| Direction | Item |
| --- | --- |
| Out | Session up / down (device id, generation); device data (device id, generation, opaque payload); cloud-bound data for L4 |
| In | `send(device, payload)` → rejected/busy, queued, sent, or device-acknowledged where the protocol supports it |
| In | `close(device)` |

- A new connection for the same device replaces the old session; the old one can no longer
  emit events.
- Per-device queues are bounded. A full queue returns busy and never blocks a shared loop; a
  stalled peer fails its own session.
- A disconnect after a partial write is an unknown outcome and is never retried automatically.
- Shutdown stops accepting, closes sessions, and joins owned tasks; its control path does not
  depend on free capacity in data queues.
- No persistence, device list, or grace. CA material and listener configuration are passed in
  at construction.

Verification: loopback/capture-replay integration tests and a standalone run in which devices
connect, get ACKed, and stay connected with nothing above L3.
The ThinQ1 runtime and TLS/SNI front door are recorded in [L3 implementation](0.2-l3-implementation.md);
CA/CSR and HTTPS provisioning services are recorded in [provisioning implementation](0.2-l3-provisioning.md);
The local ThinQ2 embedded MQTT subset and deploy/timesync execution are recorded in
[MQTT implementation](0.2-l3-mqtt.md); broader MQTT compatibility and bridge fencing remain pending.

## L4 — Bridge

Every connection to servers rusthinq does not impersonate:

- Per-device LG cloud connections, LG registration lifecycle, and outbound reconnect policy.
- The device↔LG relay, using L3's cloud-bound data and `send`.
- SNI passthrough and firmware/SOTA host learning (which hosts must be spliced to the real
  server), registered as L3's passthrough hook.

The bounded firmware/SOTA host evidence core is implemented in
[L4 foundation](0.2-l4-implementation.md). Its bounded TLS passthrough hook is verified against fake endpoints; cloud
real cloud registration and application wiring are still pending. A bounded
registration ownership/management handle now fences ThinQ1 downlink dispatch and
connects validated command evidence to firmware learning.

`BridgeHandle` exposes per-device enable/disable, deregistration, and status events.

- Enabling keeps an existing LG registration (as 0.1 does since upstream PR #107).
- Outbound reconnect is a transport policy with backoff. It is not a panic retry, and an inbound
  device replacement never triggers a dial.
- The relay does not interpret payloads beyond what L1 needs to decide ACK ownership.
- Bridge disabled or LG unreachable leaves L3 and local operation unaffected.

Verification: relay and passthrough tests against fake endpoints; real-LG validation is
recorded per device.

## L5 — Scripts

The [bounded Rhai host foundation](0.2-l5-implementation.md) now implements opaque
ordered outputs, execution limits, fault isolation and explicit generation reload.
A bounded blocking worker now serializes calls/reloads and joins on shutdown.
L6 now owns device/session-bound workers and joins them on normal runtime shutdown.
Automatic driver/callback/output dispatch, timers and real-driver acceptance remain pending.

- One worker per device, one invocation at a time, run off transport loops, with Rhai
  operation/memory limits. Native host functions are bounded and nonblocking.
- Inputs: device data, online/offline (from the lifecycle model, via L6), consumer
  commands, timers.
- Outputs are opaque: device send through `ServerHandle`, publication to a consumer sink, timer
  changes. The host checks only identity, generation, and bounds, never IL content (D1).
- Reload compiles outside the worker. Compile failure keeps the old generation; success cancels
  old timers and starts fresh state. Outputs from a replaced generation are discarded.
- Script error or panic is contained: timers are cancelled, a health event is published, and
  the generation stays faulted until an explicit reload. No automatic retry or restart.
- The consumer sink is implemented above L5. With no sink attached, publication returns an
  explicit disabled error.

Verification: real-driver runs against captured input. IL conformance itself is tested in
rusthinq-scripts.

## L6 — App

- Runs the L2 lifecycle model: feeds it L3 session events, step results, and `now`; arms its
  deadlines; forwards online/offline to L5.
- Executes its effects: `close` on L3, deregistration on L4, ledger writes through a small
  storage module. Each result goes back to the model as an input.
- Loads the ledger at startup.
- `AppHandle` for L7: device list and change events, forget, script reload, consumer commands
  routed to L5, and the L5 consumer sink.
- Thin: it executes L2's decisions and makes none of its own.

Verification: integration tests over fake L3/L4/L5 handles and a temporary storage directory.

## L7 — Adapters

- External MQTT: broker connection, delivery, retained cleanup, and routing inbound consumer
  commands to L5. Optional; nothing below is affected when it is disabled or the broker is down.
- GUI/management API: device list and status from `AppHandle`; works without an external
  broker. Property-value screens are out of scope.
- CLI/MCP: online paths use the management API; offline tools reuse L1 codecs.

## Daemon

- Loads configuration and constructs L3, L6, and L4/L5/L7 when enabled.
- Wires handles between layers. No other logic.
- Owns shutdown order: stop admission, then adapters, app, scripts, bridge, server.

## Cross-Cutting

- Panic isolation (design P1): guard per-device handler and script boundaries so one device
  cannot stop shared processing or other devices. No supervisors, panic retries, or
  `panic=abort`.
- Every task has an owner that cancels and joins it at shutdown or device removal.
- Exact queue sizes, method names, and storage encoding are implementation details.

## Intentional Changes from 0.1

- ACK policy moves from scripts (`ctx`) to `lg_compat`.
- IL handling moves from the host to Rhai (D1): `IlState`, `publish_il`, host-side command
  validation, and host-applied availability are removed.
- A script fault stops that script until reload instead of continuing with possibly corrupt state.
- Forget closes live sessions and reports each step's outcome instead of unconditional success.
- Publication with external MQTT disabled returns an explicit error.
- SNI passthrough is available only with the bridge; without L4, unserved names are refused.

## Open Items

- Script fault and IL availability: the host cannot publish IL unavailable for a faulted
  script. Decide whether consumers rely on the health event or Rhai provides a fallback.
- Whether firmware passthrough is ever needed without the bridge. Firmware URLs arrive in
  cloud→device messages, so this document assumes not.
- Crate names and which layers start as crates rather than modules.

## Retained publication deletion requirement

Every retained MQTT publication must have an explicit removal route before it is
enabled: a recorded owner and exact topic, individual deletion, owner-wide cleanup
for device/adapter removal, and complete namespace cleanup. MQTT remote deletion
uses an empty-payload PUBLISH with RETAIN=1. Local map deletion, unsubscribe,
connection closure, and device offline do not prove remote retained deletion.
Removal work must survive remote failure and restart until delivery is confirmed;
persistent adapters must store the cleanup inventory/pending tombstones durably.
Device retained ownership includes lifecycle incarnation. Cleanup begins only from
the durable `Removed` action; offline state alone never deletes retained values.
A QoS0 socket write alone is not broker confirmation. Reconnect, mapping changes,
and disable/remove flows must drain or recover cleanup work, not silently abandon it.

`rusthinq-server::retained::Store` now provides bounded owner/topic inventory,
empty-payload removal, individual/owner/all cleanup manifests, and owner-scoped
replay. Tombstones encode empty RETAIN=1 packets. It is an in-memory foundation,
not a remote publisher or durable cleanup queue. Owned retained network publication now goes through the durable inventory and
matching PUBACK path in L6; daemon lifecycle orchestration remains pending. Will retain metadata likewise remains an observation
until this publication/deletion path exists.
