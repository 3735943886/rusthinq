# rusthinq 0.2 Design Decisions

Status: proposed implementation contracts under an agreed architectural direction. None of
these entries claims completed implementation. M0 reviews structural contracts before implementation;
M1 validates the first slice. Update decisions when evidence changes rather than silently
changing their meaning.

See the [plan](0.2-plan.md) and [milestones](0.2-milestones.md).

## Reference and Scope

The reference is rustuya's transition from v0.3.0 to v0.4.0, especially its explicit
protocol/lifecycle core, I/O driver, owned discovery service, and documented decisions about
previously ambiguous behavior. The local reference checkout also contains subsequent 0.4.x
refinements; it is a design reference, not a dependency or an exact release specification.

Adopt the separation of decisions from execution and the practice of recording behavior
changes. Do not import its embedded/no_std requirements, library facade, outbound connection
model, or Tuya-specific response semantics. rusthinq remains a standalone server.

## D0 — New Implementation with Staged Cutover (Accepted Direction)

The rethink-to-Rust lineage is a reason to reconsider inherited structure rather than
preserve it through compatibility wrappers. Build new daemon internals and retain the old
implementation as a fixed behavioral/protocol reference during development. This decision
is accepted; it does not imply any implementation work is complete.

Selectively reuse independently verified components. Preserve wire compatibility, IL and
script contracts, and panic isolation where required; do not preserve internal types,
callbacks, global ownership, or factory dependencies solely for source compatibility.
Unexplained legacy behavior requires evidence under C4 before preservation or intentional change.

First relocate the tracked 0.1 project into `legacy/0.1/`, preserving its own workspace and
reference revision. The root is the new 0.2 project immediately, not a temporary second binary
inside the old architecture. Retain root Git metadata and 0.2 planning documents; archive old
project-specific hidden configuration with the old project. Exclude ignored artifacts and
personal files from the relocation. Root automation must target only the new project unless
an explicit reference comparison is requested.

The legacy workspace is a reference, never a dependency: forbid path dependencies, source
includes, and runtime fallbacks into it. Copy/adapt a component into the new tree only when
needed, with its provenance, dependency review, and validation recorded. Keep legacy edits
limited to documented relocation necessities. Verify its build from its own directory.

Compare through isolated runs or replay. Never run both control paths against the same live
device. M1 validates new ownership boundaries; subsequent milestones establish feature
coverage and documented differences. M5 gates production cutover and legacy-tree removal,
not the initial choice of root workspace. Git preserves the original reference for rollback.

## Core Boundaries

| ID | Current approach / problem | Decision for 0.2 | Validation |
| --- | --- | --- | --- |
| C1 | `rusthinq-core` contains configuration, MQTT helpers, clock reads, and file persistence alongside shared types. Its name does not enforce an I/O boundary. | Establish a dedicated protocol/lifecycle core boundary. Move services to their real owners. Allow std, but exclude direct I/O, Tokio execution, and clock reads. | Dependency audit and core tests without sockets, files, or real waits. |
| C2 | ThinQ1 `process_one` interprets messages while invoking callbacks and an ACK channel. | Core processing produces typed outbound messages and events; the driver performs transmission and dispatch. | Protocol fixtures pin parsing, ACK behavior, invalid input handling, and event order. |
| C3 | Connection policy is spread across connection tasks and DeviceBridge's pending drops and handler replacement. | Separate per-session protocol state from device-level replacement/offline policy. Give each one an explicit owner and deterministic transitions. | Reconnect, old-session close, grace expiry, and handler replacement event sequences. |
| C4 | Existing implementation details can be mistaken for compatibility requirements. | Classify behavior as preserve, intentionally change, or retire. Reuse proven codecs and compatibility handling; redesign ambiguous contracts. | Every intentional change has a rationale, expected result, test, and migration note where externally visible. |

## Runtime and Ownership

| ID | Current approach / problem | Decision for 0.2 | Validation |
| --- | --- | --- | --- |
| R1 | Traits and callbacks hide transport details but can also obscure state ownership and execution order. | Runtime tasks own core instances; an application registry owns session handles and accepts only current-generation events. Expose handles, not mutable implementation state. | A replaced connection cannot send authoritative updates or mark its successor offline. |
| R2 | Socket work, queued commands, and timers must coexist under load; actor structure alone does not guarantee progress. | Define bounded queues, partial-write state, fair input processing, and shutdown independent of command queue capacity. | Stalled peer, saturated command queue, timeout progress, and shutdown tests. |
| R3 | Scripts have a process-wide timer runtime; lifecycle cleanup also uses callbacks and task cancellation. | Application/runtime owners manage script services, timers, and task lifetimes explicitly. Avoid global mutable lifecycle services on migrated paths. | Service create/drop cycles, reload, stale timer delivery, and shutdown leave no active owned work. |
| R4 | Local devices connect inbound while the optional bridge establishes outbound connections. | Model accepted sessions and outbound LG reconnect policy separately. Reuse policy helpers only where semantics match. | Inbound replacement never triggers an invented device dial; outbound retries follow their own policy. |

## Application and Adapters

| ID | Current approach / problem | Decision for 0.2 | Validation |
| --- | --- | --- | --- |
| A1 | GUI reconstructs state through its own MQTT client; MCP queries retained state. | Common application commands, queries, and subscriptions serve all adapters. GUI uses an internal handle; remote tools use the management API. | GUI and management API work without an external broker; the API works without GUI assets. |
| A2 | External MQTT control conventions reach device-facing abstractions through publish methods. | Application state/events are independent of topics. MQTT mapping and retained cleanup belong to the external adapter; device-facing MQTT remains transport. | No topic construction in protocol/lifecycle models; existing MQTT contracts or documented changes verified. |
| A3 | Callback-style send/publish interfaces do not themselves express command completion or stream loss. | Distinguish acceptance, transmission, protocol-confirmed ACK, and observed state. Separate latest state from bounded events; make gaps visible. | Uncorrelated replies never complete arbitrary commands; slow subscribers detect loss and recover from a snapshot. |
| A4 | Persistence, scripting, bridge management, and tool workflows have different execution needs. | Keep orchestration in ordinary application services. Reuse shared services/codecs across CLI and MCP without a universal effect framework. | Slow service work does not block device progress; errors and operation completion reach callers consistently. |

## Script Output and IL Contracts

### S1 — Adapter-Neutral Driver Sink

Current factories receive `Arc<dyn MqttConnection>`. `ctx.publish_property` both updates
`IlState` and publishes to MQTT; `publish_il` stores a descriptor and builds MQTT bindings.
This makes transport abstraction carry the semantic device-state path.

Replace that dependency on migrated paths with a device-scoped output sink carrying IL
descriptors, typed values, and events to the application. Define bounded delivery and failure
semantics in M0. A session/driver generation accompanies output so superseded scripts cannot
update current state. The host assigns identity; the script supplies semantic content.

The application owns the authoritative exposed descriptor/value store and command validation
view. A driver retains only decoding/algorithm state it needs. Any existing IlState cache
must be moved, shared through one owner, or made a read-only projection; it must not become a
second authority. MQTT formatting, retained policy, and `x-mqtt` bindings belong to the MQTT
adapter. Disabling MQTT must not disable descriptor/value production.

M1 must run one real script through this path and assert descriptor/value/event behavior,
command validation, and stale-generation rejection. Full script-service migration remains M2.

### S2 — Cross-Repository Compatibility

The local reference repositories are `../rusthinq-scripts` and `../ildevice` relative to the
rusthinq checkout. These are external contracts, not files guaranteed to exist for every build.
Record the tested repository revisions and fixture provenance; CI must obtain pinned inputs
or use explicitly sourced fixtures rather than rely on sibling directories.

The normative IL sources are `il.md`, `il-messages.md`, descriptor/message schemas, and
conformance vectors. `il-mqtt.md` defines only the MQTT mapping. IL is currently a draft;
record its tested revision instead of silently following changes. Reuse relevant vectors
for command validation, typed values, descriptors, and MQTT mapping at their respective layers.

Preserve the selected script's observable Rhai API behavior in M1. Document intentional
changes and coordinate required driver updates across repositories. Full driver inventory
and compatibility validation occur in M3, not as a prerequisite for M1.

### S3 — Explicit Raw MQTT Compatibility

`ctx.publish_raw` is also a public script escape hatch; rusthinq-scripts documents non-IL
custom drivers. Do not pretend arbitrary topic publications are IL values. Isolate any
retained compatibility hook as an MQTT-specific adapter capability, with explicit behavior
when MQTT is disabled. Decide deprecation or replacement through the M3 compatibility review.
It must not bypass the authoritative IL store for normal descriptor/value updates.

## Panic Isolation — P1 (Preserve)

`panic_guard::guard` catches unwinds around per-device callbacks. Shared dispatch loops and
the release profile rely on this containment. Preserve the guarantee that a handler/script
panic does not terminate shared processing or disrupt unrelated devices.

Keep guards at migrated shared callback/script invocation boundaries unless an isolated task
boundary demonstrably provides the same guarantee. Merely spawning a task is insufficient:
its failure must be observed, outstanding callers resolved, and affected resources cleaned
up without terminating the registry or unrelated sessions. Record the choice for the M1 path.
Do not switch the release profile to panic=abort.

Containment is not recovery. Do not add application panic retries, automatic actor/script
restarts, or restart supervisors. Fix panic causes. Cancellation/join ownership in R2/R3 is
resource lifecycle management only. Existing protocol-directed reconnect after network failure
is distinct from retrying a panicked operation and must remain explicitly scoped as such.

Verification: induce a handler panic and prove another device and shared dispatch still work;
prove the failed invocation is not replayed, no replacement task is automatically spawned,
and waiting callers are not left hanging. Record the affected-device state after containment
rather than assuming partially mutated state is safe to resume.

## ThinQ2 Server Boundary — T1

The embedded `mqtt_broker.rs` is owned by the runtime/server layer, independent of the
external MQTT adapter. Keep existing broker machinery unless a demonstrated contract requires
changes. ThinQ2 device/session interpretation feeds the protocol core. Provisioning, firmware,
and SNI passthrough are separate I/O services with explicit dependencies on application state
where needed. Do not bury their migration in one protocol checkbox; use M2b's separate gates.

## M0 — Architecture Review Before Implementation

The concrete proposed resolutions are in [architecture contracts H1–H7](0.2-contracts.md):
state ownership, script invocation ordering, command/reload behavior, pressure and shutdown,
forget semantics, LG compatibility policy, and crate dependencies.

Review their intentional behavior changes before relocating legacy or writing the new daemon.
These proposals supersede the earlier first-slice-only M0 scope. Accepted D0 direction does
not imply acceptance of every newly proposed execution or failure contract. Once reviewed,
record accepted/revised decisions and unresolved blockers explicitly. Method names and numeric
capacities may remain implementation details; ambiguous ownership and failure outcomes may not.

## Behavior Review Record

For each nontrivial migration, add a record with the following fields. Do not fill the table
with speculative bugs; link to inspected code, a reproducer, a test, or a protocol observation.

| Field | Required content |
| --- | --- |
| Behavior and source | Existing path and evidence of its current behavior |
| Classification | Preserve, intentionally change, or retire |
| Decision | Explicit target behavior and responsible layer |
| Rationale | User-visible need, protocol constraint, or maintenance problem |
| Verification | Deterministic core test and/or runtime/adapter integration scenario |
| Compatibility | Configuration, wire, script, CLI, and persisted-state impact as applicable |
| Status | Proposed, accepted, implemented, or verified; link to implementation when available |

## Review Gates

At M1, review whether the core actually owns protocol decisions, whether the runtime can
make progress under backpressure, and whether the application boundary serves both GUI and
MQTT without duplicated state. Revise the design before expanding to ThinQ2 if this fails.

At release, audit both code and dependencies. Passing unit tests does not establish correct
shutdown, migration, real-device interoperability, or adapter behavior. Record unverified
environments explicitly. No embedded build or public-library stability promise is required.
