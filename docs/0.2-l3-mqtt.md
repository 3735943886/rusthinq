# L3 — Local ThinQ2 MQTT foundation

L6 now connects this broker to lifecycle, durable storage and automatic generation
refill through `Runtime::new_mqtt`; see [runtime integration](0.2-l6-implementation.md).
Generation-targeted close completion tracks redeploy on the same physical stream.
The caller/front door still owns and joins broker transport tasks.

`Broker::sharing` can now reuse ThinQ1's registry, generation allocator, aggregate
connection limit and shutdown signal for one mixed L6 owner. Send operations
reject sessions of the other protocol; snapshot/close/allocator operations span
the shared registry. See the mixed harness and shutdown contract in L6 docs.

The pure L1 `mqtt` module supplies bounded MQTT framing and device packet codecs.
L3 `mqtt::Broker` implements `tls::LocalService`, so the existing TLS/SNI front door
owns MQTT connection tasks, cancellation, and joins. `Broker::run` also accepts
caller-owned generic transports for replay/integration testing. This service
uses no external MQTT broker and interprets no IL. L3 adds chrono for UTC and
base64 for the reviewed timesync wire format; L1 retains only serde_json.

## Supported device connection path

- MQTT 3.1.1 CONNECT with a clean session and optional empty client ID, with optional
  username/password fields parsed but not authenticated (matching the reference).
- SUBSCRIBE/UNSUBSCRIBE with correlated SUBACK/UNSUBACK; at most sixteen filters
  per connection, each at most 1024 bytes. Valid `+` and trailing `#` filters match
  only outputs to that same device; this is not a cross-device MQTT fanout broker.
  SUBACK always grants QoS 0. PINGREQ/PINGRESP and clean DISCONNECT are supported.
- QoS 0/1/2 incoming publish, including DUP. QoS1 PUBACK retains its packet ID;
  QoS2 uses PUBREC/PUBREL/PUBCOMP and dispatches only on release.
  Device-facing outputs are QoS 0, non-retained. Malformed flags/lengths/IDs/UTF-8,
  unknown packet types, and unsupported features close that connection.
- MQTT packet allocation is bounded before reading the declared body. The frame
  cap is the configured CLIP payload limit plus 4096 bytes of envelope allowance;
  CLIP input/output payloads retain the stricter payload limit. Packet reads stay
  alive across outbound selection, so a partially read header/body is not lost.
- Complete received packets refresh the broker deadline. A nonzero CONNECT
  keepalive uses the maximum of 1.5 times the declared interval, 300 seconds,
  and the configured inactivity timeout. Zero keepalive uses the same grace floor.
  Before CONNECT the configured timeout applies (90 seconds by default).
  Partial-byte traffic and outbound writes do not refresh the receive deadline.
  Format reference: [MQTT 3.1.1](https://docs.oasis-open.org/mqtt/mqtt/v3.1.1/os/mqtt-v3.1.1-os.html).

## ThinQ2 execution and readiness

Each connection runs its own L1 ThinQ2 session with bridging disabled. Device
MQTT publishes feed topic/payload and an injected outbound message ID to L1.
A deploy action claims a bounded, generation-fenced transport identity before
writing its response, replacing and closing any old connection. The new entry
is pending: it is absent from the public snapshot and cannot receive application
commands. Replacement reports the old session down immediately. A delayed older
deploy is rejected even if the newer transport has since closed; the shared
runtime's bounded generation history protects that transition.

The response preserves the reviewed `completeProvisioning` fields, `type: 0`,
`host: message`, message/provisioning publication topics, provisioningType, and
600-second deployInterval. It is sent only when the connection subscribed to the
applicable `lime/devices/{did}` topic. Full write/flush success is reported to L1
with the matching operation ID before another device packet is dispatched.
Absent subscription, encoding bounds, or write failure report provisioning failure
and close the pending transport. No failed/pending provisioning is published as Up.

Only L1 Ready makes the session usable and emits ordered Up and Ready events with
the original deploy metadata. Explicit completion and LG-002's observed-model
first-packet fallback stay L1-owned. Repeated deploy on the same transport
allocates a new logical generation and stays pending until completion, preserving
the transport and subscriptions. See the reprovisioning section below.

Timesync actions use an injected L3 clock. The default reads UTC and milliseconds
since Unix epoch. The response preserves `resp_timesync`, `type: 1`, and the seven
base64-encoded bytes: year modulo 100, zero-based month, day, hour, minute, second,
and Sunday-based weekday. Fixed clocks make the integration tests reproducible.
Clock errors fail the connection; clock panics are contained by the owned task.

L1 local ACK actions are written before Data and CloudBound events. Binary data
and original unknown CLIP fields remain opaque. CloudBound is a local-only
observation: it must not be queued/replayed to a subsequently enabled LG bridge.
There is no bridge input API, cloud-origin send queue, bridge-generation update,
or LG connection in this implementation. L1's bridge contracts are unchanged,
and their L3/L4 runtime enforcement remains pending.

## Runtime ownership and handles

`mqtt::Handle` exposes ready-session snapshots, generation-tagged bounded broadcast
events, targeted close, and bounded nonblocking command admission. Queued receipts
report Sent after write/flush, Failed for unsent cancellation or missing subscription,
and Unknown for partial writes/lost completion. None implies a device ACK.
Subscribe changes cannot redirect another device's frames to this connection.
Queued work is never retried. Slow event consumers receive Lagged and must recover
through a snapshot/generation fence above L3.

The service reuses the ThinQ1 runtime's generation-history/cleanup guard and entry
representation, with a readiness bit for pending MQTT provisioning. ThinQ1
behavior remains unchanged. `Broker::stop` marks admission stopped and signals
all connections independently of queue capacity; their caller/front door owns
joining them. Front-door shutdown cancels and joins all MQTT TLS tasks before
returning. Independent MQTT replay callers must likewise stop and join owned tasks.
Connection and generation bounds are checked; caller-supplied generation floors
must respect the loaded lifecycle ledger. Unified generation allocation and
ownership when composing ThinQ1 and ThinQ2 with L6 are still integration work;
standalone independent brokers must not be wired to one lifecycle identity store
with colliding/reset counters.

## Deliberate limits and changes

This is a local device transport foundation, not a complete general MQTT broker.
Retained input/store/replay and persistent sessions
are explicitly unsupported and close the peer. Outbound QoS 1/2 and broker-to-broker relay are
absent. The legacy appliance-tested five-minute keepalive minimum is preserved;
a larger declared or configured interval extends it.
The MQTT client ID is parsed but does not own replacement: validated ThinQ2
identity owns device-session replacement, as in the reviewed reference.
Additional capabilities require device evidence/replay fixtures and tests before
expanding the supported subset. No real-appliance compatibility is claimed.

## QoS1 retransmission compatibility

QoS1 PUBLISH with DUP is now admitted instead of disconnecting the session.
Both first-seen DUP and retransmissions get PUBACK and enter the same L1 path as
fresh messages. This preserves the reference broker's at-least-once ingress;
packet IDs are reusable after acknowledgement and do not establish CLIP command
identity. Repeated opaque traffic is forwarded for every arrival. No MQTT-level
exactly-once promise or application deduplication is introduced. Existing L1
state checks still apply. Same-transport redeploy now gets a fresh logical generation.

Reference: the fixed 0.1 `mqtt_broker.rs` Publish handler acknowledges and forwards
incoming QoS1 regardless of DUP. New tests cover first-seen DUP, repeated payload,
packet-ID reuse with new payload, PUBACK for each arrival, subsequent PING, stable
session identity, and clean shutdown. Pure codec tests reject zero IDs and QoS0
DUP. These are synthetic tests, not appliance captures.

## Same-transport reprovisioning

Repeated deploy/preDeploy uses the existing MQTT transport and subscriptions.
The runtime allocates a fresh registry generation, removes the prior ready entry,
reports its Down, and admits the replacement as pending. Queued old-generation
commands fail rather than being replayed into the replacement. Old send/close
handles become stale. Once the provision response is written and L1 accepts
completion, the new identity publishes Up/Ready. Pending redeploy can itself be
replaced without disconnecting, and generation exhaustion remains terminal.

The fixed reference `thinq2/device.rs` replaces deploy metadata and sends a new
response for each deploy/preDeploy. New transport tests exercise ready-to-pending
replacement, a second pending deploy, stale handles, new-generation sends, and
shutdown. Internal write-result operation correlation is preserved by L1.
Device completion ACKs do not carry enforced operation correlation in this slice;
an indistinguishable delayed completion ACK can still satisfy the current pending
operation, as in the existing protocol path. No stronger wire-level correlation
is claimed. Cloud/bridge generations remain a separate integration requirement.

## Empty clean-session client IDs

The broker now accepts an empty MQTT client ID for clean sessions. Its transport
admission generation distinguishes connections, and validated ThinQ2 `did`
continues to own device identity/replacement. Two empty-ID clients can provision
separate devices and receive isolated outbound traffic; neither replaces the
other merely because their MQTT IDs match. No persistent session or client-ID
recovery is implied. Non-clean CONNECT is still explicitly unsupported.

The fixed reference `mqtt_broker.rs::decode_connect` skips the client ID and
accepts empty values. A pure codec test covers empty clean versus unsupported
non-clean CONNECT; a runtime test provisions two distinct devices with empty
IDs, verifies targeted commands on both, and joins shutdown. Fixtures are
synthetic and do not establish real-device compatibility for other CONNECT flags.

## Last Will ingress and observations

CONNECT now accepts a bounded Will topic and binary payload, validating QoS and
retain flags before consuming authentication fields. Nonempty wildcard-free topics
are required; QoS 0/1/2 metadata is preserved (this does not implement downstream QoS2
Will delivery). On EOF, transport/protocol failure or idle expiry, a current connection
emits Event::Will before Down. The event carries its admission generation, optional
validated device session, and original topic/payload/QoS/retain. Pre-provisioning
connections can therefore report Will without inventing a device identity.

Normal MQTT DISCONNECT suppresses Will. Application close, broker stop, replaced
sessions and front-door cancellation suppress it as intentional administrative
shutdown. This improves the reference broker's unconditional cleanup publication,
which also published on clean disconnect. No Will is synthesized on panic or
aborted futures. Current-generation checks and event emission share the registry
lock so late failures cannot publish a replaced session's Will.

This is an observation interface for future application/broker publication.
Subscriber fanout, retained storage/replay and Will delivery QoS handshakes remain
unimplemented, so complete Will feature parity is still an open acceptance gate.
Tests cover binary payload and flag validation, first connection EOF observation,
clean-disconnect suppression and administrative shutdown suppression. No actual
appliance Will fixture or downstream delivery is claimed.

## QoS2 ingress

QoS2 PUBLISH is stored per connection and acknowledged with PUBREC. Retransmission
with the same packet ID/topic/payload repeats PUBREC without running L1. A changed
payload under an outstanding ID is rejected. PUBREL removes the stored packet,
processes it once, and sends PUBCOMP before executing protocol actions. Repeated
or unknown PUBREL sends PUBCOMP without processing again. Packet identifiers are
reusable after completion. All operations stay inside the owned connection task.

Outstanding records are bounded by configured outbound_capacity; each payload is
bounded by max_payload. Capacity/payload violations close only that connection.
Records carry their admission generation so releases from an earlier logical
session do not dispatch into a redeployed device. Pending records expire with
connection closure; this is clean-session ingress, not durable exactly-once across
reconnect, downstream QoS2, or persistent MQTT sessions.

The reference `mqtt_broker.rs` PUBACKs all positive incoming QoS values, including
QoS2; this incomplete exchange is intentionally corrected. Synthetic codec tests
validate PUBLISH/PUBREL flags and IDs. Runtime tests cover delayed dispatch,
retransmission, repeated release, ID reuse, and bounded outstanding storage.

## Retained ownership and deletion foundation

`retained::Store` requires an explicit owner for every topic, prevents ownership
collisions, and bounds records and logical owner/topic/payload bytes. Replacement
admission is atomic. Empty payload deletes rather than remaining replayable.
Individual removal, remove_owner, and clear return exact-topic tombstone manifests;
an empty put for an unknown topic still yields a tombstone to clean remote state
that outlived process memory. Wildcard replay is owner-scoped and deduplicated.

Tombstone::frame encodes a zero-payload RETAIN=1 PUBLISH. The caller owns reliable
remote delivery and must persist retry inventory before enabling retained remote
publication. This module emits no network messages and does not yet enable retained
broker ingress/fanout or external MQTT. Four pure tests verify cleanup routes,
remote tombstone bytes, empty deletion, owner isolation, and bounded atomic updates.

## Recoverable retained cleanup ledger

`retained::Cleanup` atomically admits bounded tombstone batches and allocates a
fresh attempt token for each send/retry. Failed/unknown results retain work;
only matching broker-confirmed completion removes it. Replacement, retry, and
recovery invalidate older results. Empty-payload remote deletion remains explicit.
Checkpoints contain a schema version, token high-water mark, and owner/topic work
inventory. Restore rejects malformed, oversized, duplicate, and invalid-topic
records; interrupted attempts are never resumed as confirmed.

This ledger is pure. L6 must durably commit admission and token checkpoints before
remote sends, and commit completion afterward. A failed completion checkpoint can
safely replay deletion after restart. It does not own atomic file writes or validate
that a caller's boolean actually represents broker acknowledgement. Remote retained
publication now goes through L6 durable ownership and correlated PUBACK; the device
broker still does not accept retained ingress/fanout. Three tests cover failure/retry/late results, restart token fencing,
and atomic capacity/recovery rejection.

L6 checkpoint file ownership is now implemented in
[application foundation](0.2-l6-implementation.md), including commit-before-send
and recovery fencing. Remote publishing and acknowledgement wiring remain pending.
