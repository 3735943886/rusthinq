# 0.2 L6 application foundation

`rusthinq-app` begins with caller-owned durable retained deletion work in
`retained_cleanup::Ledger`. L3 provides the pure deletion ledger; L6 owns file
I/O and commit ordering. No device registry, daemon composition, script host, or
general network publisher is implied by this foundation.

Ledger::open requires an existing parent directory, locks a persistent sidecar
file for the owner's lifetime, and bounds checkpoint reads before parsing. Missing
checkpoint means a new empty ledger; invalid data is rejected without overwriting
it. Do not remove the lock file while a process may own it. Use a single canonical
configured checkpoint path; arbitrary aliases to a checkpoint are not supported.

Each mutation stages a clone of the pure ledger. Commit writes a uniquely named
temporary file in the same directory, syncs the file, atomically replaces the
checkpoint, then syncs the directory. Only successful commit updates live state.
Temporary files use tempfile's restricted default permissions and are removed on
pre-rename failure. The sidecar is deliberately retained so later owners lock the
same inode. No directory or personal configuration file is created implicitly.

enqueue durably records deletions. begin returns an attempt token only after the
inventory and token high-water mark are committed. complete persists matched
results; only explicit broker-confirmed success removes work. Failed/unknown
delivery remains pending. A crash after remote deletion but before completion
commit safely repeats empty-payload deletion after recovery. Restored attempts
are invalidated while their high-water mark is preserved.

Any commit I/O error marks the owner uncertain and blocks further mutations until
drop/reopen. This includes directory-sync failure after rename: the caller must
not assume either the old or new disk image won. pending is the last committed
in-memory view, not authoritative disk state when requires_reopen is true. Failed
begin never authorizes network work. Atomic rename/directory-sync behavior is
validated on Linux; remote/network filesystems and power-loss fault injection
are unverified. The daemon must run these synchronous operations on an owned
blocking worker, not an async protocol I/O task.

Three filesystem tests cover restart recovery and stale result fencing, exclusive
ownership and invalid checkpoint preservation, and failed save blocking subsequent
sends while preserving pending memory/recoverable prior contents. Workspace
tests, formatting and warning-free Clippy remain required.

Retained value publication inventory,
device-removal orchestration and full application persistence are still pending.
The deletion file does not inventory every remote retained topic automatically;
publishers must record ownership before enabling retained values and route removals
through this owner. Retained value publication now uses this inventory, as described below.

## Acknowledged remote deletion

`cleanup_mqtt::Session` uses a caller-supplied AsyncRead/AsyncWrite transport and
an exclusive clean MQTT 3.1.1 connection. It performs CONNECT/CONNACK, then sends
only zero-payload QoS1 RETAIN=1 deletion packets. It does not dial, subscribe,
relay device traffic, or accept unrelated publishers
on the same connection. Transport TLS/authentication is caller-owned; MQTT username
and password configuration is not implemented in this foundation.

Each attempt gets a monotonic, non-reused packet ID in this connection. A matching
PUBACK is the only network success signal. Unexpected acknowledgement, EOF, write
failure or timeout poisons the connection; reconnect before retry. Exhausted packet
IDs also require reconnect. The bounded exchange timeout covers write/flush/read;
responses are four-byte bounded packets. Broker PUBACK confirms receipt, not a
promise that arbitrary remote broker storage is durable against power loss.

`delete_one` takes exclusive ownership of Ledger, runs begin on spawn_blocking,
awaits the exact PUBACK, and durably commits completion on spawn_blocking. It returns
the ledger on success. On error the ledger is dropped and must be reopened from
its checkpoint; unconfirmed work remains pending. Future cancellation may leave a
blocking commit finishing, so wait for ownership/lock release before reopening;
no network send is authorized until begin returns. Cancellation after PUBACK can
leave a completion commit finishing or a safe replayable deletion. The caller owns
this future, transport shutdown and joining its task; no reconnect loop is spawned.

Two duplex fake-broker tests cover exact QoS1 retained deletion bytes, durable
completion/reopen, wrong packet-ID PUBACK, missing-ACK timeout and poisoned-connection
retry refusal with recovered pending work. There is no live broker/device test.
Owned retained publication and explicit startup/removal draining are now implemented;
automatic daemon orchestration remains pending.

## Startup/removal cleanup draining

`cleanup_mqtt::Session::drain` consumes a recovered Ledger and sends pending
empty retained QoS1 deletions sequentially. Matching PUBACK and a durable
completion commit precede each next send. On error it stops immediately; the
caller reopens the checkpoint and supplies a fresh connection. Acknowledged and
committed entries stay removed, failed/unsent entries stay queued. No detached
retry or reconnect task is created. Future cancellation follows delete_one's
ownership/lock-release rules. The returned completed count applies to this run,
not historical removals; successful drain returns the still-owned empty ledger.

A fake-broker restart test confirms a, drops before b's PUBACK, verifies only b/c
survive recovery, then drains them on a fresh connection and reopens empty state.
This supplies the cleanup execution path for future startup/device-removal wiring;
credentials/TLS dialing and automatic daemon
lifecycle orchestration remain pending and are not implicitly enabled.

## Owned retained value publication

Session::publish_owned_retained registers the owner and exact topic in the durable
cleanup inventory before writing a nonempty QoS1 RETAIN=1 value. Value PUBACK does
not erase the inventory. An unknown publication result also preserves it, including
when the peer received bytes before disconnect. Payloads are bounded at 1 MiB;
empty payload must use the acknowledged deletion route. Owner conflicts, invalid
topics, inventory capacity and failed commits prevent untracked publication.

Every inventoried topic is eligible for deletion; it is not automatically scheduled
for deletion while an active value is in use. Explicit delete_one removes one;
remove_owner removes only that device/adapter's topics; drain clears all recorded
topics for startup resynchronization, disable, namespace cleanup or removal. Each
operation removes only broker-confirmed work and persists progress before advancing.
The single-owned ledger serializes publication and cleanup. Mapping changes must
clean the previous topics before recording/publishing their replacements; changing
an existing topic's owner is refused until prior ownership is removed.

On restart the inventory contains all possibly published topics, including active
values and uncertain sends. The owner decides when to drain and republish desired
state. Payload values are not persisted by this ledger; scripts/adapters must
reconstruct them. No automatic lifecycle/device-forget hook, credentials configuration,
TLS dialing or external MQTT adapter is implied. Checkpoint deletion by an operator
loses the inventory and requires separate broker cleanup; it is never automatic.

Three additional tests verify durable inventory before network publication, success
and unknown-result recovery, owner-isolated removal, and zero publication bytes
when inventory admission fails. Together with deletion/recovery tests these cover
individual, owner-wide and complete removal routes.

## Lifecycle removal correlation

`lifecycle_cleanup::apply` accepts L2 actions and triggers retained cleanup only
for `Action::Removed`, which L2 emits after close/deregister and durable device
removal succeed. Offline, Changed, ForgetStep and ForgetFailed do not erase retained
state. Remote cleanup failure does not resurrect an already durably removed device;
the separate retained checkpoint keeps its work for reconnect/startup retry.

Device retained owners use `device/{id_length}:{id}/{incarnation}`. Including the
incarnation prevents a delayed cleanup for an old device from deleting topics
published by a new device with the same ID. Length-prefixing makes IDs containing
separators unambiguous. Device publishers must use `device_owner` rather than a
bare device ID; arbitrary adapter owners remain responsible for their own stable,
bounded owner namespace.

The hook processes one lifecycle action and returns an explicit Ignored or Removed
outcome with the number of confirmed topic deletions. The future owns the ledger
during cleanup. On failure the caller drops/reopens the ledger and schedules retry;
there is no hidden retry task. The full daemon action loop and retry scheduler are
still pending, so this is a tested orchestration boundary rather than a running
composition root. Tests verify that only Removed triggers deletion and that old
incarnation cleanup preserves a newer incarnation's inventory.
