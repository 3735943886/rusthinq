## Running the composed 0.2 device runtime

The `rusthinq` binary in rusthinq-app now composes ThinQ1 TLS, device MQTT TLS,
shared ThinQ1 XML/ThinQ2 provisioning HTTPS, a bounded CSR signer, metadata
observations, and durable mixed-protocol lifecycle/generation reservation.
The same daemon also owns optional LG bridge, Rhai, management and external MQTT
services. Release and appliance-validation limits are tracked in
[milestones](0.2-validation.md#milestones).

```toml
thinq1_bind = "127.0.0.1:5502"
mqtt_bind = "127.0.0.1:8883"
https_bind = "127.0.0.1:8443"
hostname = "local.example"
ca_certificate = "ca.pem"
ca_key = "ca-key.pem"
device_ledger = "devices.json"
legacy_tls = false
```

```sh
cargo run --release -p rusthinq-app --bin rusthinq -- config.toml
```

Paths are relative to the configuration file. Parent directories and an existing
valid CA are required. The configuration is bounded at 64 KiB and rejects unknown
fields, invalid bind addresses, malformed names, and nonboolean TLS options.
No CA is created or overwritten. The lifecycle checkpoint uses its existing
exclusive lock and atomic durability rules. All ports are bound before reserving
a generation block. A zero bind port is supported for test/local ephemeral use;
provisioning advertises the actual bound HTTPS/MQTT ports, not zero.

Device TLS front doors use the configured CA and DNS identity as their default.
They mint local certificates for valid requested SNI names, bounded to 64 distinct
names per front door; peers without SNI use the configured default identity.
`legacy_tls` explicitly selects the RTK_RTL8711am compatibility profile.
Device hostnames must still route to these endpoints. The firmware relay forwards
claimed remote hosts rather than terminating them locally; the optional LG bridge
supplies cloud/provisioning evidence for remote routing.

The shared HTTPS endpoint routes `/lgehadm/` paths to ThinQ1 and other paths to
the provisioning service, preserving each handler's method/body/error behavior.
It bounds headers and connection lifetime and closes after one response.
ThinQ1 metadata flows into L6; it does not itself establish device readiness.
ThinQ1 and device MQTT use the same generation registry and durable lifecycle.

Ctrl-C or SIGTERM stops listener admission, joins transport/lifecycle tasks, then
stops and joins the signer. The process prints application events and bound endpoint
addresses. Signer tasks are owned by Daemon::serve, whose future must be awaited
through shutdown rather than externally aborted. Daemon::prepare exposes endpoint
addresses and an application handle for embedding and integration tests.

Verification includes existing provisioning/CSR/error tests against the shared
HTTPS router, a ThinQ1 XML metadata route on the same listener, a strict-chain regression test for generated CA/server identities, a CA-verified
composed-runtime TLS request checking advertised ports, and joined shutdown.


<a id="runtime-optional-application-services"></a>
### Optional application services

The daemon accepts optional `management`, `drivers` and `external_mqtt` sections.
See [operations](0.2-operations.md) for configuration and API contracts. The HTTP
management service owns its bounded connections and WebSocket shutdown. GUI/API
remain available without external MQTT. Automatic model preparation provides the
scripts' opaque publications, commands and owned timer effects.
The external adapter durably inventories every retained publication and provides
individual, owner-wide, full and restart-safe deletion with QoS1 confirmation.


<a id="runtime-release-status"></a>
### Release status

Local and bridged paths, pairing controls, firmware/SNI routing, GUI/API, Rhai and
migration have implementation and test evidence. Remaining release work includes
production cutover, fixture revision bookkeeping and recorded environment limits.
See [milestones](0.2-validation.md#milestones) for acceptance rather than treating this runtime
configuration guide as a checklist. No live LG account or real appliance validation
is claimed. Model porting and deployment packaging follow host completion.

Server identities now include Subject/Authority Key Identifiers and generated CAs
include a Subject Key Identifier, addressing strict-client validation discovered
by the process smoke test. Existing CA material is loaded unchanged; supplied
legacy roots are not rewritten and may have their own strict-validation limits.


<a id="runtime-compile-time-capabilities"></a>
### Compile-time capabilities

`bridge`, `scripting` and `gui` are independent Cargo features, all on by default.
All eight combinations are supported at compilation. Examples:

```sh
# Full daemon without embedded GUI assets
cargo run --release -p rusthinq-app --no-default-features --features bridge,scripting -- config.toml
# Local device transports and management, without LG or Rhai
cargo run --release -p rusthinq-app --no-default-features -- config.toml
```

The core build preserves TLS/provisioning, durable lifecycle/model metadata and
retained MQTT cleanup. Omit `cloud_account` without bridge and `drivers` without
scripting; requesting an absent capability is an error before device startup.
Without GUI, `management.gui` defaults to false and explicit true is rejected.
Without bridge, firmware/SNI remote passthrough is absent. Without scripting,
script invocation returns an explicit disabled result. The adapter command
subscriber and driver watcher are compiled only with scripting.


<a id="runtime-reviewed-application-boundary"></a>
### Reviewed application boundary

Adapters receive `api::AppHandle`, which exposes application delivery/rejection,
projected events, metadata and cloud account requests. Composition uses
`runtime::Handle` to bind the single account owner and supply workers/transports;
adapters do not receive those lower handles or write receipts. L4 owns account
policy, L5 Scheduler/Preparation own script admission/order/timer decisions, and
L5 driver code reads/prepares Rhai sources. L6 runs and joins their effects and
checks lifecycle scope before dispatch. See the [M0 review](0.2-architecture.md#architecture-review).


<a id="runtime-configured-driver-reload-through-management"></a>
### Configured driver reload through management

The reviewed `api::AppHandle` now exposes an application-owned reload operation;
L7 receives only a generation or typed rejection, never a worker/Compiled/transport
handle. The runtime owns a bounded preparation JoinSet shared with automatic driver
admission through L5's preparation budget. Preparation reads remain in L5, scope
checks use L2/current model bindings, and the existing worker reload/init/timer
sequence is reused. Startup/file-watch and manual recovery therefore have the same
replacement semantics. Shutdown joins started jobs and returns Stopped to pending
callers. See [operations](0.2-operations.md#explicit-driver-reload-and-fault-recovery).

## Release builds and binary size

The workspace release profile uses size-oriented optimization (`opt-level = "s"`),
Thin LTO, one codegen unit and symbol stripping. It applies to the daemon and all
tools; normal development builds retain their existing behavior.

```sh
cargo build --release -p rusthinq-app --bin rusthinq
cargo build --release -p rusthinq-tools --bins
```

Plain `cargo build` produces development binaries. Use `--release`
for deployment. The default release still includes bridge, scripting and GUI;
features have not been removed to obtain a smaller default binary.

Panic unwinding is retained because Rhai/native callback isolation and signer
recovery use `catch_unwind`. `panic = "abort"` would change a contained fault into
process termination. Stripping removes symbol names from deployed artifacts, so
symbolic debugging requires an unstripped build. Thin LTO and one codegen unit
increase build time; no throughput improvement is claimed from size optimization.

OpenSSL remains vendored for device TLS compatibility and host-independent static
builds. Its native code contributes to size and is not rewritten by Rust LTO.
Disabling capabilities is a separate deployment choice:

```sh
cargo build --release -p rusthinq-app --bin rusthinq --no-default-features --features bridge,scripting
cargo build --release -p rusthinq-app --bin rusthinq --no-default-features
```

Measure the same target, features and source revision when comparing profiles.
Use file byte counts rather than filesystem block allocation, and distinguish
unstripped artifacts from stripped ones. A static musl binary and a dynamically
linked GNU binary are not a like-for-like size comparison.


<a id="build-recorded-measurement-2026-10-04"></a>
### Recorded measurement (2026-10-04)

Same source revision, default features and ARM64 GNU target:

| Release profile | Bytes | MiB |
| --- | ---: | ---: |
| Previous default | 23,671,768 | 22.58 |
| Size profile above | 12,677,000 | 12.09 |

The reduction is 46.4%. The optimized executable passed startup, management health,
embedded GUI, CA-verified default/SNI TLS and joined SIGTERM shutdown smoke checks.
These measurements include vendored OpenSSL and all default runtime capabilities;
they do not establish appliance compatibility or throughput. Two release-mode
native panic isolation tests also passed.

The rebuilt ARM64 musl static daemon is **11,824,288 bytes (11.28 MiB)** and
passed the same executable smoke checks. The pre-existing musl artifact was
22,832,784 bytes (21.77 MiB), or 16,215,336 bytes after stripping a copy. Its source
revision was not re-established, so use the GNU measurements above for the
controlled before/after comparison.

```sh
cargo build --release --target aarch64-unknown-linux-musl -p rusthinq-app --bin rusthinq
```

Cross/static builds also require the matching C compiler and linker for vendored
OpenSSL; the target triple alone does not install these tools.
