# Running the composed 0.2 device runtime

The `rusthinq` binary in rusthinq-app now composes ThinQ1 TLS, device MQTT TLS,
shared ThinQ1 XML/ThinQ2 provisioning HTTPS, a bounded CSR signer, metadata
observations, and durable mixed-protocol lifecycle/generation reservation.
This replaces separately running transport harnesses for this implemented scope.
It is not the complete 0.1 daemon or a certified non-inferior release.

```toml
thinq1_bind = "127.0.0.1:5502"
mqtt_bind = "127.0.0.1:8883"
https_bind = "127.0.0.1:8443"
hostname = "local.example"
ca_certificate = "ca.pem"
ca_key = "ca-key.pem"
device_ledger = "devices.json"
legacy_tls = false
```

```sh
cargo run -p rusthinq-app --bin rusthinq -- config.toml
```

Paths are relative to the configuration file. Parent directories and an existing
valid CA are required. The configuration is bounded at 64 KiB and rejects unknown
fields, invalid bind addresses, malformed names, and nonboolean TLS options.
No CA is created or overwritten. The lifecycle checkpoint uses its existing
exclusive lock and atomic durability rules. All ports are bound before reserving
a generation block. A zero bind port is supported for test/local ephemeral use;
provisioning advertises the actual bound HTTPS/MQTT ports, not zero.

All three listeners serve the configured DNS identity. Baseline TLS is the default;
legacy_tls explicitly chooses the existing RTK_RTL8711am compatibility profile.
The deployment must route its device hostnames to these endpoints; arbitrary SNI
identity issuance is not implicitly enabled. A shared L4 firmware relay is now
installed on HTTPS; completed current provisioning protects local endpoints.
Only validated cloud-adapter/operator evidence should learn remote names. The
CLI does not supply a real LG cloud adapter, so no remote URL learning is automatic.

The shared HTTPS endpoint routes `/lgehadm/` paths to ThinQ1 and other paths to
the provisioning service, preserving each handler's method/body/error behavior.
It bounds headers and connection lifetime and closes after one response.
ThinQ1 metadata flows into L6; it does not itself establish device readiness.
ThinQ1 and device MQTT use the same generation registry and durable lifecycle.

Ctrl-C or SIGTERM stops listener admission, joins transport/lifecycle tasks, then
stops and joins the signer. The process prints application events and bound endpoint
addresses. Signer tasks are owned by Daemon::serve, whose future must be awaited
through shutdown rather than externally aborted. Daemon::prepare exposes endpoint
addresses and an application handle for embedding and integration tests.

Verification includes existing provisioning/CSR/error tests against the shared
HTTPS router, a ThinQ1 XML metadata route on the same listener, a strict-chain regression test for generated CA/server identities, a CA-verified
composed-runtime TLS request checking advertised ports, and joined shutdown.

## Optional application services

The daemon accepts optional `management`, `drivers` and `external_mqtt` sections.
See [operations](0.2-operations.md) for configuration and API contracts. The HTTP
management service owns its bounded connections and WebSocket shutdown. GUI/API
remain available without external MQTT. Automatic model preparation and Rhai
compatibility helpers provide opaque publications, commands and owned timer effects.
The external adapter durably inventories every retained publication and provides
individual, owner-wide, full and restart-safe deletion with QoS1 confirmation.

## Release completion gates still open

- Wire per-device pairing management, outbound reconnect and device/cloud relay integration; LG HTTP/OAuth, durable account ownership, automatic token renewal and management/GUI account login/logout are implemented. ThinQ1/ThinQ2 pairing primitives and the durable account/incarnation-scoped intent store now exist; see [L4 implementation](0.2-l4-implementation.md).
- Required production hostname/identity coverage and appliance request replay.
- Complete broader 0.1 compatibility/migration review. Lifecycle on_drop, persisted model metadata and opt-in driver watch/reload are implemented.
- MQTT cloud/raw control routes, GUI device bridge controls and tool migration.
- 0.1 migration/rollback and final release audit.

Real-appliance/LG-account validation is excluded at the user's request. These
implementation gaps are not waived, and this executable does not establish full
M1–M5 acceptance.

Server identities now include Subject/Authority Key Identifiers and generated CAs
include a Subject Key Identifier, addressing strict-client validation discovered
by the process smoke test. Existing CA material is loaded unchanged; supplied
legacy roots are not rewritten and may have their own strict-validation limits.
